# 职责规矩由程序注入

职责规矩：程序按职责（pm、worker、reviewer、qa、explore）固定提供、用户改不到的流程规矩。定义正文：角色定义文件里头部设置下面的那段文字，用户在这里写专长和偏好。

## 用户故事
### P0：作为自定义子代理的用户，我想要只写描述就能用，改写正文也不丢流程规矩
**用例（主路径）**
- 场景：用户把 reviewer 复制成 security-reviewer，正文只写"重点看注入和鉴权"。
- 操作：PM 指定用 security-reviewer 审一个 worker 任务。
- 预期：审查照常核对需求边界、第三方依赖、界面原型、先红后绿，并额外关注注入和鉴权；结论照常分阻塞、建议、未验证。

### P0：作为写 Go 项目的用户，我想要在自己的 worker 正文里写规范，reviewer 按它审
**用例（主路径）**
- 场景：用户的 go-engineer 正文写着"新函数按 Go 官方库风格写说明注释"。
- 操作：go-engineer 交了一个新增函数但没写注释的任务，reviewer 审它。
- 预期：reviewer 收到这段正文，把"缺说明注释"列为阻塞。

### P1：作为做 PPT 的用户，我想要 worker 不写测试也能交付
**用例（边界）**
- 场景：任务是做一份汇报 PPT，没有可测行为。
- 操作：worker 不写测试，在结果里写明先红后绿不适用及理由，再交付。
- 预期：reviewer 不会因为没有失败测试的记录而打回。

## 约束
- C-1：当派出 worker、reviewer、qa、explore 或启动 PM 时，系统应把该职责的职责规矩加进提示词，放在定义正文之后，并写明职责规矩优先于正文。
- C-2：当定义正文为空时，系统应照常派出或启动，不报错。
- C-3：内置的 worker、reviewer、qa、explore 定义正文应为空。
- C-4：worker 做实现的那次运行，职责规矩应包含：只做派工任务，不清楚就停下并在结果里说明；只做最小改动；先把任务写成"步骤 → 验证项"；只用受控写文件和验证工具；遵守项目规范，不改项目规范文件；需要新依赖时不自己装，写进结果；有用户通过的原型时先读它，实现与它一致；先红后绿，没有可测行为时写明不适用及理由；测试名写明期望结果；用提交工具交结果，不伪造通过；不读需求全文和归档。
- C-5：worker 做原型的那次运行，职责规矩不应包含先红后绿，而应包含原型的交付要求：单个 HTML 文件，样式和脚本写在文件里；图形界面画出正常、空数据、加载中、出错四种状态，有交互的地方能点；终端界面用深色背景、等宽字体、80 列，多步交互按顺序画出每一步；有返工意见时按意见改。
- C-6：worker 的职责规矩不应包含说明注释的写法，也不应要求测试名带需求章节编号。
- C-7：reviewer 的职责规矩应包含：只审派工任务的改动，不改文件，先看本次 diff；核对目标、安全、鲁棒和性能条件；核对项目规范、界面原型、第三方依赖、需求里写明"不做、不改"的边界、先红后绿（含不适用的豁免）；结论分阻塞、建议、未验证；只跑被审任务范围的测试，不自填通过，不新增门槛。reviewer 的职责规矩不应包含说明注释的写法。
- C-8：当派出 reviewer 审查一个 worker 任务时，系统应把这个任务所用 worker 定义的正文交给 reviewer，并要求违反其中写明的规范列为阻塞；正文为空时不附加任何内容。
- C-9：qa 的职责规矩应包含现有的全部验收规矩；项目没有可交互入口时，QA 按测试名写明的期望结果对应验收场景，对上且通过的算已验证，对不上的标未验证。
- C-10：explore 和 pm 的职责规矩应包含它们现有的全部规矩。

## 验收
### AC-1 规矩加在正文之后 ← C-1
- 触发：派出一个子代理
- Given：职责是 worker，定义正文写着"擅长 React"
- When：读取这次运行的会话记录
- Then：提示词里先出现"擅长 React"，后出现 worker 的职责规矩，并写明职责规矩优先

### AC-2 正文为空照常运行 ← C-2、C-3
- 触发：派出一个子代理
- Given：用内置 worker、reviewer、qa、explore 中的任意一个
- When：查看定义文件和派出结果
- Then：定义正文为空，派出成功，提示词里有该职责的职责规矩

### AC-3 实现运行的规矩齐全 ← C-4、C-6
- 触发：派出 worker 做实现
- Given：任意 worker 任务
- When：读取提示词
- Then：包含 C-4 列出的每一项；不包含说明注释写法，也没有要求测试名带需求章节编号

### AC-4 原型运行不要求先红后绿 ← C-5
- 触发：派出 worker 做原型
- Given：一个界面任务
- When：读取提示词
- Then：包含 C-5 列出的原型交付要求，不包含先红后绿

### AC-5 reviewer 规矩齐全 ← C-7
- 触发：派出 reviewer
- Given：任意已完成的 worker 任务
- When：读取提示词
- Then：包含 C-7 列出的每一项核对，不包含说明注释写法

### AC-6 reviewer 收到 worker 正文 ← C-8
- 触发：派出 reviewer 审查
- Given：被审任务所用 worker 定义的正文写着"新函数要写说明注释"；另一个任务用的是正文为空的内置 worker
- When：分别读取两次审查的提示词
- Then：第一次带有这段正文，并要求违反时列为阻塞；第二次不附加任何正文

### AC-7 QA 按期望结果对应场景 ← C-9
- 触发：检查轮里派出 QA
- Given：项目没有可交互入口
- When：读取提示词
- Then：要求按测试名写明的期望结果对应验收场景，对不上的标未验证

### AC-8 explore 与 pm 规矩不丢 ← C-10
- 触发：派出 explore、启动 PM
- Given：两者的定义正文都为空
- When：读取提示词
- Then：分别包含 explore、pm 现有的全部规矩

## 验证路径
1. 复制 worker、正文写一句专长 → 派出实现 → 提示词里正文在前、规矩在后（AC-1、AC-3）。
2. 同一任务派原型 → 提示词里有原型要求，没有先红后绿（AC-4）。
3. 在 worker 正文写一条规范 → 派 reviewer → 提示词带这段正文；换内置 worker 时不带（AC-5、AC-6）。
