# 批准需求时带上原型

几个词先说清楚：
- 原型：一份单个 HTML 文件的界面设计，用户在浏览器里直接打开就能看。每份原型有名字和版本。
- 需求草稿：需求还没被用户批准的下一版内容，显示为"草稿，第 N 版"。用户在"确认原型"窗口里通过的原型，会写进草稿。
- 批准：用户同意某一版需求，这一版才交给 PM 去拆计划、派人实现。批准这一步现在由"批准需求"窗口完成；用户用 @ 指明需求说批准时，现在不弹这个窗口。
- 在途原型：设计师还在做，或者已经交稿、用户还没选通过、返工、放弃的那一版原型。

## 用户故事
### P0：作为用户，我想要批准需求时看清楚一起批准了哪些原型
**用例（主路径）**
- 场景：需求第 2 版批准过"命令行输出"第 1 版和"旧外观弹窗"第 1 版；草稿第 3 版里新通过了"设置页"第 3 版，移除了"旧外观弹窗"。
- 操作：用户说"批准"。
- 预期：弹出"批准需求"窗口，列出"这一版一起批准的原型（2 份）："，下面是绿色的"设置页 第 3 版 本次新确认"、普通颜色的"命令行输出 第 1 版 沿用第 2 版需求"、红色的"旧外观弹窗 第 1 版 本次移除"，最后一行"原型的样子以你在浏览器里通过的那一版为准。"；用户确认后第 3 版生效。

**用例（@ 指明需求）**
- 场景：草稿带原型。
- 操作：用户输入"@设置页支持深色模式 批准"。
- 预期：照样弹出带原型清单的"批准需求"窗口。

### P0：作为用户，我想要还有原型没定下来时不会被批准
**用例（异常）**
- 场景："设置页"第 3 版在等确认，"命令行输出"的设计师还在做。
- 操作：用户输入"@设置页支持深色模式 批准"。
- 预期：不弹批准窗口；主代理转告"还不能批准：原型「设置页」第 3 版还在等你确认，原型「命令行输出」设计师还在做。先把这两份处理完（通过、返工或放弃），再说批准。"

### P0：作为用户，我想要只改正文时原型照样在
**用例（主路径）**
- 场景：第 2 版需求批准过"设置页"第 2 版。
- 操作：用户只改正文，批准第 3 版。
- 预期：第 3 版里"设置页"标为沿用，PM 照样拿到它，用户不用重新确认原型。

## 约束
- C-1：当用户要批准的草稿里有在途原型时，系统应拒绝批准、不弹批准窗口，并把原因交给主代理：逐个写出在途原型的名称和状态（"第 v 版还在等你确认"或"设计师还在做"），建议先通过、返工或放弃它们再批准。
- C-2：当草稿带原型（包括本次要移除的）时，系统应在批准时弹出"批准需求"窗口，用户用 @ 指明需求时也弹。
- C-3：带原型时，"批准需求"窗口应在现有的需求、编号、仓库、简介之后显示"这一版一起批准的原型（N 份）："，每份一行：名称、"第 v 版"、标签。标签有三种：本次新确认（绿色）、"沿用第 M 版需求"（普通颜色）、本次移除（红色）；按新确认、沿用、移除的顺序排。N 只数新确认和沿用的份数。清单后显示"原型的样子以你在浏览器里通过的那一版为准。"
- C-4：当草稿不带原型时，批准的行为应和现在一样：用 @ 指明需求时不弹窗，窗口里没有原型清单。
- C-5：当用户在批准窗口里确认时，这一版需求应包含清单里新确认和沿用的原型，不包含移除的；当用户取消时，草稿和其中的原型都不变。
- C-6：当用户批准新版本时，草稿里没有改动过的原型应原样沿用，不需要用户再确认。
- C-7：当新草稿只改了原型、正文一个字没改时，用户应能批准它，版本号照常加 1。
- C-8：当用户批准新版本、而原型有变化时，PM 收到的需求更新通知里应写明：哪些原型是新确认的、哪些替换了旧版本、哪些被移除了。
- C-9：当批准开始写入时，草稿里的原型已和批准窗口显示的不一样，系统应拒绝这次批准，并且不留下任何挡住后续操作的记录：之后用户照常能改草稿、重新批准。批准写入进行中，登记原型决定、移除原型、派原型设计师都暂时被拒，原因写明需求正在批准、稍后再试。

## 验收
### AC-1 在途原型拦下批准 ← C-1
- 触发：用户批准
- Given：草稿里"设置页"第 3 版在等确认、"命令行输出"设计师还在做
- When：用户分别以不带 @ 和带 @ 的方式说批准
- Then：两次都没有弹窗、没有批准；主代理收到的原因逐个写出两份原型的名称和状态，并建议先处理

### AC-2 带原型一定弹窗 ← C-2、C-3
- 触发：用户批准
- Given：草稿里新通过"设置页"第 3 版，沿用第 2 版需求的"命令行输出"第 1 版，移除"旧外观弹窗"第 1 版
- When：用户输入"@<需求> 批准"
- Then：弹出"批准需求"窗口；标题行是"这一版一起批准的原型（2 份）："；三行依次是绿色的新确认、普通颜色的"沿用第 2 版需求"、红色的本次移除；最后一行是"原型的样子以你在浏览器里通过的那一版为准。"

### AC-3 首次批准 ← C-3
- 触发：用户批准第 1 版
- Given：草稿里只有"设置页"第 2 版
- When：查看批准窗口
- Then：清单是"这一版一起批准的原型（1 份）："和"设置页 第 2 版 本次新确认"

### AC-4 不带原型保持现状 ← C-4
- 触发：用户批准
- Given：草稿和已批准版本都不带原型
- When：用户用 @ 指明需求说批准；另一次不带 @
- Then：带 @ 时不弹窗，直接按现在的流程批准；不带 @ 时弹出的窗口没有原型清单

### AC-5 确认与取消 ← C-5
- 触发：批准窗口里确认或取消
- Given：AC-2 的草稿
- When：一次取消，一次确认
- Then：取消后草稿里三份原型的状态不变；确认后新版本里有"设置页"和"命令行输出"，没有"旧外观弹窗"

### AC-6 没改的原样沿用 ← C-6
- 触发：批准新版本
- Given：第 2 版批准过"设置页"第 2 版；第 3 版草稿只改正文
- When：批准第 3 版
- Then：第 3 版里有"设置页"第 2 版；期间没有弹出确认原型的窗口

### AC-7 只改原型也能批准 ← C-7
- 触发：批准新版本
- Given：第 2 版已批准；草稿正文没改，只新通过了"设置页"第 3 版
- When：批准
- Then：批准成功，生成第 3 版，第 3 版里是"设置页"第 3 版

### AC-8 PM 收到原型变化 ← C-8
- 触发：批准新版本
- Given：第 2 版需求里有"设置页"第 2 版和"旧外观弹窗"第 1 版；第 3 版草稿里"设置页"换成新通过的第 3 版，新通过"命令行输出"第 1 版，移除"旧外观弹窗"
- When：PM 收到需求更新通知
- Then：通知里写明"设置页"替换为第 3 版、"命令行输出"新确认、"旧外观弹窗"被移除

### AC-9 原型中途变了不卡死 ← C-9
- 触发：用户在批准窗口点确认
- Given：窗口显示之后、写入之前，另一份原型被用户通过
- When：批准被拒后，主代理改草稿并再次发起批准
- Then：第一次被拒，原因写明原型在批准过程中变了；之后改草稿成功，再次批准时窗口列出新的清单，确认后批准成功

## 验证路径
1. 派"设置页"，还在做时说批准 → 被拦下，主代理转告原因（AC-1）。
2. 通过"设置页"后用 @ 说批准 → 弹窗里有原型清单 → 确认（AC-2、AC-3、AC-5）。
3. 只改正文再批准 → "设置页"标为沿用（AC-6）。
4. 正文不动，只重做"设置页"并通过，再批准 → 生成新版本，PM 的更新通知里写明替换（AC-7、AC-8）。
