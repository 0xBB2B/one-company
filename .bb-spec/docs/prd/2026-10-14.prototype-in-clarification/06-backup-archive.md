# 备份与归档带上原型

几个词先说清楚：
- 原型：一份单个 HTML 文件的界面设计，用户通过后写进需求，批准需求时一起批准。原型文件存在本机数据目录里，不在业务仓库里。
- 批准版本：用户批准过的某一版需求，包含这一版的正文和原型。
- 备份与恢复：用户让主代理把本机的需求数据打包保存，之后可以原样恢复。
- 归档：需求完成后，程序把最终的需求正文写进项目仓库里的需求归档目录，随交付一起提交。

## 用户故事
### P1：作为用户，我想要恢复备份后原型还在
**用例（主路径）**
- 场景：需求第 2 版批准时带着"设置页"第 3 版，PM 正在派任务。
- 操作：用户做一次备份，换一台机器恢复。
- 预期：恢复后 PM 派出的 worker 照样拿到"设置页"第 3 版，能打开这个文件。

### P1：作为用户，我想要需求完成后在项目仓库里找到当时的原型
**用例（主路径）**
- 场景：需求最终批准的版本带"设置页"和"命令行输出"两份原型。
- 操作：需求完成，程序归档。
- 预期：项目的需求归档目录里，除了这个需求的正文，还有这两份原型的 HTML，文件名里能看出原型名称；双击就能在浏览器里打开。

## 约束
- C-1：当用户备份时，备份应包含每个需求所有批准版本引用的原型文件；草稿里还没批准的原型不保证包含。
- C-2：当用户从备份恢复后，批准版本引用的原型应能照常交给子代理，内容和指纹与备份前一致。
- C-3：当需求完成归档时，系统应把最终批准版本里的每份原型 HTML 和需求正文一起写进项目的需求归档目录；每份原型的文件名里能看出它属于哪个需求、叫什么名字；文件内容与用户通过的那一版一致。
- C-4：归档里的原型文件应和需求正文一起随交付提交，交付检查不因为多了原型文件而失败。
- C-5：当最终批准版本没有原型时，归档的结果应和现在一样。

## 验收
### AC-1 备份带原型 ← C-1
- 触发：用户备份
- Given：需求第 1 版批准过"设置页"第 2 版，第 2 版批准过"设置页"第 3 版；草稿里有刚通过、还没批准的"命令行输出"第 1 版
- When：查看备份内容
- Then：包含"设置页"第 2 版和第 3 版的文件

### AC-2 恢复后可用 ← C-2
- 触发：从 AC-1 的备份恢复
- Given：恢复到另一个本机数据目录
- When：PM 按第 2 版派出 worker，worker 读原型
- Then：读到"设置页"第 3 版，指纹与备份前一致

### AC-3 归档写入原型 ← C-3、C-4
- 触发：需求完成归档
- Given：最终批准版本带"设置页"第 3 版和"命令行输出"第 1 版
- When：查看归档提交
- Then：需求归档目录里有需求正文和两个 HTML 文件，文件名能看出需求和原型名称，内容与通过的版本逐字节一致；交付检查通过

### AC-4 没有原型照旧 ← C-5
- 触发：需求完成归档
- Given：最终批准版本没有原型
- When：查看归档提交
- Then：和本需求之前一样，只有需求正文

## 验证路径
1. 带原型批准需求 → 备份 → 恢复到新目录 → PM 派出的 worker 能读到原型（AC-1、AC-2）。
2. 让需求走到完成 → 归档提交里有正文和原型 HTML，交付检查通过（AC-3）。
3. 不带原型的需求走到完成 → 归档和以前一样（AC-4）。
