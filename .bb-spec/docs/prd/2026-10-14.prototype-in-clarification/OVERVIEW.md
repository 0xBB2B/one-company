# 原型设计挪到主窗口澄清阶段

## 背景与问题
- 原型：一份单个 HTML 文件的界面设计，用户在浏览器里打开就能看到界面长什么样。现在的原型要等需求批准、PM 拆完计划之后才做：PM 给要改界面的任务打上标记，先派 worker 出原型，用户在 PM 面板里确认，确认后才派实现。
- 原型本来是帮用户把界面需求说清楚的，却排在需求批准之后。用户看了原型改主意，就得回主窗口更新需求、再批准一次，PM 再复核计划，来回很慢。
- 现在的原型挂在 PM 计划里的单个任务上，判断"通过"时只看这个任务最新一版原型的决定，不看它对应的是哪一版需求。需求出了新版本，旧原型照样算通过。
- 用户想用带自家设计规范的设计师出原型，现在只能复制 worker 定义来改，而 worker 定义同时还用来写代码。

## 目标
- 需求涉及界面时，主代理在澄清阶段就派原型设计师出原型，用户在批准需求之前看到界面。
- 用户对原型的每个决定（通过、返工、放弃、移除）都由用户在程序窗口里亲手选，不经过任何模型转述。
- 只有用户通过的原型才写进需求草稿；批准需求就是连同草稿里的原型一起批准。
- PM、worker、reviewer、qa 都从批准的需求版本里拿原型，不再有 PM 那套原型流程。
- 用户能在 /one:agents 里自定义原型设计师，主代理按描述挑选。

## 非目标
- 主代理自己写原型 HTML。
- 原型以图片、设计工具文件或文字描述的形式给用户看。
- 升级前已在进行、计划里带旧原型记录的需求做迁移或兼容处理。
- 撤销"移除原型"：移除后想要回来，就再派一次原型设计师出新版本。
- 把原型和 PM 计划里的具体任务一一对应。
- 新旧两版原型的差异对比。
- PM 或其他子代理派原型设计师。

## 整体验证路径
1. 在主窗口提一个要改设置页的需求 → 主代理先建需求草稿，再派原型设计师出"设置页"原型。
2. 设计师交稿 → 浏览器自动打开这份 HTML，主窗口弹出"确认原型"窗口 → 选返工，写"开关放到标题右边" → 对话里显示已登记，主代理接着重派设计师，设计师拿到上一版文件和这句原话。
3. 第 2 版交稿后选通过 → 对话里显示"已通过，已写进需求草稿"。
4. 说"批准" → 弹出"批准需求"窗口，清单里有"设置页 第 2 版 本次新确认" → 确认。
5. PM 拆计划 → 派出的 worker、reviewer、qa 收到的任务说明里都有这份原型的位置。
6. 再改一版正文、不动界面并批准 → 新版本里"设置页"标为沿用，PM 派出的任务照样拿到它。
7. 再派一次设计师，在它还没交稿时说"批准" → 程序拦下，主代理转告"原型「设置页」设计师还在做"。

## 决策记录
- **质疑结论**：用户在 2026-10-13 和 2026-10-14 已经比较过"主代理自己写 HTML"并否决：原型 HTML 会占满主窗口的上下文；用户也没法自定义一个带设计规范 skill 的设计师。保留 PM 那套流程也被否决：原型排在批准之后，用户改主意要来回走一遍批准和复核。
- **原型是需求草稿的一部分，批准需求就是一起批准原型**（用户 2026-10-14 决定）：这取代了最初方向里"需求出新版本时，原型要用户在新版本里再确认才算数"。用户的原话是"用户确认通过之后，才算是最终落到需求文档里。也就是输入需求一旦通过，代表着 UI 设计相关内容也算通过"。被否决的做法是每次出新版本都逐份重新确认原型：界面没改时这一步纯属重复。
- **原型一律是 HTML，用户只看 HTML**（用户 2026-10-14 决定）：终端界面也在 HTML 里模拟 80 列终端。不让模型用文字转述原型，用户看到的就是实现要照着做的那一份。
- **用户的决定只由程序窗口记下**：沿用现在"确认原型"窗口的做法。威胁模型"模型输出不可信"要求主代理不能替用户说"这版可以"；主代理只能让程序弹窗。
- **在途原型拦下批准**（用户 2026-10-14 决定）：被否决的做法是批准时忽略在途原型。那样用户批准了，设计师随后交的稿却进不了这一版，用户容易以为它已经算数。
- **草稿带原型时批准一定弹窗**（用户 2026-10-14 决定）：用 @ 指明需求时现在不弹批准窗口，但原型清单必须让用户亲眼看到，所以带原型时也弹。没带原型时保持现状。
- **一个需求可以有多份带名字的原型**（用户 2026-10-14 决定）：一个需求常常同时改几处界面。名字由主代理派出设计师时起；同名再派就是这份原型的新版本，新名字就是新一份原型。这是按确认过的预览定的默认做法，用户可以推翻。
- **同一份原型同时只能有一版在途**：同名的上一版还在做或还没确认时再派，程序拒绝。否则两版同时等确认，用户分不清哪版是最新的。
- **文件在交稿后被改过，这一版作废**（用户 2026-10-14 决定，写实施计划时发现）：只拒绝登记的话，这一版会一直在途，需求再也批不了。作废后主代理重新派设计师即可。一时读不到文件（权限、磁盘错误）不作废，免得误伤。
- **名称只差大小写或写法时拒绝派出**（用户 2026-10-14 决定，写实施计划时发现）：macOS 默认的文件系统不分大小写，"Settings"和"settings"会写进同一个文件，覆盖已通过的版本。被否决的做法是把它们自动当成同一份原型，那会改变"同名"的含义。
- **移除只能在程序窗口里亲手做，不能撤销**（用户 2026-10-14 决定移除方式）：撤销要再加一套机制；想要回来时再派一次设计师即可。
- **返工意见由程序原话交给设计师**：返工后主代理负责重派，但用户写的意见由程序直接附给设计师，不经主代理转述。
- **原型设计师是新职责，不复用 worker**：worker 定义同时用来写代码，用户自定义设计规范时会互相干扰。栏名和内置定义名都用 `prototype`（用户 2026-10-14 决定），和 worker、explore 一样用英文职责名。
- **只能由主窗口派出**：原型属于澄清阶段，澄清只在主窗口进行。PM 派不了，防止批准后的流程再绕回"PM 自己出原型"。
- **默认跟随主窗口的模型和思考等级**：沿用需求一"内置定义默认跟随派出方"的做法；原型设计师只由主窗口派出，所以跟随主窗口。
- **轮数上限沿用主窗口派检索的做法**：主代理派出时写明 1 到 100 轮，程序设进会话配置，用满就停。
- **原型文件上限 1 MiB 保留**：这是现有上限。原型文件会交给 worker、reviewer、qa 读，上限保护的是这些下游模型的输入大小。
- **自定义设计师按描述挑，用户点名的优先、点名的用不了不换**（用户 2026-10-14 决定）：主窗口只能看到原型设计师这一类定义的列表。用户点名的定义用不了时换一个，用户会以为用了自己的设计规范。
- **PM 遇到缺原型的界面任务只能上报，用户只能回主窗口补原型**（用户 2026-10-14 决定）：被否决的做法是让 PM 自己派设计师或让用户跳过原型。前者绕过澄清阶段，后者让 reviewer 的"改了界面但需求里没有原型就阻塞"失去依据。
- **下游拿批准版本里的全部原型**：不再把原型和任务一一对应，免得 PM 再给任务打界面标记。没改界面的任务拿到原型也不受影响。
- **旧数据不做处理**（用户 2026-10-14 决定）：升级前已在进行、计划里带旧原型记录的需求，README 里写明先做完或取消再升级。这遵守项目"不做向后兼容"的规矩，也符合威胁模型"旧流程与旧记录不产生授权"。
- **备份和归档都带上原型**（用户 2026-10-14 决定）：原型是批准版本的一部分，恢复或归档后少了原型，需求就不完整。备份只保证批准版本引用的原型；草稿里还没批准的原型不保证。
- **只改原型、正文没改也能出新版本**：原型是需求的一部分，原型变了就是需求变了。现在的批准流程收不收"正文一字未改"的新版本，写实施计划时核对代码；改动大就停下问用户。
- **输入栏下方的面板改叫"状态面板"**（用户 2026-10-14 决定，实施时提出）：面板里除了 PM 的运行和事项，还有主窗口派出的检索和这次加的原型设计，"PM 面板"名不副实。只改说明、提示词和注释里的叫法，代码文件名是内部名字，不改。
- **所有程序窗口排队**（用户 2026-10-15 决定，实施时发现）：pi 打开新的程序窗口时直接替换当前窗口，被替换的那个永远等不到结果。交稿自动弹窗是第一个不经用户或主代理主动操作就出现的窗口，会和提问、批准等窗口互相挤掉，让对应的工具调用一直卡住。被否决的做法是交稿后不自动弹窗、改由主代理打开，那和确认过的"交稿即弹窗"不同。
- **批准开始写入时就核对原型，批准进行中锁住原型看板**（用户 2026-10-15 决定，实施时发现）：原先在写入的最后一步才核对原型有没有变，被拒时已经留下一条进行中的批准记录，之后改草稿和批准全被它挡住，需求卡死。被否决的做法是重试时改用当前的原型集合，那样批准的就不是用户在窗口里看到的清单。
- **代价**：写代码约 2.5 到 3 天。改了 PM 和主代理的提示词，合并前要跑全部真实模型验收：单点 P1 到 P12、零自定义完整流程 M9-AC12，以及渐进需求完整流程 M9-AC2、AC3、AC11，一整批约 2500 万 token。
