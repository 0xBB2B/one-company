# 代码按功能模块拆进 src/

## 背景与问题
- 源码平铺在三个目录里：`runtime/` 有 125 个文件，`extensions/` 16 个，`daemon/` 13 个，都没有子目录。维护时要在 150 多个文件里翻。
- 同一个功能的代码散在两三个目录里。例如 Git 交付，主窗口注册的部分在 `extensions/git-delivery.ts`，交付逻辑在 `runtime/git-delivery.ts`。
- 新文件放哪、模块之间能不能互相引用，都没有规矩，也没有检查。
- 仓库根上，代码目录和程序运行时读取的素材目录（agents/、rules/、role-rules/、shared/、skills/、resources/）混在一起。

## 目标
- 一个功能的全部源文件只在一个目录里：底层放在 `src/core/<名>/`，功能放在 `src/modules/<名>/`，pi 入口和守护进程的组装代码放在 `src/app/`。
- 模块排成上下层，只能上层引用下层；违反时测试失败。
- 不改任何产品行为：包能照常安装、运行，现有测试和真实模型验收全部通过。

## 非目标
- 统一封装外部命令（git、ps 的调用各自保持原样，另起一轮）。
- 搬测试文件：`tests/` 的位置不动。
- 改任何产品行为、提示词、报错文字。
- 给模块加 `index.ts` 统一出口；把包拆成多个 pi 扩展；模块之间改用 `pi.events` 通信。

## 整体验证路径
1. 看仓库根 → 没有 `runtime/`、`extensions/`、`daemon/`；`src/` 下只有 `core`、`modules`、`app` 三个目录。
2. 跑类型检查、单元、集成、安装四项纯代码测试 → 全部通过，其中包括架构测试。
3. 在 `src/modules/requirement/` 的任一文件里临时加一行引用 `src/modules/pm/` 的 import，再跑架构测试 → 失败，报错写明文件、行号、上层模块名和被引用的文件。
4. 用 `pi install` 装上本地包、打开 pi → `/one:setting`、`/one:ps` 都能打开，守护进程能启动。
5. 跑全部真实模型验收（P1–P13、M9-AC12、M9-AC2/AC3/AC11）→ 全部通过。

## 决策记录
- **质疑结论**：更便宜的替代是继续用 AGENTS.md「查功能、查问题的规矩」第 2 条，按需求文档的 `features:` 和 `git log --grep` 找代码。它只能查到"改过哪些文件"，看不出模块边界，也管不住以后新文件放哪。用户 2026-10-16 决定做，选了"按功能分模块"，不选"只在 runtime/ 里按功能建子目录"——后者让同一个功能仍然分在主窗口、守护进程、逻辑三个目录里，只是缓解。
- **管住以后不再乱的是测试，不是目录名**：目录排成什么样都挡不住新代码乱放、乱引用，真正起作用的是两条架构测试（每个源文件必须在模块目录里、只能上层引用下层）。
- **布局用 src/core + src/modules + src/app**（用户 2026-10-16 决定）：和 pi 自己的源码布局一致（pi 是 `src/core/…` 加 `src/modes/<运行方式>/…`）；代码全部收进 `src/`，仓库根上只剩素材目录。被否决的是"core/、modules/ 放仓库根，extensions/、daemon/ 只留组装代码"：少改约 6 处路径，但代码目录和素材目录还是混在仓库根上，`extensions/` 也名不副实。功能模块套一层 `modules/`，是因为仓库根上已有放角色定义文件的 `agents/`，不套会和 agents 模块同名。
- **模块之间单向引用，挪 4 处代码让规则成立**（用户 2026-10-16 决定）：实测 main `ce7c3f7` 上文件之间的 657 条 import 没有循环；按功能分组、排好上下层后，只有 4 处是下层引用上层，都在守护进程客户端和通信格式里。被否决的做法：一是把这两个文件写成例外，规则从一开始就有洞；二是只分目录、不立规矩，"所有功能解耦"的目标落空。
- **请求参数校验表放进组装层**（用户 2026-10-16 决定，写实施计划时发现）：原定把通信格式用到的三组格式定义挪进 core，但知识查询的格式依赖项目索引的查询限额和索引路径规则（约 400 行、会调用 git），硬挪会把项目索引拆在 core 和 modules 两处。改为把那张校验表、守护进程的通信服务端（全项目只有它调用这张表）和项目索引在守护进程里的宿主一起放进 `src/app/daemon`，代价是项目索引的宿主代码不在 project-index 目录里。被否决的还有"各模块注册自己的请求格式"：最解耦，但要改服务端接口和 5 个测试，和这一轮只搬不改冲突，可以以后单独做。
- **不加 `index.ts` 统一出口**（用户 2026-10-16 决定）：文件之间没有循环，统一出口解决不了实际问题，只会多出 14 个转发文件，每加一个公开函数要改两处。
- **测试文件不搬**（用户 2026-10-16 决定）：测试文件名和源文件名基本一一对应，按名字就能找到；一起搬的话改动量大约翻倍，审查时更难分清哪些是搬家、哪些是真改了代码。
- **外部命令只搬到一起，不统一封装**（用户 2026-10-16 决定）：6 处各自调用 git 的代码参数和超时各不相同，统一封装会改变行为，和这一轮"只搬不改"冲突，另起一轮做。
