# 提问不用人称代词，点选回答带上选项理由

## 背景与问题
- 提问窗口：主代理调用 `one_company_user_interact` 的 ask 动作后，程序弹出的选择窗口。需求澄清提问和面板事项提问（主代理针对面板上的待办事项问用户）用的是同一种窗口。
- 选项理由（reason）：主代理给每个选项写的一句说明。用户在窗口里点选某一项，程序就把"这一项的标题 + 理由"记成用户这一轮的原话，交给草稿核验器。草稿核验器是程序内部的一次模型调用，检查需求草稿有没有超出用户原话。
- 2026-10-19 在企微 BOT 需求里，主代理按点选结果改草稿，第一次提交连续被核验器拒绝，原因有两个：
  - 返回给主代理的回答只有"选第 2 项：标题（推荐）"，不带理由。主代理漏写了理由里已经定下的"计划交付日期、优先级"，把它写成了待明确。
  - 选项理由写的是"由你确认通过"，草稿写成"由负责人确认通过"。核验器看不出"你"就是负责人，判为换了主体。主代理为了过核验，把 PRD 改成了"由你确认"，以后读 PRD 的人不知道"你"指谁。

## 目标
- 提问窗口里主代理写的每一段文字都不含"我""你""您"，改用"用户""AI""负责人"这类角色词。
- 用户点选某一项后，主代理拿到的回答文字和交给核验器的用户原话完全相同。

## 非目标
- 不改草稿核验器的提示词，不让核验器把"我/你"自动当成用户的角色。原因：这等于放宽核验，主代理把"我"写成错的角色时核验器就查不出来。
- 不检查用户自己在"其他"里输入的文字，也不检查主代理在对话里直接说的话。
- 不改程序固定的面板事项选项文字（如"再给一次机会，轮数上限 N"），它们本来就不含人称代词。
- 不改终端里提问结果的显示样式。

## 整体验证路径
1. 主代理发起需求澄清提问，某个选项理由写"由你确认" → 登记被退回，退回原因写明哪个字段含"你"、要改成角色词。
2. 主代理改成"由负责人确认"后重新提问 → 窗口正常弹出。
3. 用户点选这一项 → 主代理拿到的 answer.text 是"标题、换行、理由"两行，和核验器收到的用户原话一字不差。
4. 主代理按 answer.text 改草稿，草稿写"由负责人确认" → 核验器放行，第一次提交就保存成功。

## 决策记录
- 人称问题从提问一侧解决（禁止提问文字用"我/你/您"），不从核验器一侧放宽。用户 2026-10-19 决定。被否决的方向：核验器提示词加一句"我/你指用户本人，写成用户的角色不算换主体"，会让核验器少检查一步。
- 用程序检查加主代理规则，不只写规则。原因：只写在提示词里模型会漏，漏一次就被核验器拒一次；程序检查能在弹窗之前挡住。用户 2026-10-19 决定。
- 检查 question、rootCheck、label、reason、recommendedReason 五处，字为"我""你""您"（"我们""你们"一样会被退回）。rootCheck 不进入用户原话，也一起查，是为了让整个提问窗口口吻一致；查"您"是防止模型改写"您"绕过。代价是"自我"这类偶然含这些字的词也会被退回重写一次。用户 2026-10-19 决定。
- 选项理由放进 answer.text（改成和用户原话相同的两行），不另加 reason 字段。原因：主代理和核验器看同一份原话，主代理不用自己把两段拼起来。这推翻了 commit 78b8605 里"返回给主代理的 answer.text 不变"的做法。用户 2026-10-19 决定。
- 需求澄清提问和面板事项提问两种都改。原因：两者用同一套格式检查和同一条"点选=标题+理由"的规则，只改一种会让两边规则不同。用户 2026-10-19 决定。
- 质疑结论：值得做。不改的话，每次被拒都要多跑一轮模型；为了过核验，主代理还会把"你"写进 PRD，PRD 质量变差。
