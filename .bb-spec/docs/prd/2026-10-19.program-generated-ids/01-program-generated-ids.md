# 新操作的编号由程序生成

## 用户故事
### P0：作为在 pi 里用 one-company 的开发者，我想要主代理和 worker 不用自己造编号就能调用工具，以便少一次 Bash 调用、不依赖本机装了 python3，也不会因为编号格式拼错被拒

**用例（主路径）**
- 场景：开发者在一个样例项目里对主代理说"增加手机号验证码登录"。
- 操作：主代理调用 `one_company_requirement_manage` 的 create，只填 repoId、summary、title、body，不填 `requestId`、`operationId`。
- 预期：草稿建成功，结果里带有需求编号和这次保存的操作编号。会话记录里，这次调用之前没有生成 UUID 的 Bash 命令。

**用例（边界）**
- 场景：同一个主代理连续调用两次 updateDraft，两次内容不同。
- 操作：两次都不填 `operationId`。
- 预期：两次都成功，各自结果里的操作编号不同，需求版本号依次加一。

### P0：作为开发者，我想要中断的操作在程序给出原编号后能续完，以便进程崩溃后需求不会一直被锁住

**用例（主路径）**
- 场景：主代理保存需求草稿时，主窗口进程在写入中途退出。
- 操作：重新打开主窗口后，主代理对同一个需求再发起一次 updateDraft。
- 预期：
  - 调用被拒，报错写明"这个需求还有一次没完成的保存"，并给出那次保存的操作编号，以及"带上这个编号和原来的内容再调一次"的下一步建议。
  - 主代理照抄这个编号，带原内容再调一次后，保存完成，需求解锁。

**用例（异常）**
- 场景：主代理续做时填了原编号，但内容和原来那次不一样。
- 操作：调用 updateDraft，填报错给出的编号，title 改了一个字。
- 预期：调用被拒，报错说明内容与原操作不同，建议带原来的内容续做。需求仍是锁住的状态，没有写入新内容。

## 约束
- C-1：`one_company_requirement_manage`、`one_company_user_interact`、`one_company_project_manage`、`one_company_workflow_manage`、`change_apply` 这 5 个工具，所有动作都能在不填 `requestId`、`operationId` 时调用成功。新操作的编号由程序在每次调用时生成，是合规的 UUIDv7。
- C-2：每次写入类调用的结果里都带有本次的操作编号。连续两次不填编号的调用，得到两个不同的编号，是两次独立的操作。
- C-3：这 5 个工具的说明里没有要求模型生成编号的话，不出现"新生成""UUIDv7"字样。说明里写明：操作编号只在续做时填，而且只填报错或结果里给出的那个编号。
- C-4：凡是报错或结果要模型"用原来的操作编号继续"的地方，都必须给出这个编号。已知的场景有：
  - 需求保存（create、updateDraft）中断，或者还有一次没完成的保存。
  - 关闭需求返回"关闭中"，或者已有一次没完成的关闭。
  - 工作区准备中断。
  - 备份、恢复中断。
  - change_apply 写到一半，或者部分文件写入失败。
- C-4b：批准（confirmUpdate）的状态一次写完：要么完整生效，要么什么都不写，不会留下需要续做的半截批准；confirmUpdate 不接受 operationId。另一次保存还没做完时，批准被拒，报错给出那次保存的操作编号。
- C-5：带上 C-4 给出的编号、带原来的内容再调一次，程序会把原操作做完，结果和原操作一次做完时相同。
- C-6：填了操作编号，但它不属于这个目标上一次没完成的同类操作时，调用被拒。三种情况都算：编号不存在、那次操作已完成或已失败、编号属于别的需求或别的动作。报错写明是哪种情况，并建议"不填编号重新发起"或"按报错给出的编号续做"。内容与原操作不同时也被拒，报错建议带原内容续做。
- C-7：编号由程序生成后不可能再发生的报错，从代码里删掉。至少包括"这个操作编号之前已失败过，不能再用"和"需求编号已被占用"。需求编号撞号时，程序自己换一个编号重来，模型看不到。
- C-8：在仓库根执行 `grep -rn '新生成' src | grep -v '重新生成'`，没有输出。
- C-9：除了编号由谁生成、续做时怎么拿到原编号、批准一次写完，需求的起草、提问、批准、派工、写入、关闭、工作区、备份恢复的行为都和改动前一样。改动前已有的纯代码测试，去掉自造编号后全部通过。

## 验收
- [ ] C-1：对 5 个工具的每个写入动作，不填 `requestId`、`operationId` 各调用一次 → 都成功，程序生成的编号符合 UUIDv7 格式。
- [ ] C-2：同一个需求连续两次不填编号调用 updateDraft → 两次结果里的操作编号不同，版本号依次加一。
- [ ] C-3：5 个工具的说明文字里没有"新生成""UUIDv7"，并写明操作编号只在续做时照抄报错或结果给出的编号。
- [ ] C-4：C-4 列出的每种场景各造一次中断或未完成状态 → 报错或结果里都给出原操作编号。
- [ ] C-4b：在批准的写入过程中注入一次写入失败 → 调用被拒；需求记录、事件、批准使用记录、操作记录、写占用都和调用前一样；随后不填编号重新批准成功。另造一次没完成的 updateDraft，再批准 → 被拒，报错给出那次保存的编号。confirmUpdate 填 operationId → 参数不合格被拒。
- [ ] C-5：C-4 的每种场景照抄编号、带原内容续做 → 原操作完成，结果和一次做完时相同。
- [ ] C-6：分别填不存在的编号、已完成操作的编号、别的需求的编号、内容不同的原编号 → 都被拒，报错写明具体原因和下一步建议，状态没有变化。
- [ ] C-7：代码里找不到"这个操作编号之前已失败过""需求编号已被占用"这两条报错；模拟需求编号撞号 → create 仍然成功。
- [ ] C-8：`grep -rn '新生成' src | grep -v '重新生成'` 没有输出。
- [ ] C-9：类型检查、单元、集成、安装四项纯代码测试全部通过；全部真实模型验收（P1–P13、M9-AC12、M9-AC2/AC3/AC11）通过，这些运行的主代理和 worker 会话记录里没有生成 UUID 的 Bash 命令。

## 验证路径
1. 执行 `grep -rn '新生成' src | grep -v '重新生成'` → 没有输出。
2. 跑 `pnpm run typecheck`、`pnpm test`、`pnpm run test:integration`、`pnpm run test:installation` → 全部通过。
3. 在样例项目里，让主代理不填编号建一份需求草稿并改一次 → 两次都成功，操作编号不同。
4. 制造一次需求保存中断，再发起新保存 → 报错给出原编号；照抄编号、带原内容续做 → 保存完成，需求解锁。
5. 跑全部真实模型验收 → 全部通过；在会话记录里搜 `uuid` → 没有模型执行的生成编号命令。
