# 新操作的编号由程序生成

## 用户故事
### P0：作为在 pi 里用 one-company 的开发者，我想要主代理和 worker 不用自己造编号就能调用工具，以便少一次 Bash 调用、不依赖本机装了 python3，也不会因为编号格式拼错被拒

**用例（主路径）**
- 场景：开发者在一个样例项目里对主代理说"增加手机号验证码登录"。
- 操作：主代理调用 `one_company_requirement_manage` 的 create，只填 repoId、summary、title、body。
- 预期：草稿建成功，结果里带有需求编号和这次保存的操作编号。会话记录里，这次调用之前没有生成 UUID 的 Bash 命令。

**用例（边界）**
- 场景：同一个主代理连续调用两次 updateDraft，两次内容不同。
- 操作：两次都只填需求编号、版本号和内容。
- 预期：两次都成功，各自结果里的操作编号不同，需求版本号依次加一。

### P0：作为开发者，我想要中断的操作用原来的内容再调一次就能续完，以便进程崩溃后需求不会一直被锁住

**用例（主路径）**
- 场景：主代理保存需求草稿时，主窗口进程在写入中途退出。
- 操作：重新打开主窗口后，主代理用原来的标题和正文，对同一个需求再调一次 updateDraft。
- 预期：程序认出这是那次没做完的保存，用原编号把它做完，需求解锁；结果和一次做完时相同。

**用例（异常）**
- 场景：那次保存没做完，主代理这次带的内容和原来那次不一样。
- 操作：调用 updateDraft，title 改了一个字。
- 预期：调用被拒，报错写明"这个需求还有一次没完成的保存"，建议先用原来的内容再调一次把它续完，再做新的保存。需求仍是锁住的状态，没有写入新内容。

## 约束
- C-1：`one_company_requirement_manage`、`one_company_user_interact`、`one_company_project_manage`、`one_company_workflow_manage`、`change_apply` 这 5 个工具，参数里没有让模型填写的新操作编号（`requestId`、`operationId`），带了就是参数不合格。新操作的编号由程序在每次调用时生成，是合规的 UUIDv7。引用已有东西的编号照旧由模型从结果里抄，例如 `savedOperationId`、`backupOperationId`、change_apply status 动作的 `operationId`。
- C-2：结果里照旧返回之后要引用的编号：需求保存的操作编号（批准时作为 `savedOperationId`）、worker 写入的操作编号（status 查询用）、备份的操作编号（恢复时作为 `backupOperationId`）。连续两次调用得到两个不同的编号，是两次独立的操作。
- C-3：这 5 个工具的说明里没有要求模型生成或填写操作编号的话，不出现"新生成""UUIDv7"字样。
- C-4：续做由程序按内容认出。下面这些操作中断后，模型用原来的内容再调一次，程序发现这个目标上有一次没做完的同类操作、而且内容相同，就用原编号把它做完，结果和一次做完时相同：
  - 需求保存（create、updateDraft）；
  - 关闭需求（同一个原因和决定编号）；
  - 工作区准备（同一个需求）；
  - change_apply 的 apply、import（本运行里同一批文件）。
- C-4b：批准（confirmUpdate）的状态一次写完：要么完整生效，要么什么都不写，不会留下需要续做的半截批准。另一次保存还没做完时，批准被拒，报错建议先用原来的内容把那次保存续完，再重新批准。
- C-5：同一个目标上有一次没做完的操作、这次的内容又和它不同时，调用被拒，报错写明还有一次没完成的保存、关闭或写入，建议先用原来的内容再调一次把它续完。状态不变。
- C-6：备份、恢复不续做：中断后再调，就从头开始一次新的备份或恢复。
- C-7：编号由程序生成后不可能再发生的报错，从代码里删掉。至少包括"这个操作编号之前已失败过，不能再用"和"需求编号已被占用"。需求编号撞号时，程序自己换一个编号重来，模型看不到。
- C-8：在仓库根执行 `grep -rn '新生成' src | grep -v '重新生成'`，没有输出。
- C-9：除了编号由谁生成、续做由程序按内容认出、批准一次写完，需求的起草、提问、批准、派工、写入、关闭、工作区、备份恢复的行为都和改动前一样。改动前已有的纯代码测试，去掉自造编号后全部通过。

## 验收
- [ ] C-1：对 5 个工具的每个写入动作，不带编号各调用一次 → 都成功，程序生成的编号符合 UUIDv7 格式；带 `requestId` 或新操作的 `operationId` → 参数不合格被拒。
- [ ] C-2：同一个需求连续两次调用 updateDraft → 两次结果里的操作编号不同，版本号依次加一；create 结果里的操作编号能作为批准的 `savedOperationId`；apply 结果里的编号能用来查 status；backup 结果里的编号能用来 restore。
- [ ] C-3：5 个工具的说明文字里没有"新生成""UUIDv7"，也没有要模型填写操作编号的话。
- [ ] C-4：C-4 列出的每种操作各造一次中断，用原内容再调一次 → 原操作完成，结果里的操作编号就是原编号，结果和一次做完时相同。
- [ ] C-4b：在批准的写入过程中注入一次写入失败 → 调用被拒；需求记录、事件、批准使用记录、操作记录、写占用都和调用前一样；随后重新批准成功。另造一次没完成的 updateDraft，再批准 → 被拒，报错建议先用原内容续完那次保存。
- [ ] C-5：C-4 的需求保存、关闭、change_apply 各造一次没做完的操作，再用不同的内容调一次 → 都被拒，报错写明还有一次没完成的操作并建议用原内容续完，状态没有变化。
- [ ] C-6：备份中途失败后再调 backup → 从头开始一次新的备份并成功。
- [ ] C-7：代码里找不到"这个操作编号之前已失败过""需求编号已被占用"这两条报错；模拟需求编号撞号 → create 仍然成功。
- [ ] C-8：`grep -rn '新生成' src | grep -v '重新生成'` 没有输出。
- [ ] C-9：类型检查、单元、集成、安装四项纯代码测试全部通过；全部真实模型验收（P1–P13、M9-AC12、M9-AC2/AC3/AC11）通过，这些运行的主代理和 worker 会话记录里没有生成 UUID 的 Bash 命令。

## 验证路径
1. 执行 `grep -rn '新生成' src | grep -v '重新生成'` → 没有输出。
2. 跑 `pnpm run typecheck`、`pnpm test`、`pnpm run test:integration`、`pnpm run test:installation` → 全部通过。
3. 在样例项目里，让主代理建一份需求草稿并改一次 → 两次都成功，操作编号不同。
4. 制造一次需求保存中断，再用原内容调一次 → 保存完成，需求解锁。
5. 跑全部真实模型验收 → 全部通过；在会话记录里搜 `uuid` → 没有模型执行的生成编号命令。
