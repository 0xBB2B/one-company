# 新操作的编号改由程序生成

## 背景与问题
- 产品里有 5 个给模型用的工具，要求模型在调用时自己填一个"新生成的 UUIDv7"编号。UUIDv7 是一种开头带当前毫秒时间戳的唯一编号，程序会校验格式，随手编的通不过。这 5 个工具是：
  - 主代理的 `one_company_requirement_manage`：create 要填请求编号 `requestId` 和操作编号 `operationId`，updateDraft、confirmUpdate 要填 `operationId`。
  - 主代理的 `one_company_user_interact`：所有用途都要填 `operationId`。
  - 主代理的 `one_company_project_manage`：准备和回收工作区、备份、恢复、恢复检查都要填 `operationId`。
  - 主代理的 `one_company_workflow_manage`：关闭需求要填 `operationId`。
  - worker 的 `change_apply`：写入（apply）和导入（import）要填 `operationId`。
- 模型自己没有生成编号的办法，只好先用 Bash 跑一段 python3 现场算。本机会话记录里这条命令出现过 21 次，而且有好几种写法。代价有三个：
  - 每段对话多一次工具调用。
  - 依赖用户机器上装了 python3。
  - 模型拼错格式时调用会被拒，只能再试一次。
- 编号有两个作用：
  - 认出"同一次操作"。编号相同、内容不同时，程序拒绝。
  - 续做中断的操作。比如保存需求写到一半进程崩了，需求会被锁住，只有用原来的编号、带原来的内容再调一次，程序才会把那次保存做完。
- 续做时报错只说"用原来的操作编号重试"，不告诉模型原编号是多少，模型只能靠自己记住当初造的那个。

## 目标
- 模型调用这 5 个工具时，不需要自己生成任何编号。新操作的编号由程序在每次调用时生成。
- 中断的操作仍能续完：模型用原来的内容再调一次，程序按内容认出那次没做完的操作，用原编号把它做完。

## 非目标
- 不改引用已有东西的编号，例如 `requirementId`、`savedOperationId`、`backupOperationId`、`receiptId`、`decisionId`，以及 change_apply 的 status 动作要填的写入编号。这些本来就从工具结果里抄。
- 不新增"防止重复建需求、重复执行"的保护。
- 不改 `tests/integration/host-exit.test.ts` 里用 python3 模拟终端的测试。
- 不改程序内部早已自己生成编号的地方，例如运行编号、派工身份。

## 整体验证路径
1. 在仓库根执行 `grep -rn '新生成' src | grep -v '重新生成'` → 没有输出。
2. 不带编号调用 5 个工具的写入动作 → 都成功；带 `requestId` 或新操作的 `operationId` → 参数不合格。
3. 让一次需求保存中途中断，再用原内容调一次 → 保存完成，需求解锁。
4. 跑类型检查、单元、集成、安装四项纯代码测试 → 全部通过。
5. 跑全部真实模型验收（P1–P13、M9-AC12、M9-AC2/AC3/AC11）→ 全部通过；这些运行的主代理和 worker 会话记录里，没有生成 UUID 的 Bash 命令。

## 决策记录
- **质疑结论**：值得做。加一个"发编号"的工具、或让模型改用 node 生成，都还要多调一次工具，没解决根源。只有改成程序生成，才能去掉这一步。代价是改 5 个工具的参数、说明和测试，约半天；再加全部真实模型验收，约 1–2 小时。用户 2026-10-19 决定照做。
- **5 个工具全改**（用户 2026-10-19 决定）：worker 的 change_apply 一起改。被否决的是"只改主代理的 4 个工具"，这样 worker 仍要自己造编号。
- **续做由程序按内容认出，模型不填操作编号**（用户 2026-10-19 决定，真实模型验收时发现）：
  - 最初的做法是操作编号作为可选参数保留，平时不填，续做时照抄报错给出的原编号。真实模型验收 15 条里 6 条失败：模型照样自己编一个像 UUIDv7 的编号填进去，被拒后原样重试直到卡死；或者把上一次结果里的操作编号抄进下一次调用（验收输出里 P1 连续 6 次带同一个自编编号，P6 有 32 次"已经完成"的拒绝）。参数里只要有编号字段，模型就会去填，工具说明写"平时不填"也拦不住。
  - 决定：5 个工具都去掉让模型填的新操作编号参数。续做由程序按内容认出：同一目标上有一次没做完的同类操作、这次内容又相同，就用原编号续完；内容不同就拒绝并建议用原内容续完。工作区准备按需求自动续上。备份、恢复不续做，中断后从头再来：以前就允许从头来，中断留下的半截目录不影响新的备份。
  - 被否决的方案："把参数改名为 resumeOperationId"，模型会不会还去填要靠验收碰运气，只是缓解；"填错的编号直接忽略"，模型照样乱填，也违背"编号不对就拒绝"。
  - 被否决的更早方向："程序发现中断就自动撤销那次操作"，要改恢复机制本身，超出"谁来生成编号"这个问题。
- **放弃"带同一编号原样重试不会重复执行"**：现在模型如果带同一个编号再调一次，程序会认出是同一次操作，直接返回已有结果，不重复执行。改成程序生成后，模型每次调用都是一次新操作，这个保护没有了。接受的理由有两个：工具说明本来就要求每次新生成编号；主代理规矩 `rules/01-main-session.md` 也要求工具出错时不要原样重试。所以这个保护实际上用不到。
- **用不到的报错直接删**：编号由程序生成后，有些报错再也不会发生，就从代码里删掉，不留兼容分支。例如"这个操作编号之前已失败过，不能再用""需求编号已被占用"。需求编号撞号由程序自己换一个编号重来，模型看不到。还可能发生的冲突报错，改写成按新规则给出的下一步建议。
- **项目级规则写进 AGENTS.md**（用户 2026-10-19 决定）："工具不要求模型自己生成编号"对以后新加的工具同样适用，不随本需求消失，所以写进 AGENTS.md「产品设计原则」，不写在 PRD 里。
- **验收搜索命令排除"重新生成"**（用户 2026-10-19 决定，写实施计划时发现）：`src/modules/verification/change-apply.ts` 里"重新生成文件"这句提示和编号无关，但会被"新生成"搜到，所以搜索命令加上 `grep -v '重新生成'`。
- **批准一次写完，没有续做**（用户 2026-10-19 决定，执行时发现）：
  - 发现的问题：批准原来拆成好几次独立提交的数据库写入，中间失败会留下一条没做完的操作记录，把需求锁住。续做时程序会重新解读用户原话，生成新的决定编号和批准清单，和那条记录对不上，需求就永远解不开。这个问题改动前就存在。
  - 决定：用户指出决定编号由程序生成，应当像主键一样"写成功才存在"。批准先做完只读检查，再在一个数据库事务里写完批准状态；失败就什么都不写；批准不建操作记录，也不接受 operationId。事务内核对另一次保存是否没做完，没做完就拒绝，避免批准抢在半截保存前面、让那次保存永远卡住。
  - 代价：操作记录的格式变了，本机数据库版本号从 3 升到 4，旧版本留下的本机数据和备份打开时报错，用户要备份后删除本机数据目录。
  - 被否决的方案：
    - "续做时用本轮确认换掉没生效的旧凭据"：仍保留半截状态，只是缓解症状。
    - "在同一事务里建操作记录并直接标完成"：不用升版本号，但这条记录没有任何地方读，还要保留相关格式和代码。
