# 自动清掉残留的维护标记

本文说的"维护标记"，是备份、恢复、恢复对账开始时程序放在维护目录里的隐藏文件 `.database-maintenance.json`，里面记着留标记的进程的进程号和启动时间。"进程确认已不在"指：这个进程号已经没有进程；或者有进程，但启动时间和标记里记的不一样（进程号被系统分给了别的进程）。

## 用户故事
### P0：作为用户，我想要备份被强杀后仓库还能照常用，以便不用自己去找隐藏文件删

**用例（主路径）**
- 场景：用户让主代理备份本机数据，备份进行中，用户强行关掉了 pi 窗口。
- 操作：用户重新打开 pi，让主代理查看需求状态。
- 预期：主代理正常读到需求状态；数据目录里的 `.database-maintenance.json` 已被程序删掉；做了一半的备份目录还留在 `backups/` 下。

**用例（边界：维护还在进行）**
- 场景：一个 pi 窗口正在备份，用户在另一个窗口里让主代理查看需求状态。
- 操作：第二个窗口打开本机数据库。
- 预期：打开失败，报错说本机数据正在备份、恢复或对账，给出进程号，建议等它结束再试；标记原样保留，备份正常做完。

**用例（异常：判断不了）**
- 场景：受限环境里程序查不了进程，留标记的进程号上还有一个进程。
- 操作：打开本机数据库。
- 预期：打开失败，报错说判断不了留标记的进程还在不在，建议确认没有别的窗口在备份、恢复或对账后，删除标记文件，并写出它的完整路径；标记原样保留。

## 约束
- C-1：打开本机数据库时发现维护标记，且留标记的进程确认已不在 → 程序删掉标记，这次打开成功。
- C-2：留标记的进程确认还在（进程号和启动时间都对得上，包括本进程自己正在做的维护）→ 打开失败，标记不动；报错写明"本机数据正在备份、恢复或对账"、留标记的进程号、"等它结束再试"，不建议删文件。
- C-3：判断不了留标记的进程还在不在（查不了进程；或进程号上有进程，但核对不了启动时间）→ 打开失败，标记不动；报错写明"判断不了留标记的进程是否还在"，建议"确认没有别的窗口在备份、恢复或对账后，删除 <标记文件的完整路径>"。
- C-4：维护标记读不出（文件损坏、格式不对）→ 打开失败，标记不动；报错写明"维护标记读不出"，下一步建议与 C-3 相同，并写出标记文件的完整路径。
- C-5：数据目录里有一个留标记的进程已不在的残留标记时，主代理直接调 project-manage 的 backup 或 recovery-check → 都成功。
- C-6：两个进程同时打开同一个数据目录，都发现同一个可清的残留标记 → 两边都打开成功，不会因为对方先清掉而报错。
- C-7：清标记只删 `.database-maintenance.json` 这一个文件；数据目录里其他文件（包括 `backups/` 下做了一半的备份目录）原样保留。

## 验收
- [ ] C-1：放一个记着已退出进程的标记 → 打开数据库成功，标记文件不存在；放一个进程号存在但启动时间不同的标记 → 同样成功并删掉标记。
- [ ] C-2：本进程正在维护时，从同一进程的另一个连接打开数据库 → 失败，报错含"正在备份、恢复或对账"、本进程的进程号和"等它结束再试"，不含"删除"；标记仍在。
- [ ] C-3：模拟查不了进程且进程号上有进程 → 打开失败，报错含"判断不了"和标记文件的完整路径；标记仍在。
- [ ] C-4：标记文件内容不是合法标记 → 打开失败，报错含"维护标记读不出"和标记文件的完整路径；标记仍在。
- [ ] C-5：留下可清的残留标记后调 backup → 结果 completed；另起一次，调 recovery-check → 结果 restart_ready。
- [ ] C-6：留下可清的残留标记后，两个进程同时打开同一个数据库 → 都成功。
- [ ] C-7：留下可清的残留标记和一个做了一半的备份目录，打开数据库后 → 标记文件不存在，那个备份目录和里面的文件都还在。

## 验证路径
1. 在样例项目里备份一次，再手动放一个记着已退出进程的 `.database-maintenance.json` → 调 `one_company_project_manage` 的 status → 成功，标记已删。
2. 放一个内容乱写的 `.database-maintenance.json` → 调 status → 失败，报错写出标记文件的完整路径；按报错删掉它后再调 → 成功。
3. 调 backup → 成功。
