# 强杀后残留的维护标记由程序自动清掉

## 背景与问题
- 主代理调 `one_company_project_manage` 做备份（backup）、恢复对账（recovery-check）、恢复（restore）时，程序先在要维护的目录里放一个维护标记，正常结束再删掉。维护标记是一个隐藏文件 `.database-maintenance.json`，里面记着是哪个进程在维护（进程号和进程启动时间）。它存在时，别的地方打开这个目录里的本机数据库都会报错，防止维护期间有人写数据库。
- 备份和恢复对账的维护目录就是这个仓库当前的本机数据目录。如果做到一半时 pi 窗口被强行关掉、进程被杀，标记就留了下来。之后这个仓库所有要打开本机数据库的地方都失败，报"维护范围尚未确认结束"：守护进程、各个工具，连恢复对账自己也跑不起来，因为它进维护前要先读运行记录。
- 程序里没有任何办法从这个状态恢复。用户只能自己找到这个隐藏文件手动删掉，而报错里没写文件在哪、能不能删。
- 强杀不会让当前数据库处在写了一半的状态：
  - 备份只用只读方式读当前数据库，新文件只写在数据目录的 `backups/` 下面。
  - 恢复对账只核对，不写。
  - 恢复的写入都在单独的隔离目录 `restores/<编号>/` 里，当前数据目录不动。
- 所以留标记的进程一旦确认已经不在，清掉标记是安全的，不需要人来判断。

## 目标
- 留标记的进程确认已经不在时，下一次打开本机数据库，程序自动清掉残留标记并照常打开，用户不用做任何事。
- 程序判断不了、不能清时，报错写明原因和下一步怎么做。

## 非目标
- 不专门清理作废的恢复隔离目录和做了一半的备份目录。它们不挡任何操作，下次备份、恢复会用新编号、新目录。
- 不加界面：不弹窗确认，不在状态面板显示。
- 清掉标记后不写日志、不留记录。
- 不改维护期间拒绝其他连接打开数据库的规则：留标记的进程还在时照旧拒绝。
- 不改备份、恢复、恢复对账本身的流程。

## 整体验证路径
1. 在一个样例项目里开始备份，在备份进行中强行杀掉做备份的进程 → 数据目录里留下 `.database-maintenance.json`。
2. 重新打开 pi、调用任意要读本机数据库的工具 → 调用成功，`.database-maintenance.json` 已不存在。
3. 再调一次 backup → 备份成功。
4. 跑类型检查、单元、集成、安装四项纯代码测试 → 全部通过。
5. 跑真实模型验收（P1–P13、M9-AC12）→ 全部通过。

## 决策记录
- **质疑结论**：值得做。一旦发生，整个仓库都用不了，而且没有提示告诉用户该删哪个文件。最便宜的替代是只改报错文字，让用户手动删文件，但仍要用户去终端操作，只是缓解。用户 2026-10-19 决定照做。
- **程序自动清，不弹窗确认**（用户 2026-10-19 决定）：
  - 选它的原因：备份和恢复对账不写当前数据库，恢复只写隔离目录，所以强杀后当前数据目录没有写了一半的数据。弹窗问用户，用户也没有比程序更多的信息可以参考。
  - 被否决的"弹程序窗口让用户确认"：这是另一个窗口最初的建议，担心"恢复做到一半时数据目录处在中间状态"。核对代码后发现，这只适用于作废的隔离目录，不适用于当前数据目录。而且打开数据库的地方大多没有界面，要另加一个主代理调用的动作并先做界面预览，约半天到一天，换来的是一道没有判断价值的确认。
  - 被否决的"只改报错文字，让用户手动删"：仍要用户自己操作，没有解决问题。
- **在打开数据库时清，而不是守护进程启动时统一清一次**：工具会直接打开数据库，不一定先经过守护进程。只在守护进程启动时清，会漏掉这些地方。
- **清掉后不留痕迹**（用户 2026-10-19 决定）：打开数据库的地方很多，大多没有日志可写；做了一半的备份目录本身还留在 `backups/` 下。被否决的是"守护进程里清时写一行日志"，要把日志入口传进底层存储，只覆盖一部分情况。
- **清不了时报错写明原因和下一步**（用户 2026-10-19 决定）：符合 AGENTS.md"给模型看的错误只写原因和下一步"。被否决的是"报错照旧"。
- **查不了进程时按"可能还活着"处理**：受限环境里可能不允许查进程。这时程序判断不了，宁可报错让用户确认后手动删，也不冒险清掉一个可能还在用的标记。
