# 归档随需求关闭提交进分支

归档：需求以完成关闭时，程序写进需求 worktree 的 `docs/prd/<编号>.<需求描述>.md`（最终批准的需求正文和实现记录），以及批准过的原型 `docs/prd/<编号>.<原型名称>.html`。归档状态：程序记下的这次归档做到哪一步，有"已归档""待重试""受阻"三种，主代理用 `one_company_workflow_manage` 的 status 能看到，用 archive 动作能重试。

## 用户故事
### P0：作为不开远程交付、自己合并的用户，我想要需求关闭后归档已经提交在需求分支里，以便我怎么合并都会把归档一起带进主分支

**用例（主路径）**
- 场景：样例项目没有 origin。用户验收通过一个需求，主代理以完成关闭它。
- 操作：关闭完成后，在需求的 worktree 里运行 `git status --porcelain` 和 `git log -1 --format=%B`。
- 预期：`git status` 没有输出；最新提交的说明第一行是 `docs(prd): 归档需求 <编号>`，最后一行是 `Requirement: <编号>`；这个提交只新增了本需求的归档文件和原型文件。

**用例（异常）**
- 场景：用户机器上没配 Git 的用户名和邮箱，归档文件写好了，提交失败。
- 操作：主代理用 status 查看关闭状态。
- 预期：归档状态是"待重试"，原因里带 Git 给的报错；用户配好用户名和邮箱后，主代理用 archive 动作重试 → 归档状态变成"已归档"，需求分支上有归档提交，归档文件没有被重写。

**用例（边界）**
- 场景：归档提交已经完成，用户打开远程交付。
- 操作：主代理调用交付工具。
- 预期：推送前确认窗口写"归档已在分支中"，交付过程中没有新的归档提交。

## 约束
- C-1：需求以完成关闭、归档文件写好后，程序在需求分支上提交，只提交本需求的归档文件和原型文件，不碰 worktree 里的其他改动。提交说明第一行 `docs(prd): 归档需求 <编号>`，空一行，最后一行 `Requirement: <编号>`。
- C-2：归档状态只有在归档提交完成、而且需求分支最新提交里的归档文件和登记的内容一致后，才变成"已归档"。提交失败时状态是"待重试"，原因里带 Git 的报错；重试时文件已存在且内容一致就不重写，只补提交。
- C-3：需求分支上已经有内容一致的归档提交时，重试直接返回"已归档"，分支上的提交不变。
- C-4：交付工具（远程和仅本地两档）只核对归档已在需求分支里、内容和登记的一致，自己不提交任何文件；不一致时拒绝，原因写"归档文件与关闭时登记的内容不一致"。推送前或合并前的确认窗口写"归档已在分支中"。
- C-5：归档提交不算"最终检查之后的代码改动"：只多了归档提交时，交付不会因为"需求分支在最终检查后又有代码改动"被拒。

## 验收
- [ ] AC-1 ← C-1：完成关闭后，需求 worktree 的 `git status --porcelain` 为空；最新提交只新增本需求的归档和原型文件，说明第一行和最后一行如 C-1。worktree 里另有一个未提交的改动文件时，提交后它仍是未提交状态。
- [ ] AC-2 ← C-2：没配 Git 用户名时关闭需求，归档状态是"待重试"、原因里有 Git 的报错；配好后用 archive 动作重试，状态变成"已归档"，归档文件修改时间没变，分支上多一个归档提交。
- [ ] AC-3 ← C-3：对已归档的需求再调一次 archive，状态仍是"已归档"，分支上的提交数不变。
- [ ] AC-4 ← C-4：归档已提交后交付，确认窗口写"归档已在分支中"，交付过程中需求分支上没有新增说明为 `docs(prd): 归档需求 <编号>` 的提交；手动改动分支里的归档文件再交付，被拒绝，原因如 C-4。
- [ ] AC-5 ← C-5：最终检查通过后只多了归档提交，交付不报"需求分支在最终检查后又有代码改动"。

## 验证路径
1. 在没有 origin 的样例项目里做完并关闭一个需求 → worktree 干净，最新提交是归档提交，说明格式正确。
2. 去掉 Git 用户名后关闭另一个需求 → 归档"待重试"；配好后重试 → "已归档"，补上了提交。
3. 打开远程档位交付第一个需求 → 确认窗口写"归档已在分支中"，没有新的归档提交。
