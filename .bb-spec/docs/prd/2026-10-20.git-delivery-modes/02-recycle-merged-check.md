# 回收工作区按改动判断是否已合并

回收工作区：需求关闭后，主代理调用 `one_company_project_manage` 的 workspace-recycle，程序在用户确认后删掉这个需求的 worktree 目录和本地分支。主仓库当前分支：用户在主仓库目录里检出的那个分支，通常是 main。

## 用户故事
### P0：作为用压缩合并的用户，我想要 PR 合并、拉取到本地后能回收工作区，以便不用自己手动删 worktree 和分支

**用例（主路径）**
- 场景：需求分支在 GitHub 上被压缩合并，用户在主仓库执行了 `git pull`。
- 操作：主代理回收这个需求的工作区，用户在确认窗口选确认。
- 预期：worktree 目录和本地需求分支都删掉了，主仓库和其他分支不变。

**用例（边界）**
- 场景：同一个需求分别用普通合并、快进、改写提交号的 rebase 合并合进主仓库当前分支。
- 操作：回收工作区。
- 预期：三种情况都能回收。

**用例（异常）**
- 场景：PR 已在远端合并，但用户还没在主仓库拉取。
- 操作：回收工作区。
- 预期：回收被拦下，不弹确认窗口，什么都不删。原因写"需求分支还有改动没进主仓库当前分支 <分支名>"，并列出三种办法（见 C-3）。

**用例（异常）**
- 场景：压缩合并后，主分支上另一个提交又改了需求改过的同一行。
- 操作：回收工作区。
- 预期：被拦下，原因和办法同上；用户确认改动都已进去后，可以按第三种办法里的两条命令自己删除。

## 约束
- C-1：回收时，"需求已合并"的判断是：把需求分支再合进主仓库当前分支一次，合并结果和主仓库当前分支现在的内容完全相同，而且没有冲突。需求分支末端本来就在主仓库当前分支历史里时也满足这一条。判断只在本机做，不联网、不改任何文件。
- C-2：压缩合并、普通合并、快进、改写提交号的 rebase 合并之后都判为已合并；没合并、合并时有冲突、或者合并后主仓库当前分支又改了需求改过的同一处代码，都判为未合并。
- C-3：判为未合并时回收被拦下，原因写"需求分支还有改动没进主仓库当前分支 <分支名>"，下一步写三种办法：
  - 远端已经合并的，先在主仓库把目标分支拉到本地（例如 `git pull`）再回收；
  - 还没合并的，先交付或自己合并；
  - 合并后主分支又改了同一处代码、确认改动都已进去的，自己运行 `git worktree remove <worktree 路径>` 和 `git branch -D <分支名>`。
- C-4：本机 Git 版本低于 2.38 时回收被拦下，原因写"本机 Git 版本 <版本号> 低于 2.38，判断不了需求是否已合并"，下一步写"升级 Git 后再回收"。
- C-5：判断通过、用户确认后，程序强制删除本地需求分支，不会因为"分支没合进当前分支"被 Git 拒绝。回收的其他检查不变：需求已关闭收尾、归档已完成、没有未完成的写入、worktree 没有未提交或未跟踪的文件；确认窗口内容不变。

## 验收
- [ ] AC-1 ← C-1、C-2：在测试仓库里分别用压缩合并、普通合并、快进、改写提交号的 rebase 合并（逐个 cherry-pick）把需求分支合进主仓库当前分支，回收都成功，worktree 目录和本地分支都不存在了。
- [ ] AC-2 ← C-1：判断前后主仓库的 `git status --porcelain` 和各分支指向的提交都没变。
- [ ] AC-3 ← C-2、C-3：需求分支没合并时回收被拦，结果里的原因和三种办法如 C-3，命令里填的是实际的 worktree 路径和分支名；压缩合并后主分支又改了需求改过的同一行时同样被拦。
- [ ] AC-4 ← C-4：把检测到的 Git 版本换成 2.37.0 时，回收被拦，原因和下一步如 C-4。
- [ ] AC-5 ← C-5：压缩合并后回收成功，本地需求分支被删除；worktree 里有一个未跟踪文件时仍被拦下，原因是"存在未提交或未跟踪的文件"。

## 验证路径
1. 准备测试仓库，做一个需求并关闭，不合并就回收 → 被拦，看到原因和三种办法。
2. 在主仓库用 `git merge --squash` 合并并提交，再回收 → 成功。
3. 另做三个需求，分别用普通合并、快进、逐个 cherry-pick 合并，各回收一次 → 都成功。
4. 再做一个需求，压缩合并后在主分支改同一行，回收 → 被拦；按第三种办法手动删除。
