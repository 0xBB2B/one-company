# 远程交付

远程交付：Git 交付在"远程"档位时，主代理调用交付工具，程序核对后推送需求分支、建立或复用 PR（GitLab 叫 MR），再弹窗问用户怎么合并。目标分支：需求分支最终要合进去的分支，远程档位是 origin 的默认分支。Allow auto-merge：GitHub 仓库设置里的开关，默认关闭；开了以后 PR 可以设成"等仓库要求的审批和检查都通过后由 GitHub 自动合并"。

## 用户故事
### P0：作为用 GitHub 的用户，我想要交付时直接选压缩合并，以便主分支上一个需求一个提交，而且提交里带着需求编号

**用例（主路径）**
- 场景：仓库允许三种合并方式、开了 Allow auto-merge，合并方式三种都勾着，需求已完成并归档。
- 操作：主代理交付，用户在推送前确认窗口选确认；在"PR 已就绪，怎么合并？"窗口直接回车。
- 预期：光标默认在"压缩合并"上，回车即选它；仓库要求的检查通过后，主分支上多一个提交，标题"<需求标题> [<编号>] (#<PR 号>)"，正文是 PR 描述，最后一行 `Requirement: <编号>`。

**用例（边界）**
- 场景：仓库没开 Allow auto-merge，也没有要求的检查。
- 操作：同上。
- 预期：窗口里写"仓库没开自动合并，选了就现在合并"；回车后 PR 立刻被压缩合并。

**用例（异常）**
- 场景：仓库没开 Allow auto-merge，但要求 CI 检查通过，CI 还没跑完。
- 操作：选压缩合并。
- 预期：GitHub 拒绝合并；交付结果写明分支已推送、PR 已建好、合并没成功，原因是 GitHub 给的报错，建议"等检查通过后在网页上合并，或修好后重新交付"。

### P0：作为用私有部署 GitLab 的用户，我想要程序认出我的 GitLab，以便能开 MR

**用例（主路径）**
- 场景：origin 是 `git@code.example.com:acme/shop.git`，本机 glab 登录了 code.example.com，项目的压缩设置是"允许"。
- 操作：主代理交付。
- 预期：程序用 glab 建 MR；"MR 已就绪，怎么合并？"窗口里有"压缩合并"（推荐）和"不压缩（按项目设置）"。

**用例（异常）**
- 场景：origin 所在主机在 gh 和 glab 里都没登录。
- 操作：主代理交付。
- 预期：交付被拒，什么都没推送；原因"本机 gh 和 glab 都没登录 <主机>"，建议"登录后再交付，或在 /one:setting 把 Git 交付改成仅本地"。

## 约束
- C-1：认平台只看本机登录记录：origin 所在主机在 gh 里登录过就用 GitHub（gh），否则在 glab 里登录过就用 GitLab（glab）。两者都没有时拒绝，原因"本机 gh 和 glab 都没登录 <主机>"，建议"登录后再交付，或在 /one:setting 把 Git 交付改成仅本地"。没有 origin 时拒绝，原因"仓库没有名为 origin 的远端"，建议"配置 origin 后再交付，或在 /one:setting 把 Git 交付改成仅本地"。
- C-2：PR 标题是"<需求标题> [<编号>]"。PR 描述是下面几行，复用已有 PR 时也把描述换成这份：

  ```
  需求 <编号>
  交付提交 <推送的提交>
  最终检查代码 <最终检查时的提交>
  验收后已自动 rebase，这部分未重新验证。   ← 只在验收后目标分支前进、自动 rebase 过时出现

  Requirement: <编号>
  ```
- C-3：GitHub 的合并窗口标题"PR 已就绪，怎么合并？"，正文写需求标题和 PR 链接，再写一行等不等检查：仓库开了 Allow auto-merge 时写"仓库要求的检查通过后合并"，没开时写"仓库没开自动合并，选了就现在合并"。选项依次是：
  - "自己 review"（说明"PR 留着等你看，合并由你在网页上操作"）；
  - 在设置里勾了的合并方式，按压缩合并、普通合并、rebase 合并的顺序。没勾的不出现。勾了但仓库不允许的变暗，原因"仓库不允许<压缩合并、普通合并或 rebase 合并>"。查不到仓库设置时，这几项都变暗，原因"查不到仓库允许的合并方式：<原因>"。
- C-4：压缩合并带"推荐"，可选时光标默认停在它上面；它不可选时光标停在"自己 review"上。按 Esc 等于选"自己 review"。
- C-5：GitHub 合并只合并推送的那个提交。仓库开了 Allow auto-merge 时交给 GitHub 等检查通过后合并，没开时现在合并。压缩合并和普通合并时，程序指定提交标题"<需求标题> [<编号>] (#<PR 号>)"、正文是 C-2 的 PR 描述；rebase 合并不指定说明，保留各个提交原来的说明。
- C-6：GitLab 的合并窗口标题"MR 已就绪，怎么合并？"，正文写需求标题、MR 链接和"有流水线时等流水线通过后合并"。选项依次是：
  - "自己 review"（说明"MR 留着等你看，合并由你在网页上操作"）；
  - "压缩合并"：勾了压缩合并才出现，带"推荐"；项目的压缩设置是"不允许"（`never`）时变暗，原因"项目不允许压缩"；
  - "不压缩（按项目设置）"：勾了普通合并或 rebase 合并任一种才出现，说明"按项目设置的合并方式合并：普通合并、半线性或快进"；项目的压缩设置是"必须压缩"（`always`）时变暗，原因"项目要求压缩"；
  - 查不到项目的压缩设置时，后两项都变暗，原因"查不到项目的压缩设置：<原因>"。
  光标默认位置和 Esc 同 C-4。
- C-7：GitLab 合并只合并推送的那个提交，有流水线时等流水线通过，没有就现在合并。压缩合并时，程序指定压缩提交说明：第一行"<需求标题> [<编号>]"，空一行，接 C-2 的 MR 描述。
- C-8：合并没成功时（检查没过、规则集不放行、平台报错等），交付结果写明分支已推送、PR 或 MR 已建好、合并没成功，原因是平台给的报错，建议"处理后在网页上合并，或修好后重新交付"。
- C-9：其余交付步骤不变：核对完成凭据；验收后目标分支前进时能干净 rebase 才继续，有冲突就停下；推送前弹窗确认；不强推。

## 验收
- [ ] AC-1 ← C-1：origin 主机只在 gh 里登录 → 用 gh 建 PR；只在 glab 里登录 → 用 glab 建 MR，主机名里不含 github、gitlab 字样也一样；都没登录、没有 origin → 分别被拒，原因和建议如 C-1，远端没有新分支。
- [ ] AC-2 ← C-2：新建的 PR 标题和描述逐行如 C-2；验收后自动 rebase 过时多出那一行；对已有 PR 的分支再交付，PR 描述被换成新的一份。
- [ ] AC-3 ← C-3、C-4：仓库允许三种、三种都勾、开了 Allow auto-merge 时，窗口有"自己 review"和三种方式，写"仓库要求的检查通过后合并"，光标在"压缩合并"上；仓库不允许 rebase 时 rebase 合并变暗，原因"仓库不允许 rebase 合并"；设置里只勾普通合并时只出现"自己 review"和"普通合并"，光标在"自己 review"上；查不到仓库设置时方式全部变暗；没开 Allow auto-merge 时写"仓库没开自动合并，选了就现在合并"；按 Esc 的结果是自己 review。
- [ ] AC-4 ← C-5：选压缩合并或普通合并后，传给 gh 的标题和正文如 C-5，并且只允许合并推送的那个提交；开了 Allow auto-merge 时走等检查通过的自动合并，没开时直接合并；选 rebase 合并时不传标题和正文。
- [ ] AC-5 ← C-6：GitLab 项目压缩设置分别是 `never`、`always`、`default_on`、`default_off` 时，变暗的项如 C-6；只勾压缩合并时没有"不压缩（按项目设置）"；查不到设置时后两项变暗。
- [ ] AC-6 ← C-7：GitLab 选压缩合并时传给 glab 的压缩说明如 C-7，并且只允许合并推送的那个提交。
- [ ] AC-7 ← C-8：让 gh 合并报错时，交付结果写明 PR 已建好、合并没成功和平台的原因，建议如 C-8，交付工具本身没有报错退出。
- [ ] AC-8 ← C-9：验收后目标分支前进且有冲突时，交付停下，不推送。

## 验证路径
1. 用一个 GitHub 测试仓库（允许三种、开了 Allow auto-merge）交付一个需求，选压缩合并 → 检查通过后主分支上的提交标题和正文如 C-5。
2. 关掉 Allow auto-merge 再交付一个需求 → 窗口写"选了就现在合并"，合并立刻完成。
3. 关掉仓库的 rebase 合并 → rebase 合并一项变暗。
4. 用 glab 登录的私有部署 GitLab 项目交付 → 建 MR，选压缩合并后主分支上的提交说明如 C-7。
