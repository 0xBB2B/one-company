# 仅本地交付

仅本地交付：Git 交付在"仅本地"档位时，主代理调用交付工具，程序核对后弹窗问用户怎么合并，然后在本机把需求分支合进主仓库当前检出的分支，不推送。主仓库当前分支：用户在主仓库目录（不是需求 worktree）里检出的那个分支，通常是 main。

## 用户故事
### P0：作为没有远端仓库的用户，我想要需求做完后由程序替我合进 main，以便整个流程在本机就能走完

**用例（主路径）**
- 场景：样例项目没有 origin，主仓库当前分支是 main，没有未提交的改动；需求已完成并归档，合并方式三种都勾着。
- 操作：主代理交付；在"合进 main，怎么合并？"窗口直接回车。
- 预期：光标默认在"压缩合并"上；main 上多一个提交，标题"<需求标题> [<编号>]"，正文和远程的 PR 描述格式相同，最后一行 `Requirement: <编号>`；这个提交里有需求的代码改动和归档文件；需求分支和 worktree 保留。

**用例（边界）**
- 场景：验收后用户在 main 上又提交了一个不相关的改动。
- 操作：主代理交付。
- 预期：程序先把需求分支 rebase 到 main 最新提交上，窗口里写"目标分支在验收后前进，已自动 rebase，这部分未重新验证"；选 rebase 合并后，main 直接前进到需求分支末端，每个提交保留原来的说明。

**用例（异常）**
- 场景：用户在主仓库里改了一个文件还没提交。
- 操作：主代理交付。
- 预期：不弹窗，交付被拒；原因"主仓库有未提交的改动"，建议"请用户提交或暂存（stash）主仓库的改动后再交付"；main 和需求分支都没变。

**用例（异常）**
- 场景：用户在窗口里按 Esc。
- 操作：无。
- 预期：什么都不合并，交付结果写"用户选择先不合并，需求分支保留"。

## 约束
- C-1：仅本地档位下，PM 同步目标分支、最终检查、交付都对准主仓库当前检出的分支，不联网，即使仓库有 origin 也一样。远程档位仍对准 origin 的默认分支，没有 origin 时对准主仓库当前检出的分支。
- C-2：交付前先做和远程相同的核对（完成凭据、归档已在分支里、worktree 干净、最终检查后没有代码改动），再核对主仓库：
  - 主仓库没有检出任何分支时拒绝，原因"主仓库当前没有检出分支"，建议"请用户在主仓库检出要合进去的分支后再交付"；
  - 主仓库有未提交的改动（含已暂存的）时拒绝，原因"主仓库有未提交的改动"，建议"请用户提交或暂存（stash）主仓库的改动后再交付"。
  拒绝时 main 和需求分支都不变。
- C-3：主仓库当前分支在验收后前进了：能干净 rebase 就把需求分支 rebase 上去再继续，窗口里写"目标分支在验收后前进，已自动 rebase，这部分未重新验证"；有冲突就停下，不弹窗，原因"目标分支在验收后前进，自动 rebase 有冲突"，建议"请用户手动解决冲突，重新检查和验收后再交付"。没前进时窗口写"目标分支未变化"。
- C-4：合并窗口上方灰字"交付到本地分支"，标题"合进 <分支名>，怎么合并？"，正文写需求标题、编号、"分支：<需求分支> → <主仓库当前分支>（仅本地，不推送）"和 C-3 的那一行。选项只列设置里勾了的方式，顺序和说明是：
  - 压缩合并（带"推荐"）："<分支名> 上多一个提交；标题是"需求标题 [编号]"，正文末行 Requirement: <编号>"；
  - 普通合并："保留每个提交，另加一个合并提交"；
  - rebase 合并："保留每个提交，<分支名> 直接前进到需求分支末端"。
  勾了压缩合并时光标默认停在它上面，否则停在第一项。按 Esc 等于先不合并，提示行写"Esc 取消（取消就不合并，需求分支保留）"。
- C-5：三种方式合进主仓库当前分支的结果：
  - 压缩合并：多一个提交，包含需求分支相对目标分支的全部改动；标题"<需求标题> [<编号>]"，正文是下面几行：

    ```
    需求 <编号>
    交付提交 <需求分支末端的提交>
    最终检查代码 <最终检查时的提交>
    验收后已自动 rebase，这部分未重新验证。   ← 只在 C-3 自动 rebase 过时出现

    Requirement: <编号>
    ```
  - 普通合并：总是新建一个合并提交（能快进时也不快进），说明同压缩合并；
  - rebase 合并：主仓库当前分支直接前进到需求分支末端，不新建提交。
- C-6：交付结果写明用了哪种方式、合并后主仓库当前分支指向的提交。合并失败时（例如合并会覆盖主仓库里未跟踪的文件），主仓库当前分支不变，原因写 Git 给的报错，建议"处理后再交付"。需求分支和 worktree 都保留，回收工作区由用户另外决定。

## 验收
- [ ] AC-1 ← C-1：仅本地档位下、仓库有 origin 且 origin 的默认分支和本地 main 不同时，PM 同步后的需求分支包含本地 main 的最新提交，最终检查和交付都以本地 main 为准，过程中没有 `git fetch`；远程档位下仍对准 origin 的默认分支。
- [ ] AC-2 ← C-2：主仓库没检出分支、有未提交改动、有已暂存改动三种情况，交付都被拒，原因和建议如 C-2，main 和需求分支指向的提交都没变。
- [ ] AC-3 ← C-3：验收后 main 前进了不冲突的提交 → 窗口写"已自动 rebase"那一行；前进的提交改了同一行 → 交付停下，原因和建议如 C-3，不弹窗。
- [ ] AC-4 ← C-4：合并方式三种都勾时窗口有三项、光标在压缩合并上；只勾普通合并时只有一项；按 Esc 后什么都没合并，结果写"用户选择先不合并，需求分支保留"。
- [ ] AC-5 ← C-5：选压缩合并 → main 多一个提交，改动等于需求分支相对目标分支的全部改动（含归档文件），说明逐行如 C-5；选普通合并 → main 多一个有两个父提交的合并提交，说明同上；选 rebase 合并 → main 指向需求分支末端。
- [ ] AC-6 ← C-6：主仓库有一个未跟踪文件、和需求新增的文件同名时，合并失败，main 不变，结果里有 Git 的报错；合并成功后需求分支和 worktree 都还在。

## 验证路径
1. 在没有 origin 的样例项目里做完一个需求，交付选压缩合并 → main 上一个提交，说明格式正确，包含归档。
2. 再做一个需求，验收后在 main 上提交一个无关改动，交付选 rebase 合并 → 先自动 rebase，main 前进到需求分支末端。
3. 再做一个需求，在主仓库留一个未提交改动后交付 → 被拒；提交后再交付，选普通合并 → main 上多一个合并提交。
