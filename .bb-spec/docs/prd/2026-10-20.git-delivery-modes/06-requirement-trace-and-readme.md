# 从代码查需求的两个来源和 README

查找规矩：包内 `rules/05-archived-requirements.md` 是程序固定加进主代理提示词的一段规矩，告诉主代理怎么从代码查到对应的需求和归档。

## 用户故事
### P0：作为在主分支上看代码的用户，我想要不管当初怎么合并的，主代理都能告诉我这段代码属于哪个需求，以便读到当时的要求

**用例（主路径）**
- 场景：一个需求在 GitHub 网页上被手动压缩合并，合并的人把提交正文清空了，标题也改成了"fix login"。
- 操作：用户问主代理"登录页的验证码校验为什么这样写？"。
- 预期：主代理用 `git log` 找到改过这段代码的提交，提交说明里没有编号；它再看这个提交新增的文件，找到 `docs/prd/<编号>.登录页加上验证码登录.md`，读这份归档回答，并写明编号和出处。

**用例（边界）**
- 场景：需求是用普通合并或 rebase 合并进来的。
- 操作：同上。
- 预期：主代理从 PM 提交末尾的 `Requirement: <编号>` 拿到编号，读归档回答。

**用例（异常）**
- 场景：代码是在主窗口直接提交的，提交说明里没有编号，提交里也没有新增归档文件。
- 操作：同上。
- 预期：主代理照实说查不到对应需求，只读提交说明。

### P0：作为准备用 one-company 的用户，我想要安装前就知道仓库该怎么设置，以便网页上合并时需求编号也不会丢

**用例（主路径）**
- 场景：用户打开 README。
- 操作：读到「前置条件」。
- 预期：「前置条件」末尾有一个醒目的提示框，写明 GitHub 和 GitLab 各要改哪几项设置；「常见问题」里没有"PR 用哪种方式合并？"这一段。

## 约束
- C-1：`rules/05-archived-requirements.md` 里从代码查需求的规矩写成：
  - 先用 `git log --format='%h %s%n%b' -- <文件>` 列出改过它的提交；只关心某个函数时改用 `git log -L <起始行>,<结束行>:<文件>`。
  - 拿编号有两个来源，按顺序用：①提交说明里的 `Requirement: <编号>` 行或标题里的 `[<编号>]`；②都没有时，用 `git show --name-only --diff-filter=A <提交>` 看这个提交是否新增了 `docs/prd/<编号>.*` 文件，有就用这个编号。
  - 从需求编号查代码时，`git log --grep <编号>` 和 `git log --diff-filter=A --format='%h %s' -- 'docs/prd/<编号>.*'` 两条一起用：后一条找到的是带着归档进来的那个提交，压缩合并时它就是整个需求的提交。
  - 一个需求压成一个提交时，要知道某处改动是哪个任务做的，读归档里的实现记录。
  - 原有的其他内容保留：读归档时以代码为准；找不到归档时把编号告诉用户；两个来源都没有时照实说查不到对应需求，只读提交说明。
- C-2：README「前置条件」加一条"Git ≥ 2.38"，并在「前置条件」的列表后面、「安装」前面放一个 `> [!IMPORTANT]` 提示框，标题意思是"用远程交付前，先改好仓库的合并设置（需要管理员权限）"，内容：
  - GitHub：Settings → General → Pull Requests：勾选你要用的合并方式（Allow squash merging、Allow merge commits、Allow rebase merging）；Allow squash merging 的默认说明选 Default to pull request title and description；勾选 Allow auto-merge，选了合并方式后等检查通过再合并，不勾时选了就立即合并。主分支设了规则集（Settings → Rules → Rulesets）时，规则里允许的合并方式也要放行你勾的方式。
  - GitLab：Settings → Merge requests：要用压缩合并时，Squash commits when merging 不要选 Do not allow；Squash commit message template 填 `%{title}`、空一行、`%{description}`。
  - 一句话说明为什么：有人在网页上合并时用的是这些默认设置，设成别的，提交说明里的需求编号可能丢；丢了也能靠归档文件查回需求，但查起来慢一步。
- C-3：README 其他地方按新行为改写，不留旧说法：
  - 「上手」第 7 条写成：验收通过后需求关闭，代码和归档已提交在需求分支里；让主代理交付，远程档位推送并开 PR，仅本地档位直接合进主仓库当前分支，合并方式在窗口里选。
  - 「Git 交付」一节写两档的区别、没设置时怎么自动选、合并方式勾选、远程和仅本地的交付步骤、回收工作区怎么判断已合并。
  - 命令表里 `/one:setting` 的用途写成"……选 Git 交付档位和合并方式"。
  - 「常见问题」的"怎么查某个需求改了哪些代码？"按 C-1 写两个来源和两条命令；"PR 用哪种方式合并？"整段删除。
  - 全文搜不到"推荐用 rebase 合并""git-delivery 写 true 或 false""开启 Git 交付"这类旧说法；PM 同步目标分支时"能 rebase 就 rebase"的说明保留。

- [ ] AC-2 ← C-1：真实模型验收里，给主代理一个"提交说明没有编号、但提交新增了 `docs/prd/<编号>.*.md`"的样例项目，问某个函数为什么这样写 → 主代理的回答里带对这个编号，并引用了归档内容。

## 验证路径
1. 读改好的 `rules/05-archived-requirements.md` → 两个来源和两条命令都在。
2. 在样例项目里造一个"标题改掉、正文清空"的压缩提交，问主代理这段代码为什么这样写 → 回答里带对编号和归档内容。
3. 在 GitHub 上打开 README → 「前置条件」后面是醒目的提示框；按 C-3 的关键词搜索 → 没有旧说法。
