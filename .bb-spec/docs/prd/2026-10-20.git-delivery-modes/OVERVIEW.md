# Git 交付支持远程和仅本地、三种合并方式都能用

## 背景与问题
- one-company 靠"代码 → 提交 → 需求编号 → 归档"这条线回答"这段代码为什么这样写"。需求编号是每个需求的唯一编号；PM 每次提交，程序在提交说明末尾加一行 `Requirement: <编号>`。归档是需求以完成关闭时，程序写进需求分支 `docs/prd/` 下的文件：`<编号>.<需求描述>.md`（最终批准的需求正文和实现记录）和批准过的原型 `<编号>.<原型名称>.html`。主代理按 `rules/05-archived-requirements.md` 先用 `git log` 找到改过代码的提交，再从提交说明里读出编号，最后读归档。
- 这条线现在只在"每个提交原样进主分支"时可靠，很多团队用的压缩合并会把它弄断：
  - 压缩合并把 PR 里的提交合成一个新提交，标题和正文由平台设置或合并的人决定。GitHub 仓库把正文设成"只用 PR 描述"或"留空"时，PM 提交里的 `Requirement:` 行全部消失；现在 PR 描述里只有"需求 <编号>"，不是 `Requirement:` 格式。
  - 回收工作区（需求做完后删掉它的 worktree 目录和本地分支）要求需求分支的最后一个提交已经在主仓库当前分支的历史里。压缩合并后这永远不成立；GitHub 的 rebase 合并也会生成新提交号（GitHub 文档原话："Always updates the committer information and creates new commit SHAs"），同样被拦。
- 2026-10-13 用户决定"自动合并优先 rebase"（提交 a110ac0），理由正是 rebase 让每个提交原样进入主分支。这只照顾了一种合并方式。
- 没有 GitHub/GitLab 远端的纯本地仓库更不完整：
  - Git 交付工具要求有名为 origin 的 GitHub 或 GitLab 远端，否则直接拒绝；纯本地仓库用不了它。
  - 归档文件只写进需求的 worktree，不提交；只有交付工具会提交它。Git 交付默认关闭，所以默认情况下归档一直没提交：回收工作区会因为"存在未提交或未跟踪的文件"被拦下，用户自己合并时也容易漏掉归档，从代码就查不回需求。
  - 需求分支合进主分支这一步只能用户自己做，README 也没写怎么做。
- 私有部署的 GitHub/GitLab 地址里不一定带 github、gitlab 字样，现在按地址里的字样判断平台，认不出来。

## 目标
- GitHub、GitLab 上的压缩合并、普通合并、rebase 合并，以及纯本地仓库里的这三种合并，交付流程都能从头跑到尾：归档进分支、合并、回收工作区。
- 不管用哪种方式合并、合并时提交说明被怎么改，从代码都能查到需求编号和归档，从需求编号也能查到改动的代码。
- Git 交付分"远程"和"仅本地"两档；没人设置时按仓库自动选；合并方式在设置页勾选，压缩合并是推荐方式。

## 非目标
- 不改 PM 同步目标分支的做法：能 rebase 就 rebase，有冲突时把需求分支的改动合成一份重新应用。
- 不读 GitHub 规则集（Rulesets）里对合并方式的限制。规则集不放行时合并会失败，交付结果写明原因；README 提醒用户去改。
- GitHub、GitLab 之外的平台（如 Gitea）不开 PR，用仅本地档位。
- 回收工作区不联网：不拉取远端、不删远端分支。
- 合并后不自动回收工作区，也不在合并后再去核对主分支上那个提交的说明。
- 不迁移旧版本写的 `"git-delivery": true / false`；不处理升级前已关闭、归档还没提交的需求。

## 依赖与交付顺序
01 → 02 → 03 → {04、05 可并行} → 06。01 是其余各项的前提：归档在需求分支里，压缩后才和代码在同一个提交里，回收时工作区才是干净的。03 定下档位和合并方式后，04、05 才知道列哪些选项。

## 整体验证路径
1. 准备一个没有 origin 的样例项目。设置页「开关」里 Git 交付显示"仅本地"、来源"内置"，合并方式三种都勾着。
2. 让主代理做完一个小需求并验收通过 → 需求分支上多一个说明为 `docs(prd): 归档需求 <编号>` 的提交，worktree 里没有未提交的文件。
3. 让主代理交付 → 弹出"合进 main，怎么合并？"，光标在"压缩合并"上；回车 → main 上多一个提交，标题是"<需求标题> [<编号>]"，正文最后一行 `Requirement: <编号>`，同一个提交里新增了归档文件。
4. 让主代理回收工作区 → 确认后 worktree 目录和本地分支都删掉了。
5. 选需求改过的一个函数，按 `rules/05-archived-requirements.md` 的查法 → 查到编号并读到归档；`git log --grep <编号>` 列出第 3 步的提交。
6. 另做两个需求，分别选普通合并、rebase 合并，重复 3～5 → 都能合并、回收、查回需求。
7. 用一个 GitHub 测试仓库（gh 已登录）：Git 交付自动显示"远程"；交付后选压缩合并 → 主分支上的提交标题是"<需求标题> [<编号>] (#<PR 号>)"、正文最后一行 `Requirement: <编号>`；拉取后回收成功。再用网页手动压缩合并一个需求，把正文清空 → 按两个来源仍能从代码查回编号。
8. 跑类型检查、单元、集成、安装四项纯代码测试 → 全部通过；跑全部真实模型验收（P1–P13、M9-AC12，以及因为改了 `rules/*.md` 要加跑的 M9-AC2/AC3/AC11）→ 全部通过。

## 决策记录
- **质疑结论**：值得做。更便宜的替代是只让用户把仓库的压缩说明设成"PR 标题 + 描述"，但回收被拦和纯本地缺口都解决不了，而且每个项目都靠人设置、网页合并时还能被改掉。用户 2026-10-20 决定做。
- **推翻 2026-10-13 的"自动合并优先 rebase"**（提交 a110ac0，用户 2026-10-20 决定）：仓库允许的、用户勾选的合并方式都能用，压缩合并是推荐方式。对应关系不再靠"提交原样进主分支"，改为落在任何合并方式都改不掉的东西上：归档文件本身（01、06）和改动内容（02）。
- **撤回本次对话前半段的"只保留压缩合并"方案**（用户 2026-10-20 决定）：那个方案只是想办法把编号塞进压缩提交，只解决一种合并方式，纯本地也没覆盖。用户问能否兼容所有方式和纯本地后，换成现在的方案。
- **从代码查需求用两个来源**（用户 2026-10-20 决定）：先看提交说明里的编号，没有再看这个提交是否新增了 `docs/prd/<编号>.*`。不压缩的方式会保留每个提交的说明；压缩时归档和代码在同一个提交里。被否决的做法：用 git notes（附在提交上的额外说明）存需求编号——它默认不随推送和克隆同步，换台机器就没了。
- **已合并的判断改成"再合一次不带来任何改动"**（用户 2026-10-20 决定）：在临时仓库实测过，压缩、快进、普通合并、改写提交号的 rebase 合并都判为已合并，没合并、以及合并后主分支又改了同一行都判为未合并。后一种宁可拦下，由用户确认后手动删。依赖 Git 2.38 起才有的 `git merge-tree --write-tree`（Git 2.38.0 发布说明："git merge-tree" learned a new mode where it takes two commits and computes a tree）。
- **归档写完就立即提交**（用户 2026-10-20 决定）：不管 Git 交付在哪一档、用户之后怎么合并，分支上都已经是完整的一份。被否决的是"交付或回收时再提交"：用户在回收前自己合并的话，归档会漏掉。
- **Git 交付改成"远程 / 仅本地"两档，没有"关闭"**（用户 2026-10-20 决定）：没设置时，origin 所在主机在本机 gh 或 glab 里登录过就用远程，否则用仅本地。只看本机登录记录、不联网：实测 `glab auth status` 会请求 `https://gitlab.com/api/v4/user`，不能用；私有部署只能靠登录记录认出平台。这推翻了已合并 PRD 2026-10-16.unified-settings-page 里 Git 交付开关的约束：取值从 true / false 改成 remote / local，内置默认值从"关闭"改成按仓库自动选，交付工具两档下都一直在工具列表里。旧值不迁移（项目规矩：1.0 前不做向后兼容）。
- **仅本地档位下，同步、最终检查、合并都对准主仓库当前检出的分支**（用户 2026-10-20 决定）：检查过的就是最后合进去的。被否决的是"同步和检查仍用 origin 默认分支"：本地分支和 origin 不一致时，检查过的版本和合进去的版本对不上。
- **合并方式在设置页勾选，远程和本地都生效**（用户 2026-10-20 决定）：默认三种都勾；至少留一种。交付窗口里压缩合并排第一、标推荐、光标默认停在它上面（推荐方式，和 bb-spec 一致）。名字用"压缩合并、普通合并、rebase 合并"，比"合并提交""rebase 后快进"好懂（用户 2026-10-20 决定）。
- **交付窗口只列合并方式，等不等检查由程序决定**（用户 2026-10-20 决定）：GitHub 仓库开了 Allow auto-merge（GitHub 文档："merges a pull request automatically after all required reviews and status checks pass"，默认关闭）就等检查通过再合，没开就现在合；仓库要求的检查没过时 GitHub 会拒绝，交付结果写明原因。被否决的是"没开就把自动合并变暗"：没改设置的仓库只能去网页上合。
- **压缩提交的正文照 bb-spec 只写交付信息加 `Requirement:` 行**（用户 2026-10-20 决定）：各个提交的说明不进主分支，哪个任务做了什么看归档里的实现记录。被否决的是"再列出分支上每个提交的说明"：和实现记录重复，需求大时正文很长。复用已有 PR 时也把描述换成新正文（用户 2026-10-20 决定）。
- **GitLab 先查项目的压缩设置**（用户 2026-10-20 决定）：项目设置 `squash_option` 取值是 never、always、default_on、default_off（GitLab API 文档）。不允许压缩时压缩合并变暗，要求压缩时"不压缩"一项变暗，不会推送后才在合并那一步报错。
- **回收被拦时写原因和三种处理办法**（用户 2026-10-20 决定）：程序不强删，但用户不会卡住。
- **README 的仓库设置提醒放在「前置条件」末尾的提示框里**（用户 2026-10-20 决定）：用户安装前一定会读到，内容只写一处；常见问题里旧的"PR 用哪种方式合并？"整段删掉。
- **GitLab 选"不压缩"时也带上程序写的压缩说明**（用户 2026-10-20 决定，写实施计划时发现）：项目压缩设置是"默认压缩"（`default_on`）时，不带压缩参数合并，GitLab 可能仍按项目默认压缩并用模板生成说明（推测，本机没有 GitLab 账号未能验证），提交里就没有 `Requirement:` 行。带上说明后，万一被压缩，用的也是带编号的说明。实施时核实 glab 只传说明不会强制压缩，核实不了就把 `default_on` 当成"必须压缩"处理（"不压缩"一项变暗）。被否决的："直接当成必须压缩"会让只勾了普通合并的用户在这种项目里只能自己 review；"不特殊处理"会丢编号，只能靠归档文件查回。
- **登录有效性：默认档位看本机记录，交付前再真连一次**（用户 2026-10-20 决定，执行时发现）：审查发现 glab 第一次运行就会生成一个令牌为空的 gitlab.com 条目，按"有主机条目就算登录过"会误判，所以 glab 改为要求令牌有值。用户提出直接请求一次最简单的 API 判断是否有效；默认档位不这样做，因为档位决定 PM 同步和最终检查对准哪个分支，联网判断会让档位随网络变化，而且读设置很频繁、断网时每次都要等超时。真正需要确认连得上的时刻是推送前，所以远程交付在推送前用 `gh api user` / `glab api user` 真连一次，连不上就拒绝并写明原因。被否决的："默认档位也用 API 判断"，断网时档位会变，还要另定缓存规则。
- **回收被拦的原因句写出两个分支、目录被删后照样判断**（用户 2026-10-20 决定，执行时发现）：原因写"需求分支 <需求分支名> 还有改动没进主仓库当前分支 <主仓库分支名>"，避免读成主仓库检出的是需求分支。审查实测发现：worktree 目录被手动删掉并 prune 后，旧写法会跳过合并判断、用强制删除删掉没合并的分支，所以改为用本地分支末端照样判断。PRD 02 C-1 的"不改任何文件"改为"不改工作区和暂存区、不动任何分支"（`git merge-tree` 会在对象库里写临时对象）。
- **GitLab"默认压缩"按"必须压缩"处理**（执行时核实，按用户 2026-10-20 事先定的退路）：glab 源码 `internal/commands/mr/merge/mr_merge.go` 的 validate() 会拒绝"只给 --squash-message 不给 --squash"（报 `--squash-message can only be used with --squash`），所以"选不压缩时也带上程序写的说明"做不到。项目压缩设置是 `default_on` 时，"不压缩（按项目设置）"变暗，原因"项目默认压缩"，只给压缩合并。
- **项目是否受信任一律按仓库现查 trust.json**（用户 2026-10-20 决定，见 03 C-10）：交付工具、设置页、主窗口里的解释器和草稿核验器原来用 pi 会话启动时对会话所在目录的判断（`ctx.isProjectTrusted()`），守护进程按仓库现查 `ProjectTrustStore.get(仓库根)`。多仓库工作区里子仓库有单独的信任记录、或会话中途改了信任时，两边结论会相反：PM 同步和最终检查对准的目标分支，可能和交付合进去的不是同一个。改为交付工具、设置页、解释器和草稿核验器也按仓库现查，和守护进程用同一个口径。被否决的：交付工具改向守护进程要档位（要给主窗口和守护进程之间加接口，改动大）；不改（少见情况下检查和交付对不上）。
- **设置页底部说明：Git 交付缩短、合并方式补进 PRD、选择时照常显示**（用户 2026-10-20 决定，看过对比页后选定）：Git 交付这一行的底部原文 80 列下要占 3 行，缩短为"Git 交付：远程＝推送并开 PR；仅本地＝合进主仓库当前分支 · …"，细节留给修改第 1 步的选项说明；合并方式那一行实现里已有的底部说明保留并写进 03 C-2；修改的两步里底部照常显示这一行的说明，和「模型」分类一致。被否决的：选择时底部清空（和预览一致，但和「模型」分类不一致）；合并方式底部只写来源（少了"勾选对两档都生效"这条信息）；保持 3 行原文（偏长、和第 1 步选项说明重复）。
- **交付工具用守护进程给的主仓库根目录**（用户 2026-10-20 决定）：交付工具原来自己用 `git worktree list` 推算主仓库根，改为由守护进程组装交付信息时带上它登记的主仓库根目录，交付工具用它查信任、读项目层设置、做仅本地交付。这样交付和守护进程读设置、查信任用的是同一个仓库根。被否决的：交付工具换别的 git 命令推算（实测在 `--separate-git-dir` 布局下拿不到主工作区）。
- **`--separate-git-dir` 建的仓库记为已知限制**（用户 2026-10-20 决定，执行时实测）：这种布局下 `git worktree list` 的第一条是 Git 数据目录，守护进程启动时把它当主工作区，执行 `git rev-parse --show-toplevel` 报 "this operation must be run in a work tree" 后退出，整个 one-company 用不了，不只是交付。要支持它得改守护进程启动时的仓库身份核对，和安全有关、改动面大，没有在本需求里做，README「已知限制」写明。被否决的：本需求里顺带改守护进程的身份核对。
- **主窗口和守护进程的协议版本号升到 3**（用户 2026-10-20 决定，审查时发现）：本需求改了守护进程返回给主窗口的内容（归档提交、交付信息带主仓库根），升级包后旧守护进程还在跑时，新版交付工具拿不到主仓库根，会报看不懂的错误。升版本号让握手时直接拒绝旧守护进程，并把提示写成"后台进程是旧版本，和当前安装的 one-company 不一致：请关闭所有 pi 窗口后重新打开"。被否决的：不改（升级后窗口没关的那段时间里会出看不懂的错）。
- **在 worktree 里打开 pi 时，窗口侧也用主仓库目录**（用户 2026-10-20 决定，审查时发现、实测确认）：设置页、解释器和草稿核验器原来用窗口所在目录的 `git rev-parse --show-toplevel`，在 worktree 里拿到的是 worktree 目录；守护进程用的是主仓库目录。实测主仓库项目层写了"远程"（文件没提交、worktree 里没有）时，四种信任布局下设置页都显示"仅本地"、守护进程实际按"远程"走，其中两种布局下信任结论也相反。改为窗口侧和守护进程用同一个函数，取 `git worktree list` 里第一个非裸、非 prunable（目录已不存在）的工作区作为主仓库目录，查信任、读写项目层设定和项目层角色定义都用它（03 C-10）。被否决的：只在 README 记为已知限制（用户会被设置页误导）；本需求不管、以后另开需求；窗口向守护进程要仓库根（要给主窗口和守护进程之间加接口，改动大、结果相同）。
