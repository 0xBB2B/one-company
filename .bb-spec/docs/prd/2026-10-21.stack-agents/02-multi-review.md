# 一个任务多个审查

几个词先说清：
- 通用审查：内置的 reviewer 定义。每个 worker 任务都由它按现有的审查规矩审一遍（目标符合性、先红后绿记录、需求边界、依赖、原型、项目规范等）。
- 专项审查：名字是 `<栈>-reviewer` 的审查定义（内置的 6 个，或用户自己写的职责为 reviewer 的非通用定义），只按自己预设的 skill 审本次改动的编码规范、安全和鲁棒性。
- 一轮审查：worker 交出一次改动后，这次改动收到的全部审查（PM 整轮派的、单独重派的、临时加的）。第 1 轮之后，每次返修完再派审查算下一轮。
- 审查名单：任务里写的和自动挂上的专项审查，加上 PM 临时加的。
- 打回：审查结论是"阻塞"或"未验证"。

## 用户故事
### P0：作为用户，我想要一个同时改了 Go 和 Vue 的任务被几个角度同时审，以便每种技术栈的坑都有人查
**用例（主路径）**
- 场景：PM 规划 T3，执行定义是 go-worker，改动里还有 Vue 页面；go-reviewer、vue-reviewer 都开着。
- 操作：PM 在 T3 上挂 vue-reviewer，理由写"改了 web/ 下的 Vue 页面"；T3 写完后 PM 派审查。
- 预期：计划里 T3 的专项审查是 go-reviewer（同栈自动挂上）和 vue-reviewer；派审查时 reviewer、go-reviewer、vue-reviewer 三个同时启动；三个都通过后 T3 才算完成。

**用例（边界：一个打回）**
- 场景：第 1 轮 reviewer、vue-reviewer 通过，go-reviewer 打回，指出 `api/client.go:42` 用了没有超时的 `http.Get`。
- 操作：PM 派 worker 返修，返修完再派审查。
- 预期：worker 收到的返修意见注明来自 go-reviewer；第 2 轮只派 reviewer 和 go-reviewer，vue-reviewer 这一轮不派；两个都通过后 T3 完成。

**用例（边界：专项审查被关掉）**
- 场景：T3 自动挂了 go-reviewer，派审查前用户把它关了。
- 操作：PM 派审查。
- 预期：只派 reviewer 和 vue-reviewer；交给 PM 的审查结果里有一条「go-reviewer 已关闭，本轮未审」；任务能正常完成。

**用例（异常：两轮都有打回）**
- 场景：第 1 轮 go-reviewer 打回，返修后第 2 轮 reviewer 打回。
- 操作：第 2 轮结论全部交回。
- 预期：任务转为待用户裁决，状态面板上的待处理事项是「待裁决：任务 T3 两次未通过审查（go-reviewer、reviewer）」。

## 约束
- C-1：计划里每个 worker 任务可以写 0 个或多个专项审查，每个写定义名和一句理由。提交计划时这些情况被拒，并写明原因：理由为空；同一任务里重复写同一个定义；写了 reviewer（通用审查不用写）；写的定义不存在、职责不是 reviewer、或已关闭；非 worker 任务写了专项审查。
- C-2：worker 任务的执行定义名是 `<前缀>-worker`、而且存在名为 `<前缀>-reviewer` 的定义时，程序自动把 `<前缀>-reviewer` 加进这个任务的专项审查，PM 不用写理由；PM 自己也写了它时不重复。不论 `<前缀>-reviewer` 当时开着还是关着都挂上，关着的在派审查时按 C-4 跳过；自动挂上的不受 C-1"已关闭就拒绝"这条限制。PM 读计划时能看到哪些专项审查是自动挂上的，理由显示为「同栈自动挂上」。
- C-3：PM 有三种派审查的方式，每次都自己给轮数上限：
  - 整轮派：程序同时派出通用审查和本轮要审的全部专项审查，都用这次给的轮数上限。
  - 单独派：只派审查名单里的某一个，或通用审查。
  - 临时加：派一个名单外的专项审查，必须写理由；定义不存在、职责不是 reviewer、已关闭、或没写理由时被拒并写明原因。临时加的从此算进这个任务的审查名单，之后每一轮都和名单里的一样对待。
- C-4：第 1 轮要审的专项审查是任务里写的和自动挂上的全部专项审查。派的时候已关闭的不派，在本轮审查结果里记「<名字> 已关闭，本轮未审」；不存在了的（文件被删）同样不派，记「<名字> 已不存在，本轮未审」。专项审查全都没派时，本轮只有通用审查。
- C-5：专项审查只按自己预设的 skill 核对本次改动，不核对目标符合性、先红后绿记录、需求边界、依赖、原型这些通用审查的项目。本次改动不涉及它的技术栈时，结论为通过，摘要写「本次改动不涉及 <技术栈>，不适用」。
- C-6：专项审查的每条意见写明 `文件:行号`、在什么情况下会出事、按 skill 给出的修法。能写出这三样的列为阻塞；只能说"可能有风险"、写不出触发条件的只能列为建议。专项审查不修改任何文件。
- C-7：一个审查代理没交出结论（运行出错、轮数用满、被停止，或停下了没交）时，程序立刻把这一个的原因告诉 PM，不等同轮其他审查；PM 单独重派它，可以换轮数上限。别的审查已经打回时也照样重派。本轮名单里每个审查代理的最近结果都是通过、打回、被跳过，或本轮两次没交出结论时，这一轮才结束；还有在跑的或在等 PM 重派的，就没结束。结束时判定：
  - 通用审查通过，名单里每个都通过或被跳过 → 任务完成。
  - 有任何一个打回 → 任务进入待返修；交给 worker 的返修意见合并了本轮所有打回的意见，每条注明来自哪个审查代理。
  - 没有打回、但有审查代理本轮两次没交出结论 → 按 C-9 交用户裁决。
  通过和打回的结果在这一轮结束时合成一条交给 PM。
- C-8：返修完再派审查时，通用审查必派；专项审查只派上一轮打回的、没交出结论的、被作废的那几个，上一轮通过的这一轮不派。任务不是因为打回而返修、而是重新执行（例如计划改了以后重做）时，下一轮像第 1 轮一样派通用审查和全部专项审查。返修没做完、PM 让 worker 重试后完成的，也按重新执行算，下一轮全部重审。
- C-9：一个任务累计两轮有打回（不论是哪个审查代理打回的）时，任务转为待用户裁决，待处理事项写「待裁决：任务 <任务号> 两次未通过审查（<打回过的审查代理名，按第一次打回的先后排，不重复>）」。同一轮里同一个审查代理两次没交出结论时，不再重派它，等这一轮结束后转为待用户裁决，写「待裁决：任务 <任务号> 两次审查未完成（<名字>）」；进入新一轮重新计数。用户裁决"再给一次机会"后，这几个审查代理各再派一次、用用户给的轮数上限，这一次再没交出结论就再交用户裁决；放行的那次审查被作废后重派，仍用用户给的轮数上限。
- C-10：交给 PM 的每轮审查结果按审查代理分开列出：名字、结论、意见；被跳过的写跳过原因。
- C-11：PM 的规矩写明：规划每个 worker 任务时，看它的改动涉及哪几种技术栈，每种有开着的专项审查就挂上并写理由；和执行定义同栈的专项审查程序会自动挂，不用写。

## 验收
- [ ] AC-1 ← C-1：分别提交带以下问题的计划，各自被拒并写明原因：专项审查理由为空；同一任务写两次 vue-reviewer；写了 reviewer；写了 go-worker（职责不是 reviewer）；写了已关闭的 vue-reviewer；qa 任务写了专项审查。
- [ ] AC-2 ← C-2：执行定义是 go-worker、没写专项审查的任务，计划里它的专项审查是 go-reviewer、理由「同栈自动挂上」；go-reviewer 关着时计划照样提交成功、照样挂上；执行定义是 acme-worker、没有 acme-reviewer 时，专项审查为空；PM 自己写了 go-reviewer 时只出现一次。
- [ ] AC-3 ← C-3、C-4：挂了 go-reviewer、vue-reviewer 的任务整轮派审查（轮数上限 12）→ 同时启动 reviewer、go-reviewer、vue-reviewer 三个运行，轮数上限都是 12；派之前关掉 go-reviewer → 只启动 reviewer 和 vue-reviewer，本轮结果里有「go-reviewer 已关闭，本轮未审」；PM 单独派 vue-reviewer（轮数上限 20）→ 只启动 vue-reviewer，上限 20；PM 临时加名单外的 node-reviewer 并写理由 → 启动它，任务的审查名单里多了 node-reviewer 和 PM 写的理由，它也通过后任务才完成；临时加时不写理由、或加已关闭的、职责不是 reviewer 的定义 → 被拒并写明原因。
- [ ] AC-4 ← C-5、C-6：go-reviewer 审一个只改了 Vue 文件的任务，结论是通过，摘要含「本次改动不涉及」；它的阻塞意见都带 `文件:行号`、触发条件和修法；审查运行结束后工作区没有被它修改的文件。
- [ ] AC-5 ← C-7：三个审查里两个通过、一个打回 → 任务待返修，返修意见只含打回的那条并注明来源；三个都通过 → 任务完成；一个没交出结论、另两个还在跑 → PM 立刻收到这一个的原因；PM 单独重派它后它通过、另两个也通过 → 任务完成；它第 2 次又没交出结论 → 不再重派，另两个都结束后任务待用户裁决；另一个已经打回时，没交出结论的照样能单独重派，重派结果的意见也并进返修意见。
- [ ] AC-6 ← C-8：第 1 轮 go-reviewer 打回、vue-reviewer 通过，返修后派审查 → 只启动 reviewer 和 go-reviewer；第 1 轮 go-reviewer 打回、vue-reviewer 没交出结论、react-reviewer 通过，返修后派审查 → 启动 reviewer、go-reviewer、vue-reviewer；上一轮 vue-reviewer 被作废时，下一轮也派它；计划改了以后任务重新执行完，下一轮派 reviewer 和任务的全部专项审查；返修没做完、PM 让 worker 重试完成后，下一轮同样派 reviewer 和全部专项审查。
- [ ] AC-7 ← C-9：第 1 轮 go-reviewer 打回、第 2 轮 reviewer 打回 → 任务待用户裁决，事项是「待裁决：任务 T3 两次未通过审查（go-reviewer、reviewer）」；vue-reviewer 在同一轮里两次没交出结论 → 事项是「待裁决：任务 T3 两次审查未完成（vue-reviewer）」；用户选再给一次机会后，这一次又没交出结论 → 再次待用户裁决；用户给了 7 轮上限、放行的那次被作废，PM 带 30 轮重派 → 这次审查的上限是 7。
- [ ] AC-8 ← C-10：一轮里有一个通过、一个打回、一个被跳过时，PM 收到的结果分三段，各写名字和结论或跳过原因。
- [ ] AC-9 ← C-11：PM 的职责规矩里有"按任务涉及的技术栈挂专项审查并写理由、同栈的程序自动挂"这一条。

## 验证路径
1. 用 C-1 列的几种错误写法提交计划，逐个看拒绝原因（AC-1）；提交合法计划，读回任务的专项审查（AC-2）。
2. 让 worker 交出改动，派审查，看同时启动了哪些运行和它们的轮数上限（AC-3）；派之前关掉一个再试（AC-3、AC-8）。
3. 用只改 Vue 的任务让 go-reviewer 审，看结论和工作区（AC-4）。
4. 构造通过 / 打回 / 没交出结论的组合，看任务状态和下一轮派了谁（AC-5、AC-6）；构造两轮打回和两次没交出结论（AC-7）。
5. 读 PM 的职责规矩（AC-9）。
