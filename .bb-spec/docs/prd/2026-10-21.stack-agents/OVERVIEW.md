# 技术栈专项代理与多角度审查

## 背景与问题
- 现在只有一个通用 worker 和一个通用 reviewer。reviewer 的职责规矩只用一句话概括安全和鲁棒性（"安全性、与目标直接相关的鲁棒性"），审查时只能凭模型的通用印象找问题，常漏掉某个技术栈特有的坑，例如 Go 的 `http.DefaultClient` 没有超时、写 nil map 会 panic，Vue 用 `v-html` 渲染用户内容会造成 XSS。
- worker 也一样：写代码时没有按技术栈的编码规范和已知的坑来写，问题要等审查打回才修，或者根本没人发现。
- 程序已经支持角色定义预设 skill（定义里的 `skills: [...]`，派出时把 skill 全文拼进任务说明），也支持 PM 按描述挑专业定义，但包里没有任何专业定义，也没有给它们用的 skill。2026-10-13 的需求决定"内置正文全空，不内置专业定义"，当时的理由是正文全空后专业定义只剩描述不同，没有意义。
- 一个 worker 任务现在只能指定一个审查定义；要从多个角度审（比如同时改了 Go 后端和 Vue 前端），做不到。
- 角色定义没有开关：放进目录就一直能被 PM 选中，想暂时不用只能删文件。

## 目标
- 包里内置 6 对专项定义（Go、Node.js / TypeScript、Python、Java / Spring、Vue、React，每对一个专项 worker、一个专项审查），各自预设同一组 skill：本栈的编码规范、本栈的排查清单，以及几份通用的安全、服务类清单。
- 包里内置 19 份 skill，每份不超过 200 行，每个检查项都写明问题、怎么在代码里认出来、修法和出处链接。
- PM 规划时按任务涉及的技术栈选专项 worker，并给一个任务挂多个专项审查；用了某栈专项 worker 的任务，程序自动挂上同栈的专项审查。
- 一个 worker 任务的通用审查和全部专项审查同时派出、并行执行，全部通过任务才完成。
- 除 5 个通用定义外，每个角色定义都能在设置页里单独开关，默认开启。
- 状态面板上，并行的每个任务、每个审查代理各占一行，写出用的是哪个定义。
- 用 Go 和 Vue 各一个埋了坑的样例项目做真实模型验收，证明专项审查能把这些坑找出来。

## 非目标
- qa、explore、prototype 职责的专项定义（专项审查好用的话以后再推广，另起需求）。
- 上面 6 个之外的技术栈（Rust、C#、PHP、Kotlin、Swift、移动端、基础设施等）。
- 按文件后缀或项目结构自动识别技术栈、自动选专项 worker：由 PM 按描述挑选。
- "专项审查比通用审查好用"的对照实验：验收只证明专项审查能找出埋好的坑。
- 状态面板的高度上限：任务和审查多时面板会变高，本轮不限制。
- 「开关」栏里的 Git 交付和合并方式，以及设置页其他分类的行为。
- 团队自定的设计约定（如主键类型、错误码格式、代码分层、认证方案）：内置 skill 只放市面公认的写法和常见问题。团队的关键设计决定写进项目或用户级 AGENTS.md，PM 规划、worker 编写、审查核对都会读到；详细写法放进用户自己的 skill，用同名定义挂到 worker 和审查上。
- 在设置页里"只在本项目关掉某个内置定义"：按空格只存到定义文件所在的那一层，内置定义的开关存到用户层；只想在一个项目里关掉内置定义，要手改项目层设置文件。

## 依赖与交付顺序
1. 前置：`git-delivery-modes` 分支先合并进 main。它改的是同一个设置页文件和设置文件的解析（「开关」栏改成两档 Git 交付加合并方式，one-company 字段的允许键也在改），本分支等它合并后 rebase 到新的 main，再开始实施。
2. 01 → 02 → 03；04 和 01～03 可以同时做；Go、Vue 的真实模型验收要等 01、02、04 都完成后再跑。

## 整体验证路径
1. 在没有任何设置文件的环境里打开 /one:setting → 角色定义 › worker：列出 worker（状态「必须」）和 go-worker、java-worker、node-worker、python-worker、react-worker、vue-worker（状态都是绿色「开启」）；reviewer 分类同样列出 reviewer 和 6 个 *-reviewer。
2. 在 python-worker 上按空格 → 这一行变成灰色「关闭」，底部「已关闭 python-worker · 全局生效」；用户设置文件的 one-company 字段下出现 `"disabled-agents": ["python-worker"]`。再按一次空格 → 恢复「开启」，这一条从文件里删掉。
3. 批准一个同时改 Go 后端和 Vue 前端的需求 → PM 的计划里，Go 任务用 go-worker，挂 vue-reviewer 之类的专项审查并写了理由；Go 任务写完后，状态面板在这个任务下面同时列出 reviewer、go-reviewer 等审查代理，各自转圈。
4. 让 go-reviewer 打回一次 → worker 返修后，第 2 轮只派出 reviewer 和 go-reviewer，面板上上一轮已通过的审查灰色保留；全部通过后任务完成。
5. 跑 Go、Vue 两条新的真实模型验收 → 专项审查把样例项目里埋的每个坑都列为阻塞，并指出文件和行号。

## 决策记录
- **质疑结论**：不做的话，审查只能凭通用印象找问题，技术栈特有的坑常被漏掉；worker 也不按规范写。更便宜的替代是只在包里放 skill、不内置代理，让用户在设置页按 C 复制 reviewer 后自己填 skills。用户选择内置代理，开箱即用（用户 2026-10-21 决定）。
- **推翻 2026-10-13 的"不内置专业定义""内置正文全空"**（用户 2026-10-21 决定）：当时的理由是"正文全空后专业定义只剩描述不同，没有意义"。现在专项定义靠预设的 skill 拉开差别，正文也写明各自负责什么、专攻什么技术栈，前提已经变了。同一份需求否决过"给每种 worker 配一个审查定义"，理由是两份规范要靠人手同步；这次 worker 和 reviewer 共用同一组 skill，规范只有一处来源，那条理由碰不到。先从 worker 和审查做起，好用的话再推广到其他职责。
- **按技术栈拆分，不按前端 / 后端拆**（用户 2026-10-21 决定）：预设的 skill 会全文拼进任务说明。只分前端、后端两个时，后端代理要带十几份 skill，每次多带 5～8 万 token，大部分和这次改动无关；按技术栈拆，每个代理带 6～9 份。
- **首批 6 个技术栈**（用户 2026-10-21 从选项里选定）：后端 Go、Node.js / TypeScript、Python、Java / Spring；前端 Vue、React。服务类 skill 选了关系数据库、Redis、消息队列、服务调用与运行时，只给后端代理带；Web/API 安全、认证与会话、依赖供应链三份所有代理都带。
- **同栈 worker 和 reviewer 共用同一组 skill**（用户 2026-10-21 决定）：写和审用同一份标准，不会互相打架，也不用写两份。代价：后端 worker 一次带 9 份 skill，估计每个任务多带约 4.5 万 token（推测，没有实测）。
- **TypeScript 编码规范单独一份，Node、Vue、React 共用**（用户 2026-10-21 决定）：同一套 TS 写法只写一处。
- **通用审查每个任务必审，专项审查只审专长**（用户 2026-10-21 决定）：通用审查的那些核对（目标、先红后绿、需求边界、依赖、原型）一个任务只需要查一遍，多个代理重复查既浪费，结论还可能打架。专项审查只按自己的 skill 核对本次改动的编码规范、安全和鲁棒性。
- **同轮审查并行，全部通过才完成；返修后通用审查必重审，专项只重派上次打回的；按任务累计两轮打回交用户裁决**（用户 2026-10-21 决定）：审查都是只读的，并行最快；已通过的角度不重复花钱，返修改坏别处的情况靠每轮必审的通用审查兜住；保留现在"两次打回就交用户"的封顶。
- **能指到代码行的就阻塞**（用户 2026-10-21 决定）：专项审查的问题只要能指出本次改动里的 `文件:行号` 并写出什么情况下会出事，就列为阻塞；说不出触发条件的只能算建议。被否决的做法是"只有安全问题阻塞、鲁棒问题一律建议"，那样超时、泄漏、重复消费这类问题会被带进代码。
- **审查只写修法，由 worker 返修**（用户 2026-10-21 决定）：审查代理不改文件，保持写和审分开；修法写进审查意见。
- **skill 每项写问题、怎么认出、修法、出处**（用户 2026-10-21 决定）：审查代理缺的是"在代码里长什么样"和"怎么改"，出处用来确认这一条不是编的。被否决的做法是去掉出处、多塞检查项，那样以后没法核对某一条对不对、有没有过时。
- **skill 和项目 AGENTS.md 冲突时按 AGENTS.md**（用户 2026-10-21 决定）：项目规范是这个项目的人自己定的，skill 只是通用的默认写法。
- **用了专项 worker 的任务，由程序自动挂同栈的专项审查**（用户 2026-10-21 决定）：靠提示词让 PM 记得挂，总有漏掉的时候；由程序保证才稳。配对规则按名字前缀：`<前缀>-worker` 自动挂 `<前缀>-reviewer`，用户自己写的同样成对命名的定义也按这个规则配对（这条配对规则是 /prd 阶段提出的，用户审阅 PRD 时确认）。
- **PM 给一个任务挂专项审查不设上限，每个写一句理由**（用户 2026-10-21 决定）：要挂几个，取决于任务碰了几种技术栈；硬限数量会漏审，要求写理由能防止乱挂。
- **开关放在角色定义列表里，每个定义各管各的，默认开启**（用户 2026-10-21 决定）：前面几轮定过"开关放在「开关」栏、按技术栈一个开关管一对、默认关闭"，用户看过预览后改成这样。除 5 个通用定义（worker、reviewer、qa、explore、prototype）外，内置专项定义和用户自己写的定义（包括同名替换了内置定义的）都能单独开关。接受的代价：
  - 开着 go-worker、关了 go-reviewer 时，自动挂审查会落空，这一轮的 Go 编码规范没人查。
  - 默认全开后 PM 每次规划都能看到 12 个专项定义，大多数任务会用上专项 worker 和专项审查，估计每个任务多带约 4～8 万 token（推测，没有实测）。
- **按空格直接切换，不弹确认；存到定义文件所在的那一层；只存关闭的**（用户 2026-10-21 决定）：开关跟着定义走，定义对哪些项目生效，开关就对哪些项目生效。内置定义和用户层定义存到用户层（全局生效），项目层定义存到项目层（本项目生效），底部提醒是全局生效还是本项目生效。切回开启就是回到默认值，删掉那条记录。
- **审查被关掉就跳过并记下来；worker 被关掉就拦下来让 PM 改计划**（用户 2026-10-21 决定）：关掉是用户明确的选择，审查可以少一个角度继续走；写代码这一步跳不过去，沿用现在"指定的定义不可用就报错、不悄悄换"的规则，用户点名的定义被关时 PM 先问用户。
- **窄终端放不下状态列时，先去掉「思考」列**（用户 2026-10-21 决定）：2026-10-16 的设置页需求要求窄到 36 列也能用，加上状态列后 36 列放不下全部列。思考等级最不常看，展开详情还能看到。
- **状态面板并列显示，任务直接列在需求下面**（用户 2026-10-21 看过预览后决定）：多个 worker、多个审查本来就是并行执行的，只显示第一个再加"等 N 个"看不出全貌。不加"N 个任务并行"这样的汇总行。
- **团队自定的设计约定不内置**（用户 2026-10-21 决定）：技术选择由 PM 在规划时做，PM 用的是写死的定义、不能挂 skill；项目规范 AGENTS.md 已经同时进入 PM 规划、worker 编写和审查核对，但有 16 KB 上限。所以关键设计决定写进 AGENTS.md，几百行的详细写法放用户自己的 skill、挂到 worker 和审查上。被否决的做法：给 PM 新增挂 skill 的机制（PM 只需要知道结论，用不着几百行细节）；把某个团队的设计偏好内置（别的团队的项目会被强加这套偏好）。
- **Vue 验收不把"token 存 localStorage"当坑，换成"路由守卫当权限校验"**（用户 2026-10-21 决定）：用户自己的认证规范要求 Web 端 token 存 localStorage，P16 把它当成必须打回的坑，和用户的规范相反。换成的坑对应 vue-pitfalls 已有的主题"路由守卫只当 UX，权限必须后端校验"。auth-session 里"token 存 localStorage 会被 XSS 读走"这个主题保留：它是市面上的通用知识，和用户项目规范冲突时按项目 AGENTS.md 优先解决。
- **真实模型验收只挑 Go 和 Vue**（用户 2026-10-21 决定）：要证明的是"预设 skill 让审查更准"这个机制，一个后端、一个前端就够；6 个栈都跑，验收条数翻 3 倍，每次改提示词都要重跑。其余 4 个栈和全部 skill 只做纯代码检查。
