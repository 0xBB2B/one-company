# 项目层当场授信、通用定义置顶

授信记录：pi 在 `~/.pi/agent/trust.json` 里给每个项目记的信任决定，有三种情况：信任、不信任、空（从没选过）。用户在 pi 启动时的授信弹窗里选，或者输入 pi 自带的 `/trust` 命令选。项目层的角色定义和设定只在记录为"信任"时生效。

通用定义：内置的 worker、reviewer、qa、explore、prototype 这 5 个角色定义。找不到对口的专项定义时就用它们干活，流程离不开，不能关闭。

## 背景与问题
- 新项目在设置页里永远存不到项目层。pi 只有在项目的 `.pi/` 下已经有 settings.json、mcp.json、skills 这类文件时，才会在启动时弹窗问用户信不信任。新项目没有这些文件，pi 不弹窗，授信记录一直是空的。OneCompany 把"空"当成不信任，设置页把项目层灰掉；项目层灰掉，就写不出 `.pi/settings.json`，pi 也就永远不会弹窗。实测：全新项目的授信记录为空，pi 认为它受信任，OneCompany 认为它不受信任。
- `/one:setting` 里复制角色定义到项目层、`/one:examples` 复制样例到项目层，也因为同样的原因被灰掉。只带 `.pi/agents` 的项目也一样卡住，因为 pi 不把 `.pi/agents` 算作要授信的文件。
- 角色定义列表现在把内置定义排在最后。worker 分区里 `worker` 排在 `go-worker`、`vue-worker` 这些专项定义后面，看不出哪个是兜底用的通用定义。

## 目标
- 授信记录为空时，用户能在设置页和 `/one:examples` 里直接选项目层；选了就把本项目设为受信任，再保存或复制，不用离开页面。
- 用户在 pi 里选过不信任的项目，项目层照样不能选，并说明怎么改。
- 每个角色分区的第一行都是通用定义，和其他定义之间用一条分隔线隔开。

## 非目标
- 改"项目层什么时候生效"的规则：仍然只有授信记录是"信任"时项目层才生效。不照抄 pi"没有要授信的文件就算信任"的规则。
- 改 pi 自己的授信弹窗和 `/trust` 命令。
- 在设置页以外的地方加"信任这个项目"的入口。
- 把内置的专项定义也排到分隔线上面。

## 整体验证路径
1. 准备一个从没设过授信的新项目，`trust.json` 里没有它，`.pi/` 也不存在 → 打开 `/one:setting`，第一行下面是黄字"! 项目还没设为受信任：项目层的定义和设定都没有生效"。
2. 在「模型」里把 PM 改成某个模型和思考等级，第 3 步选项目层 → 提示末尾是"· 已把本项目设为受信任"；`trust.json` 里这个项目记为 true；`.pi/settings.json` 的 one-company 字段下有 pm；黄字消失。
3. 换一个在 `trust.json` 里记为 false 的项目 → 打开 `/one:setting` 改 PM，第 3 步项目层是灰的，写"你在 pi 里选过不信任这个项目"；`trust.json` 不变。
4. 在第 1 步那样的新项目里输入 `/one:examples`，选一套样例、选项目层、确认复制 → 文件复制进项目，`trust.json` 里这个项目记为 true。
5. 打开 `/one:setting` 的 worker 分区 → 第一行是 worker，下面是一条灰色分隔线，线下是其他 worker 定义；qa 分区只有 qa 一行，没有分隔线。

## 决策记录
- **质疑结论**：不改的话，新项目的项目层设定、项目层定义、项目层样例都用不了，用户只能先知道 pi 有 `/trust` 命令、手动授信一次。值得改（用户 2026-10-26 决定）。
- **根因**：OneCompany 判断信任只认"记录为信任"，pi 的判断是"没有要授信的文件，或者记录为信任"，而且 pi 只在有要授信的文件时才弹窗。记录为空又没有这些文件的项目，没有任何地方会问用户。
- **选"当场问"，不照抄 pi 的规则，也不只改提示文字**（用户 2026-10-26 从三个方案里选定）：
  - 照抄 pi 的规则，被否决。从别人那里 clone 来、只带 `.pi/agents` 的仓库也会被当成受信任，里面的角色定义会在用户不知情时生效，违背"项目层定义要授信才生效"的设计。而且第一次存到项目层就会生成 `.pi/settings.json`，按 pi 的规则会立刻变成不信任，还得另外补写授信记录。
  - 只改提示文字、教用户去用 `/trust`，被否决。这只是治症状，用户还得离开页面自己去操作。
  - 当场问：在用户卡住的那一步把项目层放开，并写明"选它会把本项目设为受信任"。用户选项目层这个动作就是明确授信，不会默认放行陌生仓库。代价有三点：程序要写 pi 自己的 `trust.json`；设为信任后，项目里已有的 `.pi/agents` 和 `.pi/settings.json` 也会一起生效；界面要改。
- **写入的信任和 `/trust` 选 Trust 效果一样**：记在主仓库根目录这一项上。这次写入来自用户在页面上的选择，不是旧记录，符合"旧流程与旧记录不产生授权"。
- **`/one:examples` 一起改**（用户 2026-10-26 决定）：它也是"未受信任就灰掉项目层"，新项目里同样卡住。
- **置顶的只有通用定义**（用户 2026-10-26 决定）：用户说的"默认的角色定义，作为兜底角色"，指流程找不到对口专项定义时用的那一个，也就是和分区同名的通用定义。被否决的读法是把所有内置定义（含 go-worker 这类专项定义）都排在线上。按名字认通用定义，用户层或项目层覆盖了它时也照样置顶。
- **界面按确认过的预览实现**（用户 2026-10-26 确认）。
