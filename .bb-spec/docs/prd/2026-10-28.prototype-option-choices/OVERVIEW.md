# 确认原型窗口按设计师的方案清单列选项

## 背景与问题
- 原型：一份单个 HTML 文件的界面设计，由原型设计师（只负责出原型的子代理）交稿。交稿后程序打开浏览器，并弹出"确认原型"窗口，用户在窗口里决定这一版的去留。
- 设计师经常在一份原型里画出 A、B、C 几种方案让用户挑。现在窗口里的选项写死为"通过（写进需求草稿）""通过并补充说明（自己输入）""其他（自己输入）"，用户要选 B，只能选"通过并补充说明"再手打"用 B 方案，A 和 C 不要"。
- 窗口不知道原型里有几个方案、各叫什么，因为设计师交稿时只交 HTML 和一句说明。
- "补充说明"（用户通过时写的一段话，和那一版原型存在一起交给下游）当初就是为了写"用 B"才加的。方案能直接选之后，剩下的补充内容要么是改界面，应该让设计师改原型；要么是改需求，应该写进需求正文，由用户在批准窗口确认。再留一条"补充说明"的路，下游要同时看原型、正文和说明三处，容易对不上。
- 顺带盘点了所有程序窗口，结论是只有确认原型窗口需要改：
  - 主代理向用户提问的窗口，选项已经由主代理按问题写；
  - 面板事项里要登记决定的窗口（重试、拆分、验收、调整需求），选项文字由程序固定，模型只写理由和推荐，因为选中哪项就登记哪个决定；
  - 批准需求、登记裁决、交付、选合并方式、移除原型、设置页这些窗口由程序直接弹出，没有模型参与，每个选项对应一个固定的程序动作。

## 目标
- 设计师在一份原型里画了多个方案时，交稿附一份方案清单；确认窗口按清单列出"方案 A：<名称>""方案 B：<名称>"……和"其他（自己输入）"，用户选中一个方案就是通过这一版并选定这个方案。
- 用户选定的方案和那一版原型存在一起，出现在批准需求窗口里，并交给 PM 和它派出的 worker、reviewer、qa，写明其余方案不做。
- 主代理在下一轮开始时看到用户选了哪个方案，能据此改需求正文。
- 确认窗口里不再有"通过并补充说明"；想补充的话写在"其他"里，交给主代理处理。
- 用户在"其他"里写的话，主代理先弄清意图（提问、改原型还是改需求正文），拿不准就先问；要重出原型时，先说明修改要点，用户明确同意后才重派设计师。

## 非目标
- 改其他程序窗口的选项，或让模型给其他程序窗口出选项。
- 一次选定多个方案（例如"A 的顶栏加 B 的侧栏"）：写在"其他"里，由主代理重派设计师出一版合并后的原型。
- 方案清单里给每个方案写说明文字：清单只有名称，方案长什么样在浏览器里看。
- 需求完成归档时把选定的方案写进归档文件。
- 给已经通过的原型改选方案：想改就让设计师再出一版，重新选。
- 升级前留下的本机数据继续能用。

## 依赖与交付顺序
01 → 02。

## 整体验证路径
1. 主代理派原型设计师出"设置页"，设计师画了三种布局，交稿时附方案清单"顶部分栏、左侧导航、卡片网格" → 浏览器打开，弹出"确认原型"窗口，选项依次是"方案 A：顶部分栏""方案 B：左侧导航""方案 C：卡片网格""其他（自己输入）"，底部提示是"↑↓ 选择 · 回车确认 · Esc 放弃这一版"。
2. 先在"其他"写"B 的侧栏是不是太宽了" → 主代理没有直接重派设计师，先问你是在提问还是要改；你说"只是问问"后它回答，再重开确认窗口。
3. 选"方案 B：左侧导航"回车 → 对话里出现绿字"已登记：原型「设置页」第 1 版通过，已写进需求草稿。你选了方案 B：左侧导航。"，主代理没有马上回复。
4. 对主代理说一句话 → 主代理这一轮看到"用户通过了原型「设置页」第 1 版，选了方案 B：左侧导航，其余方案不做。"
5. 再派一份"命令行输出"，设计师只画了一种，不附清单 → 确认窗口的选项是"通过（写进需求草稿）""其他（自己输入）"；选"通过"。
6. 说"批准" → "批准需求"窗口里"设置页 第 1 版 本次新确认"下面有一行"你选的方案：B「左侧导航」，其余方案不做"，"命令行输出"下面没有附加行 → 确认。
7. PM 接手 → PM 收到的原型清单写着"- 设置页 第 1 版（用户选的方案：B「左侧导航」，其余方案不做）"；它派出的 worker 收到的原型清单里，"设置页"那一行下面写着"用户选的方案：B「左侧导航」，其余方案不做"。

## 决策记录
- **质疑结论**：问题真实存在。设计师给多个方案时，用户要手打"用 B"，打错字母或名称时下游照错的做。被否决的替代做法：保持"通过并补充说明"，只在设计师的说明里列出方案名让用户照着打。这仍要用户手打，程序也认不出用户选了哪个。
- **方案清单由设计师交稿时附上**（用户 2026-10-28 确认）：只有设计师知道自己画了几个方案。被否决的做法：主代理派设计师时指定方案数（主代理不知道设计师最后画了几个）；程序读 HTML 猜方案（不可靠）。
- **有方案清单时只列各个方案和"其他"，去掉整版"通过"**（用户 2026-10-28 决定）：原型里有多个方案时整版通过，下游不知道该照哪个做。
- **"通过并补充说明"在所有情况下都去掉，补充说明整个功能删掉**（用户 2026-10-28 决定）：用户的原话是"通过并补充说明这个我觉得可以不要了，全部放到其他（自己输入）里"。"其他"仍然不算通过：写的话交给主代理，是提问就回答，要改原型就重派设计师，要改需求就写进正文。正文会在批准窗口里由用户确认。被否决的做法：用户在"其他"里对这一版写过话、之后又通过它时，把最后一句自动当作说明存下（那句话可能只是一个提问，也会被当成说明交给下游）。代价：设计师画了多个方案却没交清单时，用户没法在通过的同时写明"用 B"，要先在"其他"里说，让主代理重派设计师补交清单。设计师的职责规矩因此加一条"画了多个方案就必须交清单"。
- **清单 2 到 6 个方案，每个名称最多 20 字**（用户 2026-10-28 决定）：程序窗口把选项名排成一列，"方案 A："加 20 个汉字共 47 列，加上 3 列缩进，在 80 列终端里不折行。只有 1 个方案等于没有选择。被否决的做法：最多 4 个、每个 12 字（设计师画 5 个方案时交不了稿）。
- **选定方案后记下的话带"其余方案不做"**（用户 2026-10-28 决定）：下游拿到的原型里画着全部方案，不写明的话可能把其余方案也做出来。这句话由程序拼出，方案名是设计师起的，字母和"其余方案不做"由程序生成，不经模型转述。
- **选定方案在主代理下一轮才让它看到，不触发回复**（用户 2026-10-28 决定）：和原来补充说明的做法一样，不打断用户；用户下次说话时，主代理据此把正文改成只剩选中的方案。被否决的做法：马上触发回复（打扰用户接着确认别的原型）；完全不告诉主代理（正文和选定的方案可能对不上）。
- **"其他"里的话由主代理先弄清意图，用户明确同意后才重派，只改给主代理的提示**（用户 2026-10-28 决定）：用户的原话是"其他输入的时候，需要 AI 先分析用户的意图，可能需要重新出预览也可能不需要出，意图明确了之后再记录，不要直接重新出预览"。原来交给主代理的提示是"是提问就回答，要修改就重派"，主代理把提问误判成修改时会直接重派，这一版当场作废。主代理把确认过的修改要点写进派设计师时"要画什么"的说明。被否决的做法：主代理要重派时由程序弹窗请用户确认（程序能保证，但用户选了只改提示词）。代价：主代理仍可能不问就重派，程序拦不住。
- **方案名中间的换行和连续空白合并成一个空格**（用户 2026-10-28 确认）：审查发现模型写的方案名带换行时，确认窗口的选项行会被拆成两行、打乱终端重绘。
- **方案名是模型写的，显示前去掉危险字符**：威胁模型"模型输出不可信"。方案名只用于显示和下游清单，选中哪一项由用户在窗口里操作决定。
- **原型数据格式变了，数据库版本号从 8 升到 9**：按项目规矩不写迁移，升级前留下的本机数据打不开（用户 2026-10-28 确认）。
