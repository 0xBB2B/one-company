# 原型统一分成左边切换、右边页面、页面下方说明

## 背景与问题
- 原型：一份单个 HTML 文件的界面设计，由原型设计师（只负责出原型的子代理）交稿，用户在浏览器里打开查看，再在"确认原型"窗口里决定去留。
- 现在设计师把要上线的页面、这次设计的说明、切换状态用的控件都画在同一张页面里。规矩只要求画四种状态、做成能点，没有说说明和切换放哪。
- 用户看"管理员每日提醒时间设置"第 2 版时，分不清哪些是正式页面、哪些只是说明。这份文件里，顶部提示条、"保存配置（演示）"按钮、"时间存储约定"、底部"发送规则，还有这些待确认"都画在页面内容里；切换状态的深色条在页面顶部，一滚动就看不见了。
- 分不清会让用户没法判断这一版该不该通过。下游也受影响：worker 要照原型实现，reviewer 和 qa 把文案不一致列为阻塞，"保存配置（演示）"可能被当成正式文案。
- 用户要所有原型统一成同一种样子，不同设计师交的稿也一样。

## 目标
- 每份新交的原型都分成三块：左边是切换栏，放切换按钮；右边上方是隔离框，只放被设计的页面；隔离框下方是说明区，放这次设计的说明。
- 外框由程序生成，每份原型的外框长得完全一样，设计师改不了。
- 设计师交的页面只含正式上线后用户能看到的内容。
- worker、reviewer、qa 只对照隔离框里的页面，切换栏和说明区的内容不实现、不核对。

## 非目标
- 程序判断某段文字该放左边还是右边：程序看不懂内容，这由设计师的规矩和用户看稿把关。
- 兼容旧格式的原型：升级前交的原型文件整份都是页面，规矩只认新外框。带这种原型的需求要先做完或重派，再升级，README 写明。
- 改"确认原型"窗口：选项、方案清单、通过和放弃的方式都保持现状。
- 改开发这个仓库时用的全局规矩 `~/.claude/CLAUDE.md`：用户选了只改产品。
- 给切换栏或说明区加"收起"按钮、拖动改变高度，或在隔离框里切换手机、平板、桌面宽度。手机界面的页面由设计师在页面里自己限定宽度。
- 改数据库记录格式或数据库版本号：拼好后写入的仍是单个 HTML 文件。

## 整体验证路径
1. 主代理派原型设计师出"设置页"，设计师画了管理员页和成员页，管理员页有正常、空数据、加载中、出错四种状态，另有两个方案 → 交稿后浏览器打开原型，左边是深蓝色切换栏，最上面的亮青色虚线框写着"这份原型有 2 个方案，点这里切换对比"，右边框上方写着"▼ 被设计的页面：只有这个框里的内容要实现"，框下方是深蓝色说明区，顶部写着"设计说明 · 不属于页面"。
2. 在切换栏依次点"出错""方案 B""成员页" → 右边框按选择重新载入，框上方右侧显示当前选择；说明区里"这个画面的说明"跟着换。
3. 看右边框里的页面 → 找不到"演示""原型""待确认"这类字样，按钮写的是"保存配置"这种真实文案。
4. 在切换栏点"方案 B"之后，看主窗口 → "确认原型"窗口仍在等你选，切换栏的点击没有登记任何决定。在窗口里选"方案 B"回车 → 显示已登记，这一版写进需求草稿。
5. 批准需求，PM 派 worker、reviewer、qa → 三者收到的规矩都写明只对照隔离框里的页面；页面里的文案和实现不一致仍算阻塞，切换栏和说明区的文字和实现不一致不算阻塞。
6. 用户在"其他"里提意见，主代理重派第 2 版 → 设计师读第 1 版文件里的页面和各张清单，按用户原话改后再分开交稿，第 2 版同样套上外框。

## 决策记录
- **质疑结论**：问题真实存在，值得做。用户看不出哪些是正式页面就没法判断要不要通过；下游规矩又要求文案与原型一致，说明混进页面可能被照着实现（这一点是读 `role-rules/worker.md:12`、`reviewer.md:9`、`qa.md:8` 推断的，没有实际跑过）。更便宜的替代做法是只改规矩，见下面"程序生成外框"一条。
- **切换放左边，页面放右边，说明放页面下方**（用户 2026-11-02 决定）：用户最初的原话是"我需要所有的原型设计明确哪些是需要被设计的页面，哪些是本次设计时候作为说明和切换用的地方"。第一版预览把说明和切换都放在左栏；用户读 PRD 时提出"页面说明是不是可以放在右边页面的下方空出一部分来放说明？有的时候说明会很多"。说明区横向宽，三块说明能并排。被否决的做法：说明和切换都放左栏（说明多时挤在窄栏里）；说明在左、切换在右、页面夹在中间（页面可用宽度更窄）。代价：页面的可视高度变矮。1440×900 的窗口里实测，说明多时页面高约 540 像素、说明区高约 300 像素；说明少时页面高约 640 像素。页面超出部分在隔离框里滚动。
- **程序生成外框，设计师分开交页面、说明和切换项**（用户 2026-11-02 决定）：根源是说明和页面由同一个设计师画在同一张稿子上，只有分开交才碰到根源，也只有程序生成才能保证每份完全一样。被否决的做法：只改规矩（设计师不照做时只能靠用户打回）；规矩加交稿检查（外框仍由设计师画，各份长相可能不同）。代价：要改交稿工具的参数，设计师的页面要配合切换，约 1 到 1.5 天。
- **切换失灵程序发现不了**：设计师不能开浏览器，也不能运行命令，页面没有响应切换时，程序不知道。用户看稿时会发现，在"其他"里提意见重派。
- **只改产品里的原型设计师**（用户 2026-11-02 决定）：截图里的问题出在产品里。全局 `~/.claude/CLAUDE.md` 的预览页规矩不在这个仓库。
- **设计师只交一份页面，页面、画面、方案都由这一份响应**：一份页面只写一次公共样式，程序只拼一次。被否决的做法：每个画面交一份完整页面（4 种状态乘 3 个方案要写 12 份，输出太长，也容易碰到 1 MiB 上限）。
- **"这个画面的说明"跟着画面走，"只在原型里成立"和"还没确认的问题"是整份原型共用的两张清单**：用户确认的预览里后两块曾随页面变化，改成整份共用后设计师只需写一次。预览页已同步改成这样。
- **只有一项可选的切换组不显示**：只有 1 个页面或 1 个画面时没东西可切；没有方案清单时不显示方案组。这是用户确认的预览没有画到的情况，按"有东西可切才显示"定的。
- **切换组名默认"状态"，设计师可以改**：终端界面的多步交互要显示成"步骤"，和预览一致。
- **窗口宽度超过 760 像素时，说明区最高占窗口的三分之一，超出时自己滚动**：这样隔离框至少留出约六成窗口高度（900 像素高的窗口里约 540 像素）。说明少时说明区按内容变矮，全部为空时不显示。三分之一是按上面的实测定的，用户可以推翻。
- **切换栏从 320 像素收窄到 260 像素**：说明移走后左栏只放切换按钮，让出的宽度给页面。1440 像素宽的窗口里隔离框宽 1152 像素。
- **有多个方案时，切换提示放在最显眼的位置**（用户 2026-11-02 决定）：用户原话是"如果有不同的方案选择需要在显著位置做切换提示"。方案是用户最后要做的选择，切换栏最上面用亮青色虚线框写明有几个方案，隔离框上方用亮青色标签一直显示当前看的方案。提示框底部提醒最后在"确认原型"窗口里定，因为在这里切换不算选定。
- **终端页面铺满隔离框，文字从左上角开始**（用户 2026-11-02 决定）：用户原话是"终端应该模拟终端的样子左上角对齐或者全屏等"。真实终端的文字从左上角开始，居中摆放不像终端。仍按 80 列换行，这和设计师规矩原有的固定 80 列一致。不画窗口标题栏，隔离框本身就是窗口。
- **旧格式原型不兼容，README 写明**（用户 2026-11-02 决定）：实施时审查发现，下游规矩写的是去 `prototype-page` 找页面，旧文件里没有这个位置。被否决的做法：四份规矩各加半句"文件里没有这个 textarea 时，整份文件就是页面"（要长期背着旧格式的写法）。代价：带旧原型的需求要先做完或重派再升级，用户自己的"管理员每日提醒时间设置"要重派一次。
- **窄窗口下说明区不限高度**（用户 2026-11-02 决定）：窗口不超过 760 像素时，整个网页本身就能滚动，再套一层滚动区在窄屏上难用。实测 390×844 的窗口里，说明很长时说明区高 3628 像素，加上限是 281 像素。代价：网页总高度变长。
- **页面里的 `#` 链接留在隔离框里**（实施时审查发现）：`srcdoc` 页面的相对地址按外层文件解析，点 `href="#"` 会把外框整个套进隔离框。修复是在页面最前面加 `<base href="about:srcdoc">`。代价：页面自己写的 `<base>` 不生效；`href=""` 和只带查询参数的链接会跳到空白页，点切换按钮或刷新网页能恢复。只在 Chromium 上实测过；Safari 和 Firefox 按 HTML 规范应当一样，这是推测，没有验证，用默认浏览器打开一份原型、点页面里的 `href="#"` 链接就能确认。
- **外框用蓝图工程风格**（用户 2026-11-02 决定）：用户要外框有样式模板，从深色工作台、浅色文档、蓝图工程、施工警示、黑白粗线 5 种里选了蓝图工程：深蓝网格底、亮青色虚线、等宽字。风格只改外框，设计师画的页面不受影响。
- **隔离框加沙箱**（用户 2026-11-02 决定）：用户要求"内部的原型样式和外部的需要隔离不受影响"。样式靠独立的 iframe 隔开，实测往两边灌最强的样式规则，另一边都不变。脚本要靠沙箱才隔得开，所以隔离框写 `sandbox="allow-scripts"`。代价：页面用不了 localStorage、alert、confirm，设计师规矩写明状态放在脚本变量里，弹窗和提示都画在页面里。
- **说明区不留空、条目收紧**（用户 2026-11-02 决定）：用户看预览时提出"底部不要留空，现在的原型里面有很多没必要的空行挤占空间"。说明区按内容决定高度，行距和条目间距收紧。
- **切换时右边框重新载入，页面里输入的内容清空**：这是用户确认的预览里的行为，也保证每个画面都从干净的状态开始看。
- **1 MiB 上限按拼好后的文件算**：这个上限保护读原型文件的 worker、reviewer、qa 的输入大小，下游读到的是拼好后的文件。
- **新增单点验收 P17：设计师按分开的格式交稿**：P13 只判主代理会不会派设计师，没有一条验收让真实模型用新的交稿格式。P17 只判能由程序判定的事：交稿被收下、四种状态都在清单里、页面里没有"演示""原型""待确认"字样。代价：每次全量验收多一条。
- **验收范围**：这次改 `role-rules/prototype.md`、`worker.md`、`reviewer.md`、`qa.md` 和交稿代码，合并前跑单点 P1–P17 和 M9-AC12；不碰 `role-rules/pm.md`、`rules/*.md` 和批准流程，不用跑渐进需求完整流程。
