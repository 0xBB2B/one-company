# 原型外框换柔和配色，设计师结合项目整体界面和 DESIGN.md 出原型

## 背景与问题
- 原型外框：程序给每份原型生成的固定外框。左边是切换栏，放原型名称和切换按钮；右边上方是隔离框，里面是设计师交的页面；隔离框下方是说明区。切换栏和说明区上线后都不存在。
- 现在的外框是深蓝网格底，线条、标签、选中按钮都是亮青色，选中的按钮整块填亮青。外框和隔离框里的白色页面反差很大，用户看原型时觉得刺眼。
- 有多个方案时，方案按钮放在切换栏最上面的虚线提示框里，下面紧跟页面和画面的按钮。三组按钮挤在同一栏，长得也一样，看的人分不清哪组切方案、哪组切页面。
- bb-spec 插件 15.5.0 的原型外壳已经换成明暗两套柔和配色，方案按钮放在右上角。用户要 one-company 的原型外框和它一致。
- 原型设计师（只负责出原型的子代理，只能读文件）出原型时，常常只画一块孤零零的页面，不带项目的顶栏、侧边导航，配色和组件也是自己定的。现在的规矩只有一句"需要了解现有界面时读源码和样式"（`role-rules/prototype.md:10`），没要求把项目的整体布局和现有样式画进去。这样画出来的页面和实际做出来的差得远，用户没法按原型判断改动好不好。
- 项目里没有一份写明设计风格的文件。每次出原型，设计师都要自己从代码里总结风格，前后几份原型的颜色、字号、间距可能各不一样；worker 写界面代码、reviewer 审查时也没有统一的标准可对照。用户会看原型判断好不好，但不一定能用专业的话把界面设计规范写下来。

## 目标
- 外框有明亮、暗黑两套柔和配色，默认跟系统外观一致，右上角能手动切换。
- 有多个方案时，方案按钮在框上方右侧；切换栏只放页面和画面的切换。
- 项目里有界面代码时，设计师先读懂整体布局和现有样式：改已有页面时照现在的样子整页还原，只改要改的地方；新页面套进现有的整体布局和样式里画。
- 用户项目根目录有一份 DESIGN.md，十章全部用可以量化的数值写界面设计规范。它由原型设计师维护：每次交原型都带全文，程序检查合格才收稿，用户通过原型时写入。设计师、worker、reviewer 都照它做。

## 非目标
- 让外框的明暗主题影响设计师交的页面：隔离框里仍是白底，主题只换外框。
- 记住用户选的明暗：不存进浏览器，每次打开都先跟系统外观。
- 已经生成的原型文件换新外框：外框在交稿时拼进文件，旧文件保持原样，下一版重新交稿后才是新外框。
- 改 qa 的规矩、主代理的规矩（`rules/*.md`）和 PM 的规矩。
- 自动提交 DESIGN.md：程序只写到仓库根目录，和项目规范 AGENTS.md 一样由用户自己提交。
- 拦住用户自己在编辑器里改 DESIGN.md：只拦代理的 edit、write。
- 程序判断 DESIGN.md 写得好不好看：程序只查章节、必填项、值的格式、间距倍数和对比度。
- 程序检查设计师有没有照项目样式画：程序看不懂页面像不像，靠 P19 和用户看稿把关。
- 保留升级前还在做或还在等确认的原型：它们没带 DESIGN.md，迁移时作废，要重派。

## 整体验证路径
1. 系统是浅色外观，设计师交一份带 2 个页面、4 种状态、4 个方案的原型 → 浏览器打开后外框是雾灰蓝底，线条是灰蓝色；框上方右侧依次是"方案"、4 个方案按钮、「☀ 明亮」「☾ 暗黑」，「方案 A」和「☀ 明亮」显示为选中；切换栏顶部写"当前：方案 A：<名称>"和"最后选哪个，在“确认原型”窗口里定"，下面只有页面和状态两组按钮。
2. 点右上角「方案 C」→ 隔离框重新载入方案 C 的页面，切换栏顶部变成"当前：方案 C：<名称>"，页面和状态的选中项不变。
3. 点「☾ 暗黑」→ 外框换成石墨深灰底，隔离框里的页面不变；把系统外观换成浅色 → 外框仍是暗黑。
4. 关掉网页重新打开 → 外框又跟系统外观一致。
5. 交一份只有 1 个页面、没有方案清单的原型 → 右上角只有明暗按钮，切换栏顶部没有"当前："那一行。
6. 在"确认原型"窗口里选方案 C 回车 → 登记的是方案 C；在右上角点方案按钮不登记任何决定。
7. 在一个有顶栏导航和自己主色的网页项目里，让主代理出"设置页加每日提醒时间"的原型 → 隔离框里是整张设置页，顶栏导航、设置页原有的几块都在，新加的设置项用项目的主色和组件样子；交稿里带一份十章齐全的 DESIGN.md，主色是项目的主色。
8. 在"确认原型"窗口里看到"通过后在仓库根目录新建 DESIGN.md……"，选"通过" → 仓库根目录出现 DESIGN.md，没有被提交。
9. 再出一份原型，设计师把次要文字写成对比度不够的颜色 → 交稿被退回，原因写明两个颜色和实际对比度；改好后重交，窗口里列出改了哪几章。
10. 批准需求，PM 派 worker、reviewer → 两者的任务说明里都有 DESIGN.md 全文；worker 用 edit 改 DESIGN.md 被拦下；reviewer 把用了 DESIGN.md 之外颜色的界面改动列为阻塞。

## 决策记录
- **质疑结论**：问题真实存在，值得做。外框是每份原型都套的，看原型的每个人都受影响；改动只在外框的样式和脚本里，代价小。
- **照搬 bb-spec 15.5.0 外壳的配色和明暗切换**（用户 2026-11-04 决定）：用户原话是"现在的蓝图看起来太刺眼了"，并指定参考 bb-spec 插件的原型外壳。我给了两个做法：只换成雾灰蓝一套颜色（约 1 小时），或者再加暗黑主题和右上角明暗切换（约半天）。用户选了后者。被否决的做法是只换一套颜色：用户用深色系统时外框仍是浅色。颜色值和 bb-spec 外壳逐个对应，两边看原型的样子一致。
- **多个方案时方案按钮挪到右上角，切换栏只放页面和画面**（用户 2026-11-04 决定）：用户原话是"如果有 ABCD 多个方案选择的话，把方案切换按钮放在右上角和给你参考一致，左边列只展示方案内的切换"。方案是整份原型最后要做的选择，和页面、画面不是一类，分开放后不会点混。
- **去掉切换栏的方案提示框和框上方的方案标签**（用户 2026-11-04 看预览后确认）：2026-11-02 的外框需求要求"在显著位置提示有几个方案"，当时用的是切换栏最上面的虚线提示框加框上方的亮青标签。现在右上角那排方案按钮本身就显示有几个方案、当前是哪个，再留提示框和标签就重复了。切换栏顶部改成一行"当前：方案 X：<名称>"。
- **"最后选哪个，在“确认原型”窗口里定"放在"当前："下面**（用户 2026-11-04 看预览后确认）：这句提醒用户在外框里切换方案不算选定，原来在方案提示框底部，提示框去掉后挪到这里。
- **切换栏、框上方一行和说明区用同一种底色**（用户 2026-11-04 看预览后确认）：原来切换栏和说明区比中间深一层。bb-spec 外壳只用一种底色，用细线和虚线分区，跟它一致。
- **明暗选择不存进浏览器**（用户 2026-11-04 看预览后确认）：和 bb-spec 外壳一致。原型文件按本地文件打开，各份原型各自存反而不一致；每次跟系统走最省事。代价：习惯手动切的人每次打开都要再点一次。
- **设计师结合项目整体界面出原型，并入这份需求**（用户 2026-11-04 决定）：用户读 PRD 时提出"如果项目能阅读源码能了解UI或者渲染的话，出原型设计的时候不要只单独模拟一个画面，这样模拟出来的画面并不精准，UI也可能完全不一样。需要结合项目的整体框架，整体UI来进行原型设计"。它和外框配色同属原型功能，两样都改产品代码，合并前都要跑一轮全量真实模型验收，并在一起只跑一轮。被否决的做法：另开一份 PRD（要多跑一轮全量验收）。
- **改已有页面整页还原，新页面套进整体布局**（用户 2026-11-04 确认）：改已有页面时只画改动的那一块，看不出它和页面其他部分放在一起的样子；新页面不套顶栏、侧栏，看不出它在应用里的位置。仓库里还没有界面代码时，设计师照现在的做法自己定。终端界面同理，照现有命令的输出格式还原。被否决的做法：只要求改已有页面时还原（新页面仍会画成孤立的一块）。
- **02 只改设计师的规矩，主代理的规矩不改**：设计师能读整个仓库，自己找得到界面代码。主代理的规矩在 `rules/*.md`，改了要多跑渐进需求完整流程，这次不需要。
- **新增单点验收 P19：设计师照项目样式画**（用户 2026-11-04 决定）：只改规矩的话，设计师有没有照做只能靠用户看稿发现。P19 只判程序能判定的事：交上来的页面里有样例项目的导航文字、主色值和设置页原有的标题。被否决的做法：只改规矩，不加验收。代价：每次全量验收多一条。
- **DESIGN.md 并入这份需求，由原型设计师维护**（用户 2026-11-04 决定）：用户读 PRD 时提出"每次UI设计都需要维护一个design.md的文档放在根目录下，每次UI设计的时候先阅读这个文档，要求设计风格统一"，并说"DESIGN.md应该由原型设计师维护，用户是主观的，需要看到原型设计的HTML判断好还是不好，但是可能并不专业，无法准确描述应该如何记录DESIGN.md内容"。所以设计师写 DESIGN.md，用户只看原型；通过原型就是同意这一版界面设计规范，这符合"代理的设计经用户明确同意才能实施"。被否决的做法：照项目规范 AGENTS.md 的做法由主代理提交、用户读全文后确认（用户不一定能判断规范写得对不对）；用户自己写（同样的原因）。
- **通过原型时立刻写到仓库根目录，不提交**（用户 2026-11-04 决定）：之后派出的设计师、worker、reviewer 马上按新内容工作，和 AGENTS.md 的写法一致。被否决的做法：需求做完关闭时随归档提交进需求分支（要处理一个需求里多份原型、多个需求同时改的情况，约多 1 天）。代价：需求后来放弃了，DESIGN.md 已经改了，要用户自己用 git 还原。
- **每次交稿都带全文**（用户 2026-11-04 决定）：程序每次都能检查章节齐不齐，和仓库里一样就不写。被否决的做法：只在要改时带（不带时程序查不了，规范可能悄悄过期）。代价：设计师每次多输出一份最大 16 KiB 的文字。
- **窗口里加一行，列出改了哪几章**（用户 2026-11-04 决定）：用户不用读 DESIGN.md 的内容，但知道通过会改到它。这一行用普通颜色，不用灰色，免得被当成可以不看的附注。被否决的做法：不显示、通过时默默写入。
- **十章、每章必填项、值的格式**（用户 2026-11-04 决定）：用户要求"需要可量的硬标准，不能是含糊不清的描述"。每个必填项都写成数值或固定选项，程序逐项检查，缺项或格式不对就退回。对比度下限 4.5:1 和 3:1 来自 WCAG 2.1 的 1.4.3"对比度（最低）"和 1.4.11"非文字对比度"。被否决的做法：只在规矩里写章节清单、程序不检查（写漏了只能靠用户发现）。
- **十章是最低要求，可以按需加章，但不许重名、重项**（用户 2026-11-04 决定）：写计划后的审查发现，原来的检查只看每章第一份、只比较十章，设计师在末尾追加第二个 `## 颜色` 或 `## 备注` 时检查能过、窗口显示没有变化，没经用户看过的内容会写进仓库、发给 worker。用户原话："十章是必须的基础，可以按需增加章节……但是 DESIGN.md也不是垃圾桶什么都往里面塞"。所以新加的章允许、程序不查内容；同名章、同节重项、重复的 `### 明亮` 都退回；窗口列改动时把新加的章和开头文字也算上，只有全文一样才不显示。DESIGN.md 只放全项目通用的规范，这条写进设计师规矩，程序不判断，靠 16 KiB 上限兜住总量。被否决的做法：十章以外一律退回（用户要能按需加章）；不退回、只在窗口里提一句（重复的章会让下游不知道该照哪一份）。
- **先读 DESIGN.md，没写到的再读代码**（用户 2026-11-04 决定）：用户原话"每次产出原型方案的时候先阅读 DESIGN.md如果不满足再阅读相应的代码，可以减少代码搜索"。整体布局、样式、组件照 DESIGN.md；这个页面现在的具体内容、DESIGN.md 里没有的组件再读代码；仓库里还没有 DESIGN.md 时照 02 的做法先读代码。
- **去掉 BOM、统一换行后再检查和比较**：审查发现，用户在 Windows 上存过的 DESIGN.md 用 `\r\n` 换行，和设计师交的同样内容比会误报"改了九章"；文件开头的 BOM 会让第一章被当成缺失。这是鲁棒性修复。
- **程序按色值算对比度，不够就退回**（用户 2026-11-04 决定）：文字、次要文字和背景要达到正文最低对比度，主色和背景要达到图标和边框最低对比度。按 WCAG 公式实算：`#999999` 配 `#ffffff` 是 2.85:1，`#6b7280` 配 `#ffffff` 是 4.83:1，`#0f766e` 配 `#ffffff` 是 5.47:1。被否决的做法：只查格式不算对比度。
- **老样式不合规时写合规的新值，在原型里问用户**（用户 2026-11-04 决定）：DESIGN.md 和原型都按新值画，老值和新值的对照写进"还没确认的问题"，用户通过原型就是同意改。被否决的做法：照实写老值（和"对比度不够就退回"冲突）。代价：通过后 worker 会按新值改到老页面的颜色。
- **各方案风格不同时每个方案各交一份**：用户选哪个方案就写入哪一份；风格相同的只交一份。这是我按"选方案就是选风格"定的，用户在预览里确认了窗口的写法。
- **DESIGN.md 最大 16 KiB**：派 worker、reviewer 时全文要放进任务说明，和项目规范 AGENTS.md 的上限一样，保护子代理的输入大小。
- **代理不能直接改 DESIGN.md**：主窗口和子代理用 edit、write 改它时被拦下，只能随原型通过写入。威胁模型的第一条是"模型输出不可信"，不拦的话，代理可以绕过用户确认改掉界面设计规范。
- **交稿后 DESIGN.md 被别处改过就不能通过**（用户 2026-11-04 在预览里确认）：两个需求同时出原型时，后通过的会覆盖先通过的。程序在派工时记下 DESIGN.md 的内容指纹，打开窗口时和写入前各对一次，不一样就不写、不登记通过，提示重派。
- **派 worker、reviewer 时带上 DESIGN.md，PM、qa、explore 不带**（用户 2026-11-04 决定）：设计师照它画，worker 照它写，reviewer 照它审，做出来的界面和原型风格才一致。qa 只按验收项测行为，PM 不写界面代码，explore 只查资料，都用不上。
- **升级时还在做或还在等确认的原型作废，确认框写一句固定的话**（用户 2026-11-04 决定）：项目规矩要求数据库只认当前格式，格式变了就写迁移。这些原型交稿时没带 DESIGN.md，按新规则不能通过；迁移把它们作废，用户重派一次即可。迁移框架只能显示写死的几句话，弹框前不读库，所以确认框写固定的一句，不列具体是哪几份。被否决的做法：改迁移框架、弹框前先读库列出具体原型（要改 storage、host 两层，约半天，只为这一次用）。
- **要升 `PROTOCOL_VERSION` 和数据库版本号**："确认原型"窗口要从守护进程拿到"改了哪几章""交稿后是否被改过"，窗口和守护进程之间的通信变了；原型记录要存设计师交的 DESIGN.md，数据库格式变了。
- **验收范围**：这次改了产品代码（原型外框、交稿检查、确认窗口、派工任务说明、写入拦截、数据库迁移）和 worker、reviewer、原型设计师的规矩，按项目规矩合并前跑纯代码测试四项、单点 P1–P19 和 M9-AC12；不碰 `role-rules/pm.md`、`rules/*.md` 和 PM 复核流程，不跑渐进需求完整流程。
