# 主代理澄清时先列新技术

主代理：用户在 pi 窗口里直接对话的代理，负责和用户把需求问清楚、写成需求草稿、请用户批准。需求「实现」板块：需求文档规范里标了 `record: implementation` 的那个板块（包里默认的规范叫「实现」），只写用户明确提出的实现要求。

## 用户故事
### P0：作为要做新项目的用户，我想要主代理在写需求时就把要用的技术列给我，以便我能在动工前换成自己想要的

**用例（主路径）**
- 场景：用户在空项目里说“做一个网页版的图书馆借还系统”，开着 vue 和 go 两个专项代理。
- 操作：主代理保存草稿后弹出技术清单窗口，用户选“全部同意”。
- 预期：清单里前端、后端、数据库各占一项，前端和后端的来源是“按项目规范或已开启的专项代理和 skill 推荐”。用户同意后，主代理修改草稿，「实现」板块列出清单里每一项的名称和类别。

**用例（用户要换）**
- 操作：用户在清单窗口里写“后端换成 Java，数据库换成 MongoDB”。
- 预期：主代理按意见改清单，再弹一次完整清单；Java 和 MongoDB 的来源是“用户点名”；用 Java 连带要用的框架（如 Spring Boot）也作为新技术列进清单。用户同意之前，「实现」板块不写这些技术。

**用例（已有技术栈）**
- 场景：项目里已经有 Go 后端和 Vue 前端，用户要加一个“按作者搜索图书”的功能，只用到 Go 和 Vue。
- 预期：主代理不弹技术清单窗口，「实现」板块不为此写技术。

**用例（用户在需求里点名）**
- 场景：空项目，用户说“用 Python 和 SQLite 做一个记账脚本”。
- 预期：清单里 Python 和 SQLite 的来源是“用户点名”，仍要用户在窗口里同意后才写进「实现」板块。

## 约束
- C-1：需求要用到新技术时，主代理在请用户批准需求之前，用技术清单窗口把这次要用的全部新技术一次列出。新技术指项目里还没用过的语言、框架、数据库、第三方库、中间件或外部服务、工具，以及要升级的已有第三方库。
- C-2：主代理读项目的依赖清单文件和代码目录判断一项技术在项目里有没有；拿不准时当作新技术列进清单。项目里已经在用的技术，接着用时不列。
- C-3：每项的来源如实填写：用户在需求里说过的是“用户点名”；按项目规范（AGENTS.md）或已开启的专项代理、skill 推的是“按项目规范或已开启的专项代理和 skill 推荐”；其余是“AI 提议”。推荐依据只用来定选哪项，不能代替用户同意。
- C-4：用户选“全部同意”后，主代理用 updateDraft 把清单里每一项的名称和类别写进「实现」板块。用户同意之前，「实现」板块不写任何新技术。
- C-5：用户写了修改意见时，主代理按意见改好清单，再用技术清单窗口弹一次完整清单；因修改连带要用的新技术也要列进去。直到用户选“全部同意”，才写进「实现」板块。
- C-6：用户按 Esc 暂不回答时，清单保留；用户之后在对话里说同意或修改，主代理照 C-4、C-5 处理。

## 验收
- [ ] C-1、C-3：空项目里说“做一个网页版的图书馆借还系统”，主代理请用户批准之前弹出技术清单窗口，前端、后端、数据库各至少一项，每项来源都是 3 种之一。（真实模型验收 P18）
- [ ] C-2：项目里已有 Go 后端和 Vue 前端，加一个只用 Go 和 Vue 的功能，主代理不弹技术清单窗口。（真实模型验收 P18）
- [ ] C-4：选“全部同意”后，草稿「实现」板块包含清单里每一项的名称。（真实模型验收 P18）
- [ ] C-1～C-6：主代理的规则文字写明：什么时候列新技术、怎么判断项目里有没有、拿不准当新技术、来源怎么填、同意后写进「实现」板块、修改后重新弹完整清单、同意前不写；包里默认需求文档规范的「实现」板块说明写明“用户在技术清单窗口里同意的技术也写在这里”。（单元测试核对规则文字）

## 验证路径
1. 在空项目里让主代理做图书馆借还系统 → 弹出技术清单窗口。
2. 写修改意见“后端换成 Java” → 再弹一次完整清单，后端是 Java，来源是用户点名，并多出 Java 用的框架。
3. 选全部同意 → 草稿「实现」板块列出清单里每一项。
4. 在已有 Go + Vue 的项目里加一个只用 Go 和 Vue 的功能 → 不弹技术清单窗口。
