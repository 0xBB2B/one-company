# PM 补漏与执行把关

PM：需求批准后接手的代理，负责拆任务、派 worker 写代码、派审查检查改动。上报：PM 用 `one_company_workflow_manage` 的 escalate 把一个任务交给用户裁决，这件事会作为待处理事项出现在状态面板上。需求「实现」板块：需求文档规范里标了 `record: implementation` 的那个板块，用户同意的新技术写在这里。

## 用户故事
### P0：作为已经批准了需求的用户，我想要 PM 发现还缺一项技术时先问我，以便项目里不会多出我没同意的东西

**用例（主路径）**
- 场景：图书馆借还系统的需求已批准，「实现」板块写了 Vue、Go、PostgreSQL。PM 拆到“导出借阅报表”任务时，发现要用一个写 Excel 的 Go 库。
- 操作：PM 上报这个任务；用户在状态面板选中这件事，主代理弹出技术清单窗口，用户选“全部同意”，再批准新版本。
- 预期：清单只有这一项，标题下写明“PM 拆计划时发现需要 · 卡住的任务：T4 导出借阅报表”。用户同意后，这个任务按“调整目标或范围”处理；主代理把这个库写进「实现」板块，用户批准新版本后，PM 复核并修改这个任务，把依赖清单文件放进它的写入范围，再派出。

**用例（worker 自己引入）**
- 场景：worker 做任务时觉得加一个 Redis 缓存更好，改动里新增了用 Redis 的 docker-compose 配置，而「实现」板块和项目里都没有 Redis。
- 预期：审查把它判为阻塞，写明 Redis 不在需求「实现」板块里、项目里原来也没有。

**用例（PM 自己写了“用户已同意”）**
- 场景：PM 在任务说明里写“用户已同意使用 lodash”，但「实现」板块里没有 lodash，项目里也没有。
- 预期：worker 不装 lodash，审查发现改动用了 lodash 时判为阻塞。

## 约束
- C-1：PM 拆计划时，语言、框架、数据库这类技术栈只用需求「实现」板块写了的和项目里已有的。任务要用两者都没有的新技术（包括升级已有的第三方库）时，PM 不派这个任务，用 escalate 上报；note 里逐项写名称、类别、用途、为什么非它不可、备选为什么不选。
- C-2：用户在状态面板选中这类事项时，主代理用技术清单窗口（带“PM 拆计划时发现需要”那一行）把 PM 要的新技术列给用户，各栏按 PM 的说明和主代理自己读到的代码填写。
- C-3：用户在这个窗口里选“全部同意”时，这个任务登记为用户选了“调整目标或范围”；主代理把这些技术写进「实现」板块，请用户批准新版本。PM 收到新版本后，才能把对应的依赖清单文件放进任务的写入范围并派出。用户写了修改意见时，主代理按意见改清单再弹一次，或按意见修改需求，任务继续等用户决定。
- C-4：PM 不能凭自己在任务说明里写的“用户已同意”放行新技术，同意只以「实现」板块为准。
- C-5：派给 worker 的任务内容里，程序附上用户批准的那一版需求「实现」板块的原文。worker 只用这段原文里写了的和项目里已有的技术，任务说明里写的不算；需要用两者都没有的新技术时，不自己装、不改依赖清单文件、不写引入它的代码或配置，在结果里写明要什么、为什么，由 PM 上报。
- C-6：审查读被审任务关联需求的「实现」板块；本次改动引入了「实现」板块没写、项目里原来也没有的新技术时，判为阻塞，写明是哪项技术、在哪个文件。新技术的范围和主代理判断的一样：语言、框架、数据库、第三方库（含升级）、中间件或外部服务、工具。
- C-7：程序给模型看的报错和工具说明里，讲到要用新技术时，写明这是新技术、要由 PM 上报、用户同意后写进「实现」板块。

## 验收
- [ ] C-1、C-4：PM 的规矩文字写明：技术栈只用「实现」板块写了的和项目里已有的；要用新技术时不派任务、先上报，note 逐项写 5 栏理由；任务说明里写“用户已同意”不算数。（单元测试核对规矩文字）
- [ ] C-2、C-3：从状态面板打开 PM 上报的新技术事项，弹出带“PM 拆计划时发现需要”一行的技术清单窗口；选“全部同意”后，这个任务的用户决定是“调整目标或范围”，PM 收到“等用户批准新的 PRD 版本后，复核并按新范围修改该任务”；选“写修改意见”后任务仍在等用户决定。（单元测试）
- [ ] C-5：派给 worker 的任务内容含批准版「实现」板块的原文（批准新版本后再派，附的是新版本的原文）；PM 在任务说明里写了别的技术，任务内容里附的仍是「实现」板块原文。worker 的规矩文字写明：依据是这段原文和项目里已有的，任务说明里写的不算；需要新技术时不装、不改依赖清单、不写引入它的代码或配置，在结果里写明要什么、为什么。（单元测试）
- [ ] C-6：审查的规矩文字写明：读「实现」板块，改动引入了板块没写、项目里也没有的新技术时判阻塞，范围包括 6 类技术。（单元测试核对规矩文字）
- [ ] C-7：任务交结果被拒收时的建议文字、PM 的 workflow_manage 工具说明，用的都是“新技术”的说法，写明由 PM 上报、用户同意后写进「实现」板块，放行依据只有「实现」板块。（单元测试）
- [ ] 改了 PM 和主代理的提示词，渐进需求完整流程（M9-AC2/AC3/AC11）、零自定义完整流程（M9-AC12）和全部单点验收照常通过。

## 验证路径
1. 在批准过的图书馆需求里，让 PM 遇到一个要写 Excel 的任务 → 状态面板出现待处理事项。
2. 选中这件事 → 弹出只有一项的技术清单窗口，标题下写明卡住的任务。
3. 选全部同意、批准新版本 → 「实现」板块多了这个库，PM 修改任务后派出。
4. 让 worker 的改动里多出一个「实现」板块没有的 Redis 配置 → 审查判为阻塞并写明 Redis 和所在文件。
