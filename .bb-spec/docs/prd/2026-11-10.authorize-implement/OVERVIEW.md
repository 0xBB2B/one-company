# 批准时提醒授权实施，事后能单独补授权

## 背景与问题
- 动作：用户能授权的五种事，分析、规划、实施、提交、推送（analyze、plan、implement、commit、push）。每种都要用户的原话明确说出来；"批准"只代表认可需求内容，不代表允许动手。
- 批准清单：用户批准需求那一刻程序记下的清单，写着确认了哪些段落、授权了哪些动作。派出 PM（需求批准后负责拆任务、派 worker 写代码的代理）和 PM 正式规划，都只认清单里的"实施"。
- 问题一：主代理请用户批准时不提醒要不要顺便说"实施"。用户只说"批准第 15 版需求"，需求生效了，批准清单里却没有实施。主代理不知道这一点（批准结果里没写授权了哪些动作），照常建工作区、派 PM，才被拦下："批准清单没有实施授权"。
- 问题二：需求生效后再补"实施"，程序没有专门的做法，只能重新批准。重新批准要解读模型把整份需求逐段重新分类（一份需求常有十几到二十段），只要有一处分类不合规就整次失败，用户的原话也跟着作废。用户只想加一个"实施"，需求内容一点没问题，却要碰运气。
- 实际发生过：2026-11-09 到 11-10，Codex5x 项目批准第 15 版后派 PM 被拦。用户三次说"授权实施第 15 版需求"：第一次主代理没去登记，直接又派 PM；第二次重新批准时解读模型的回答格式不合规；第三次重审时把一个段落分错了类。三次都没登记上，PM 一直没派出去。

## 目标
- 用户批准需求时就知道可以顺便授权实施；批准后没授权实施时，主代理第一时间告诉用户，不先去派 PM 再碰壁。
- 需求生效后，用户说一句"授权实施"就能补上实施授权：程序只判断这句话有没有授权实施，不重审需求正文。

## 非目标
- 补授权实施以外的动作（分析、规划、提交、推送）：现在程序只检查实施，补了别的也不起作用。
- 批准新版本时沿用上一版的实施授权：会违反威胁模型"旧流程与旧记录不产生授权"，每批准一版都要在原话里说实施，忘了就补授权。
- 撤销已经给出的实施授权。
- 改"批准不等于实施，每种动作都要原话明确说出"这条解读规则。
- 改现有的批准需求确认窗口。
- 草稿有未批准修改时补授权：这时要把新版本连同"实施"一起批准。

## 依赖与交付顺序
01 → 02：02 的成功结果和 01 的批准结果用同一种写法告诉主代理有没有授权实施，01 先定下这个写法；01 里派 PM 被拒时的建议指向 02 的补授权。

## 整体验证路径
1. 主代理整理好一份需求草稿、请用户批准 → 主代理的回复里提醒：批准后要直接开始实施，可以在同一句话里说"批准并开始实施"。
2. 用户只说"批准这一版"（@ 到这个需求） → 需求生效；批准结果写明没有授权实施；主代理告诉用户需求已生效、还没授权实施，要开始实施就说"授权实施"；主代理没有建工作区、没有派 PM。
3. 用户说"授权实施"（没有 @ 到需求） → 弹出"授权实施"确认窗口，写着需求名、已批准的第几版；用户选确认 → 登记成功，批准清单里各段落的确认情况和补授权前一样，多了"实施"。
4. 主代理接着建工作区并派 PM → PM 派出成功，不再报"批准清单没有实施授权"。
5. 用户改了需求、只说"批准这一版"批准新版本 → 新版本的批准清单里没有实施，主代理告诉用户还没授权实施；用户说"批准并开始实施"批准下一个新版本时 → 清单里有实施。

## 决策记录
- 质疑结论：只做提醒能减少用户忘说"实施"，但忘了之后照样补不上，所以补授权省不掉；两条放进同一份需求一起做。用户 2026-11-10 决定。
- 补授权只补"实施"，不做五种动作都能补：现在只有派 PM 和 PM 规划检查实施，其他动作补了不起作用。用户 2026-11-10 决定。
- 批准新版本时不沿用上一版的实施授权：守住威胁模型"旧流程与旧记录不产生授权"；否掉"自动沿用"，因为要改威胁模型。用户 2026-11-10 决定。
- 只在草稿没有未批准修改时允许补授权：否掉"只要需求生效就能补"，因为草稿改过后，用户容易以为授权的是正在改的草稿，实际作用在已批准的旧版本上。用户 2026-11-10 决定。
- 没有 @ 到需求时弹"授权实施"确认窗口，请用户亲手确认是哪个需求：和批准时一样，不让模型自己填需求编号；否掉"只认 @ 到需求的原话"，因为用户要多说一遍。窗口沿用批准需求窗口的样子，只换标题和内容，原型经用户 2026-11-10 确认。
- 提醒由主代理在请用户批准时说一句，批准结果写明有没有授权实施；否掉"在批准窗口里也提示"，因为用户 @ 到需求时不弹窗，提示不一定看得到，还要改界面。用户 2026-11-10 决定。
- 原话没明确说要实施时不登记、说明原因：否掉"主代理发起补授权就算数"，因为那等于让模型替用户做决定，违反威胁模型"模型输出不可信"。用户 2026-11-10 决定。
- 已经授权过实施时直接告诉主代理"已授权"，不弹窗、不重复登记。用户 2026-11-10 决定。
- 补授权成功后主代理照规矩直接建工作区（已建就跳过）并派 PM，不再问用户要不要开始：用户说授权实施就是想开工。用户 2026-11-10 决定。
- 补授权给批准清单的存储行加一个可选的补授权记录、给需求事件加一种"已补授权实施"，数据库版本号不升、不写迁移：旧数据在新格式下原样合法，代码只认一种格式，不存在要转换的数据，也不存在新旧两套写法；否掉"升版本并写空迁移"，因为每个用户每个项目都要确认一次不做任何转换的迁移。这是对 AGENTS.md"数据格式变了就升数据库版本号"的有意偏离，用户 2026-11-10 决定。
- 这次不建 DESIGN.md（项目的设计规范文件），原型照 pi 深色主题和现有确认窗口的代码画：只换标题和文字，不涉及新颜色和字号；另一个分支正在起草 DESIGN.md，避免冲突。用户 2026-11-10 决定。
