# 检索结果只给结论，按编号取来源

explore 是只读的检索代理，主代理或 PM 派它去查代码或联网查资料。它交回的报告叫检索结果，内容有结论、来源（联网是链接加摘录，本地是文件加起止行）、搜索范围（搜过的词或读过的文件）、没查到的事、没核实的事、失败、截断说明。运行编号是程序在派出时生成的编号，派出时就返回给派出方。

## 用户故事

### P0：作为主代理，我想要检索结果只给结论和可信度说明，以便不用为每份检索读进几千 token 的来源摘录

**用例（主路径）**
- 场景：用户问"ChatGPT 桌面应用里的 Codex 怎么接入自定义模型"，主代理派了一次联网 explore，explore 交回 6 条结论、8 条来源、9 个搜索词、2 条没查到、3 条没核实，网页有截断。
- 操作：检索结果送达主窗口。
- 预期：发给主代理的这条消息里有运行编号、成败、用了几轮、6 条结论全文、2 条没查到、3 条没核实、失败、截断与原因、来源条数 8；没有来源摘录、链接、搜索词、派出方信息、格式字段。完整报告存在这条消息的 `details` 里。

### P0：作为主代理，我想要按运行编号取到来源，以便把结论当依据前核对

**用例（主路径）**
- 场景：上面那份检索的第 2 条结论要写进需求草稿。
- 操作：主代理用 agent_manage 按运行编号取来源。
- 预期：返回这份检索的全部 8 条来源（链接和摘录）和搜索范围，和完整报告里的一致。主代理核对后再调 updateDraft。

**用例（边界 / 异常）**
- 场景：主代理给了一个本会话里没有的运行编号（另一个会话派的，或编号写错）。
- 操作：按这个编号取来源。
- 预期：工具失败，原因写"本会话里没有这个编号的检索结果"。
- 场景：主窗口关掉重开、守护进程重启之后，接着原来的会话。
- 操作：按之前的运行编号取来源。
- 预期：照样取到。

### P0：作为 PM，我想要和主代理一样只收到结论，需要时按编号取来源

**用例（主路径）**
- 场景：PM 在接手复核阶段派了一次本地 explore。
- 操作：检索结束，结果送到 PM。
- 预期：PM 收到的内容和主代理那边规则相同（运行编号、成败、轮数、结论、没查到、没核实、失败、截断、来源条数），没有来源摘录和搜索范围。PM 用 agent_manage 按这个运行编号能取到全部来源和搜索范围；守护进程重启后也能取到。

**用例（边界 / 异常）**
- 场景：PM 按一个不是本需求派出的检索运行编号取来源。
- 操作：调用取来源。
- 预期：工具失败，原因写"本需求没有派出过这个编号的检索"。

### P1：作为主代理或 PM，我想要检索没交结果时照旧拿到原因和日志

**用例（边界 / 异常）**
- 场景：explore 用完轮次上限也没交结果。
- 操作：结果送达。
- 预期：内容和现在一样：运行编号、成败、原因、下一步建议、运行日志路径。

## 约束

1. 检索交了结果时，发给主代理的内容包含：运行编号、成败、已用轮数、全部结论、没查到、没核实、失败、是否截断及原因、来源条数；不包含：来源的链接 / 路径 / 摘录 / 起止行 / 文件哈希 / 抓取时间、搜索范围、派出方信息（parent）、检索输入来源（source）、格式字段（format、kind）。
2. 检索交了结果时，发给主代理的内容里写明怎么用：结论要写进需求草稿，或当作回答用户的依据时，先按运行编号取来源核对；只用来决定下一步再查什么时不用取。
3. 主代理收到的检索结果消息的 `details` 存着完整报告，不发给模型。
4. one_company_agent_manage 有一个按运行编号取检索来源的动作：编号是本会话当前分支里收到过的检索结果时，返回该报告的全部来源和搜索范围；否则失败，原因写"本会话里没有这个编号的检索结果"。
5. 窗口重开、守护进程重启后，按约束 4 取同一个运行编号，结果和重启前相同。
6. PM 收到的检索结果按约束 1、2 的同一规则组成（"写进需求草稿"换成"写进计划或任务"）。
7. PM 的 agent_manage 有按运行编号取检索来源的动作：编号是本需求下派出的检索时，返回全部来源和搜索范围；否则失败，原因写"本需求没有派出过这个编号的检索"。守护进程重启后结果不变。
8. 检索没交结果时，发给主代理和 PM 的内容与现在相同：运行编号、成败、原因、下一步建议、运行日志路径。
9. 主代理规矩（`rules/01-main-session.md` 第 7 条）和 PM 规矩（`role-rules/pm.md` 核对子代理结果那条）里，检索结果的用法写成约束 2 的写法：要当依据时先按运行编号取来源核对。

## 验收

- [ ] 1：用一份含 6 条结论、8 条来源、9 个搜索词的报告送达主窗口，发给模型的内容含上述必含字段、来源条数为 8，不含任何来源链接、摘录、搜索词、parent、format。
- [ ] 2：同上，发给模型的内容里有"写进需求草稿或当作回答依据前先按运行编号取来源核对"的说明。
- [ ] 3：同上，这条消息的 `details` 与守护进程交出的完整报告逐字段相同。
- [ ] 4：按该运行编号取来源，返回 8 条来源和搜索范围，与完整报告一致；按一个不存在的编号取，失败且原因是"本会话里没有这个编号的检索结果"。
- [ ] 5：重启守护进程、重新加载会话后，按同一编号取来源，结果不变。
- [ ] 6：PM 派的检索结束后，PM 收到的内容含必含字段、不含来源摘录和搜索范围，并写明"写进计划或任务前先取来源核对"。
- [ ] 7：PM 按本需求派出的检索编号取到全部来源；守护进程重启后仍能取到；按别的需求的检索编号取，失败且原因是"本需求没有派出过这个编号的检索"。
- [ ] 8：检索用完轮次没交结果时，主代理和 PM 收到的内容含运行编号、成败、原因、下一步建议、运行日志路径，与改前相同。
- [ ] 9：两份规矩文件里讲检索结果用法的那条，写的是"要当依据时先按运行编号取来源核对"。
- [ ] 主路径：真实模型验收中，主代理派 explore 并把结论写进草稿，会话记录里能看到先取来源、后 updateDraft。

## 验证路径

1. 用测试素材让守护进程交出一份固定的检索报告 → 检查主窗口收到的消息：发给模型的部分只有约束 1 的字段，`details` 是完整报告。
2. 调 agent_manage 按运行编号取来源 → 返回与完整报告一致；换一个不存在的编号 → 失败原因正确。
3. 重启守护进程、重新加载会话 → 再取一次，结果不变。
4. 让 PM 派一次检索 → 检查 PM 收到的提示词只有约束 1 的字段；PM 按编号取来源成功，按别的需求的编号失败。
5. 让检索用完轮次 → 主代理和 PM 收到的内容与改前一致。
