# 工具结果只发必要内容，主窗口卡片简短显示

## 背景与问题

主代理（用户在 pi 主窗口里对话的那个模型会话）和后台子代理（PM、worker、reviewer、qa、explore、原型设计师）每调一次本项目的工具，程序都把整份结果对象转成 JSON 发给模型。结果里有大量模型从不使用的字段：提交号、各种哈希、`epoch`、内部操作编号、为 0 的计数、逐个文件的跳过清单和诊断清单。检索代理 explore 交回的报告更大：主代理和 PM 每收到一份，都要整份读进上下文，包括每条来源的摘录和整张搜索词清单。

实测（本机近 30 天的 pi 会话记录）：
- 一份 explore 报告平均 7,020 字，约占 2,650 token；同一会话收到 3 份就占约 8,000 token。
- 主代理的工具结果共 289 次，单次平均约 400 字，其中哈希这类长串占了相当一部分。
- 一次什么都没查到的知识查询，结果里仍有约 700 字的固定表头（工作区哈希、索引基线哈希、一串为 0 的计数）。

同时，主窗口把这些结果整段显示成 JSON，调用行也直接显示原始参数 `request={...}`，用户一眼看不出刚发生了什么。

## 目标

- 每个工具结果、每份检索结果，发给模型的内容只留模型下一步用得上的部分；完整结果仍然留存，程序、界面和测试照常可用，模型需要时按编号取。
- 一份 explore 报告发给主代理或 PM 的内容，比现在少一半以上（以同一份报告比较字数）。
- 主窗口里所有 one_company 工具和检索结果都显示成"标题行 + 一两行摘要"，按展开键看完整内容。

## 非目标

- 不改 pi 自带工具（read、bash、grep、find、ls 等）的结果和显示。
- 不改子代理交结果工具（result_submit）成功时的返回：交成功后会话下一轮就结束，返回内容不会再进模型。
- 不改工具失败时发给模型的报错文字（"X 失败。原因：…建议：…"三段），只改它在主窗口的显示。
- 不改后台步骤窗口的显示：它只显示工具参数和成败，不显示结果。
- 不改窗口和守护进程之间的通信格式，不升协议版本号。
- 不缩减系统提示词和工具说明本身占的上下文。
- 不改 pi 主题的颜色。

## 依赖与交付顺序

{01, 02 可并行} → 03。03 的摘要和展开内容要用 01、02 留存下来的完整结果。

分两批交付：主代理的 requirement_manage、user_interact 两个工具的精简（02 表里这两个工具的各行），以及接手复核（pm-intake）卡片，等另一个需求（requirement-follows-conversation，改需求存储）合并、本分支同步后再做；其余部分先做。

## 整体验证路径

1. 在一个样例项目里打开 pi 主窗口，让主代理派一次联网 explore → 检索结果送达时，主窗口出现一张"检索结果"卡片，两行内写完各项条数和编号前 8 位；会话记录里这条消息发给模型的内容有结论、没查到、没核实，没有来源摘录和搜索词清单。
2. 让主代理把检索结论写进需求草稿 → 主代理先调 agent_manage 按运行编号取来源，取到的来源和完整报告里的一致，然后才调 updateDraft。
3. 主代理新建需求、修改草稿、读需求、查需求状态 → 每次工具结果发给模型的内容里没有 commit、prdHash、epoch；主窗口每张卡片收起时不超过 3 行，按 Ctrl+O 能看到调用参数和完整结果。
4. 批准需求、派 PM，PM 派 explore 并写计划、派 worker → PM 收到的检索结果和主代理一样只有结论；worker 的验证命令结果里仍有退出码和输出；子代理的知识查询结果里没有工作区哈希和索引基线哈希。
5. 故意让一个工具失败（比如确认一个已经通过的原型） → 主窗口卡片显示标题行加一行红字"失败：原因"；发给模型的报错文字和改前一样。

## 决策记录

- **三项一起做，子代理工具也纳入**（用户 2026-11-10 决定）：问题的根子是"程序内部的结果对象原样发给模型"，主代理工具、子代理工具、知识查询、检索结果都是同一个毛病，只修主代理一侧或只修检索结果都会留下另一套写法。被否决：只改检索结果（省得最多但工具噪音还在）；知识查询不动（每次查询都带约 700 字固定表头，子代理用得比主代理多）。
- **发给模型的内容只留五样**（用户 2026-11-10 决定）：要回填到其他工具参数的编号和版本、提示词点名的字段、写给模型的下一步说明（next、reason、blockedBy 等）、正文和回答本身、状态。其余字段只放在不发给模型的位置（pi 工具结果和自定义消息的 `details`），界面、程序核对和测试照常用。判断依据是对代码和提示词逐字段的盘点，而不是凭感觉删。被否决：只删哈希和提交号（改动小但省得少，逐文件清单这类噪音还在）。
- **找不到使用证据、但主代理可能要转告用户的字段照留**（用户 2026-11-10 决定）：交付的 PR 链接、需求工作区的分支和目录、原型每版的说明、需求未确认段落清单。
- **检索结果只给结论 + 没查到 + 没核实 + 编号**（用户 2026-11-10 决定）：主代理靠结论判断下一步，靠"没查到 / 没核实"判断能信多少，这两样不能少。被否决：只留结论和编号（容易把没查实的事当成事实）。
- **完整检索报告存在会话消息里，按编号取**（用户 2026-11-10 决定）：主代理那边存进检索结果消息的 `details`，跟着会话记录走，窗口重开、守护进程重启都还在，只有新开会话后取不到。被否决：留在守护进程内存里（空闲 10 分钟退出或被换新后就没了）。PM 那边从该次检索运行的记录里取。
- **要当依据时才取来源核对**（用户 2026-11-10 决定）：检索结果是模型输出，按威胁模型不可信。结论要写进需求草稿、计划、任务，或者当作回答用户的依据时，必须先按编号取来源核对；只用来决定下一步再查什么时不取。被否决：使用前一律核对（主代理几乎每次都会去取，省不下上下文）。
- **PM 收到的检索结果和主代理同样处理**（用户 2026-11-10 决定）：同一种结果用同一套规则。
- **分页上限按发给模型的内容算**（用户 2026-11-10 决定）：上限的数值不变，本来就是保护模型输入大小的；精简后哈希等字段不再占名额，每页能多放正文。
- **主窗口所有 one_company 工具和检索结果都换成简短卡片**（用户 2026-11-10 决定）：照现有「提问」卡片的样子统一，而不是只修截图里那几张。展开键显示调用参数和完整结果，方便排查；失败时一行红字写原因，建议是写给模型的，按展开键看。
- **检索卡片只写条数**（用户 2026-11-10 决定）：界面不显示结论正文，结论给模型看；用户想看全文按展开键。
- **新增 DESIGN.md**（用户 2026-11-10 决定）：项目之前没有设计规范，这次按现有终端界面起草并写入项目根目录；pi 主题里 muted、accent、error、浅色 success、dim 对卡片底色对比度不到 4.5:1，颜色由 pi 决定、项目改不了，记为例外；对话卡片里的文字不用对比度最低的 dim。
- **总规则写进 AGENTS.md「产品设计原则」**（用户 2026-11-10 决定）：删掉本次功能后这条规则仍然成立，以后新加的工具也要照做。
- **分两批做**（用户 2026-11-10 决定）：另一个进行中的需求 requirement-follows-conversation 要改需求存储和需求工具的结果，和本需求在主代理需求工具上重叠。需求工具的结果形状只定一次，所以这两个工具的精简等对方合并后再做，其余先做。被否决：全部等对方合并（要等对方 9 步做完）；两边并行再解冲突（需求工具部分大概率要按对方的新结果重做一遍）。
- **PM 的检索完整报告存进本机数据库**（用户 2026-11-10 决定）：守护进程重启后还要能按编号取来源，运行记录里没有结果字段、会话日志里只有模型交的原文缺程序补的路径和哈希，都不可靠；新加一种记录，不动已有记录的格式，所以不升数据库版本号、不写迁移；需求关闭后不删，每份只有几 KB。
- **新增真实模型单点验收 P24**（用户 2026-11-10 决定）："要当依据时先按编号取来源"靠提示词约束模型，只有真实模型跑过才知道它照不照做；AGENTS.md 里的单点测试范围随之改成 P1–P24。编号用 P24：main 上的 P22、P23 已是授权实施的两条验收，两边同号时 `--only P22` 会选中两条不相干的验收。
- **联网搜索结果照旧带取回时间**（用户 2026-11-10 决定）：检索代理引用网页来源时必须填取回时间，只引用搜索摘要时只能从 web_search 结果里抄，去掉后模型只能自己编；搜索命中项本来就只有链接、标题、摘要，所以 web_search 发给模型的内容不变。
- **结果里写给模型的下一步说明一律保留**（2026-11-10 写计划时发现）：关闭需求时归档卡住的 reason、next，交付时合并是否成功及其 reason、next，原先的表漏了，按总规则补回。
- **一行放不下时先截长短不定的文字，计数和状态保留**（用户 2026-11-10 决定）：卡片整行从右边截时，原型状态卡片行尾的"还有 K 个原型"、交付检查卡片的"共 N 项"最先被截掉，用户看不出后面还有几项。原型状态那一行在原型名和状态里截较长的那段：名字很长时截名字，状态（如"第 3 版等你确认"）照常显示；没交稿原因很长时截原因。被否决：只保住行尾计数、名字和状态一起截（名字很长时状态被截掉，而状态才是看这张卡片要知道的）。
- **初始化、刷新索引卡片不写"有截断"**（用户 2026-11-10 决定）：这个标记来自工具结果里的清单为了不超上限被删掉了几条，不是索引没建全，用户容易看错；卡片上的文件数、跳过数在删减前就数好了，删减不影响卡片上的任何数字，展开后仍能看到删减信息。被否决：改写成"结果清单有删减"（准确，但用户用不上）。
