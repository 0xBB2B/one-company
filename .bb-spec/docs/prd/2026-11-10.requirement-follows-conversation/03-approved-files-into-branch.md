# 批准开工后文件进需求分支

本文用到的词：

- 需求分支：需求批准后，程序在用户的业务仓库里给它开的独立分支 `req/<需求编号>`，在这个需求自己的工作区（worktree，一个单独的检出目录）里检出。PM 和 worker 在这里改代码，交付时合并进主仓库。
- 批准的文件：批准的那一版需求正文、批准时通过的原型、这条线上已通过的 DESIGN.md、写进草稿的 AGENTS.md。
- 底稿：设计师开工时读到的 DESIGN.md，或主代理修改时作对比的 AGENTS.md。

## 用户故事

### P0：作为用户，我想让批准的需求文件跟着需求分支走，以便没合并之前主仓库不被改动，合并时一起进去

**用例（主路径）**
- 场景：「订单导出」在一条线上通过了一份原型（带改过的 DESIGN.md），草稿里还改了 AGENTS.md。
- 操作：用户批准需求，主代理建好工作区。
- 预期：需求分支上多出一个提交，里面有需求正文、原型、DESIGN.md、AGENTS.md；主仓库根目录的 DESIGN.md、AGENTS.md 字节不变。之后派出的 PM、worker、reviewer 拿到的 DESIGN.md、AGENTS.md 是需求分支里的。

**用例（先建工作区后批准）**
- 场景：工作区已经建好，需求还没批准。
- 操作：批准需求。
- 预期：批准成功的同时，需求分支上多出一个包含批准文件的提交。

**用例（别人改过、能合上）**
- 场景：设计师开工后，主仓库里的 DESIGN.md「颜色」一章被别人改了，这次原型只改了「组件」一章。
- 操作：批准需求、建好工作区。
- 预期：需求分支里的 DESIGN.md 同时带着别人改的「颜色」和这次改的「组件」。

**用例（别人改过、合不上）**
- 场景：别人和这次原型都改了 DESIGN.md「颜色」一章的同一处。
- 操作：批准需求（工作区已建好）。
- 预期：批准不生效，需求保持草稿；主代理告诉用户 DESIGN.md 的「颜色」一章冲突，建议让设计师按最新的 DESIGN.md 重做一版再批准。

## 约束

1. 需求已批准、工作区也建好时，程序把批准的文件提交进需求分支，作为一个提交。这两个条件谁后满足，就在那一步（批准或建工作区）里提交。
2. 以后每批准一个新版本，再提交一次，需求分支里的这些文件换成新批准版本的内容。
3. 需求正文放在需求分支的 `docs/prd/<需求编号>.<需求标题>.md`，原型放在 `docs/prd/<需求编号>.<原型名称>.html`，DESIGN.md、AGENTS.md 放在需求分支的根目录。新批准的版本改了标题或去掉了某份原型时，旧文件名的文件从分支里删掉。
4. 这次没改的文件不提交：没改 DESIGN.md 时不动分支里的 DESIGN.md，没改 AGENTS.md 时不动分支里的 AGENTS.md。
5. 提交前，分支里的 DESIGN.md 或 AGENTS.md 和底稿不同（被别人改过）时，只把这次相对底稿的改动合进分支里的现有内容，别人的改动保留。
6. 同一处两边都改了、合不上时，这些文件一个都不提交，这一步（批准或建工作区）整体不生效；给主代理的结果写明哪个文件哪一章冲突，建议下一步怎么做。
7. 需求批准前，主仓库根目录和需求分支里的 DESIGN.md、AGENTS.md 都不会因为这个需求而改变。
8. 一个需求派出的 PM、worker、reviewer、qa，拿到的 DESIGN.md、AGENTS.md 来自这个需求的需求分支，不来自主仓库根目录。
9. "确认原型"窗口里关于 DESIGN.md 的那一行，只改这一行，窗口其余内容不变：
   - 要新建 DESIGN.md 时：`批准需求后随需求分支新建 DESIGN.md，之后这个需求的原型、实现和审查都照它做。`
   - 要更新 DESIGN.md 时：`批准需求后随需求分支更新 DESIGN.md：<改了哪几章>。`，有多个方案时第二行按方案列出各改了哪几章，格式和现在一样。
10. 需求以完成关闭时，归档照旧写进需求分支的同一个位置（约束 3 的路径），内容换成最终批准的正文加实现记录。

## 验收

- [ ] 约束 1：先批准后建工作区、先建工作区后批准两种顺序，需求分支上都正好多出一个含批准文件的提交。
- [ ] 约束 2：批准新版本后，需求分支上再多一个提交，文件内容是新版本的。
- [ ] 约束 3：正文、原型、DESIGN.md、AGENTS.md 都在规定路径；新版本改了标题后，旧标题的正文文件不在分支里了。
- [ ] 约束 4：只改了正文的批准，提交里不含 DESIGN.md、AGENTS.md 的改动。
- [ ] 约束 5：别人改「颜色」、这次改「组件」，分支里的 DESIGN.md 两处改动都在。
- [ ] 约束 6：两边改同一处时，批准不生效、需求仍是草稿、分支上没有新提交，结果里写明 DESIGN.md 和冲突的章名。
- [ ] 约束 7：批准前通过原型、改 AGENTS.md，主仓库根目录和需求分支里这两个文件字节不变。
- [ ] 约束 8：主仓库根目录和需求分支里的 DESIGN.md 内容不同时，派出的 worker 任务说明里的 DESIGN.md 是需求分支里的。
- [ ] 约束 9：分别在新建、更新、多方案更新三种情况下打开"确认原型"窗口，那一行文字和上面一字不差，其余行和现在相同。
- [ ] 约束 10：完成关闭后，需求分支 `docs/prd/<需求编号>.<需求标题>.md` 的内容是最终正文加实现记录。

## 验证路径

1. 在草稿里通过一份改了 DESIGN.md 的原型、改一次 AGENTS.md → 主仓库根目录两个文件都没变。
2. 批准需求，建工作区 → `git log req/<需求编号>` 能看到一个新提交，含正文、原型、DESIGN.md、AGENTS.md；主仓库根目录仍没变。
3. 派出 PM，再由 PM 派出 worker → worker 任务说明里的 DESIGN.md 是需求分支里的那份。
4. 在主仓库里改 DESIGN.md 某一章的同一处，再让需求改同一处并批准新版本 → 批准不生效，主代理说明冲突的章名。
