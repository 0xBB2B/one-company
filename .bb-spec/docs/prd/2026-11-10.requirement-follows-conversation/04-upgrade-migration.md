# 升级时迁移现有草稿

本文用到的词：

- 迁移框：本机数据库的版本比当前代码要求的旧、当前代码又能转换时，pi 窗口在后台进程启动前弹出的确认框；用户选「迁移」后，程序先备份 data.db，再在一次事务里把旧数据转成新格式，失败时库保持原样。
- 跟线内容：草稿需求要跟着对话线走的全部内容，包括标题、正文、简介、短决定、待答提问、批准清单、原型看板和原型文件，以及草稿有没有被取消。
- 对话线：pi 主会话里从对话开头走到当前位置的那一条路线。

## 用户故事

### P0：作为已经在用 one-company 的用户，我想升级后手头的草稿一样不丢，以便接着写

**用例（主路径）**
- 场景：升级前有草稿「订单导出」，版本 7，有 4 条短决定、1 个没回答的提问、1 份通过的原型。
- 操作：升级后打开 pi，在迁移框里选「迁移」。
- 预期：迁移完成后读取「订单导出」，仍是版本 7，4 条短决定、1 个提问、1 份原型都在，内容和升级前一样。

**用例（旧对话回退）**
- 场景：升级前的对话里，「订单导出」曾经保存到版本 3、5、7。
- 操作：升级迁移后，在这个旧对话里回到版本 5 那一步。
- 预期：「订单导出」仍是版本 7，不插"已恢复"消息；在这一步保存后，这条线有了自己的版本。

**用例（迁移失败）**
- 场景：迁移中途出错。
- 操作：选「迁移」。
- 预期：库保持迁移前的样子，迁移框说明失败原因。

## 约束

1. 升级后第一次打开窗口时，本机库是旧版本的，就弹出迁移框；用户不选「迁移」，后台进程不启动。
2. 迁移后，每个草稿需求的跟线内容和迁移前逐项相同，版本号相同。
3. 迁移后，草稿的跟线内容只存在数据根目录 `repos/<仓库>/` 下 one-company 自己的 Git 里，本机数据库里查不到。
4. 已批准、正在关闭、已关闭的需求，迁移前后内容和状态都不变。
5. 主仓库根目录已有的 DESIGN.md、AGENTS.md，迁移不改动。
6. 升级前的对话回退到升级前的某个保存点时，算作"这条线上没保存过"，用这个需求最近保存的那一份。
7. 迁移失败时库保持迁移前的样子，迁移框写明哪一步失败、为什么。
8. 迁移框里列出迁移会丢掉的数据；没有会丢的数据时写明"不会丢数据"。

## 验收

- [ ] 约束 1：用旧版本的库启动，弹出迁移框；选不迁移时后台进程没启动。
- [ ] 约束 2：迁移前后对同一个草稿需求读取标题、正文、简介、短决定、提问、批准清单、原型，逐项相同，版本号相同。
- [ ] 约束 3：迁移后本机数据库里查不到草稿的跟线内容，one-company 的 Git 里能读到。
- [ ] 约束 4：迁移前后已批准、正在关闭、已关闭需求的记录逐项相同。
- [ ] 约束 5：迁移前后主仓库根目录的 DESIGN.md、AGENTS.md 字节不变。
- [ ] 约束 6：旧对话里回到升级前的版本 5 那一步，需求仍是最近保存的版本 7，不插消息。
- [ ] 约束 7：让迁移中途失败，库和迁移前字节相同，迁移框写明失败的步骤和原因。
- [ ] 约束 8：迁移框里有"会丢掉的数据"这一项。

## 验证路径

1. 在旧版本里建两个草稿需求，各保存几版、做几条短决定、通过一份原型；再批准其中一个。
2. 升级，打开 pi → 弹出迁移框，选「迁移」。
3. 读取两个需求 → 草稿那个内容和升级前一样，批准那个状态和内容都没变。
4. 在升级前的旧对话里回到较早的保存点 → 需求仍是最近保存的版本，不插消息。
