# 需求跟着对话走

## 背景与问题

用户在 pi 的主会话里和主代理（用户正在对话的那个 pi 会话）一起写需求。pi 的对话可以从中间某一步岔开：按两次 Esc 或用 `/tree` 回到某一步再说话，就多出一条新路线；用 `/fork` 从某一步另开一个对话；用 `/resume` 或启动时的 `pi -c`、`pi --session` 打开另一个旧对话。从对话开头走到当前位置的这一条路线，本文叫"对话线"。

现在程序只认一条直线：需求草稿每保存一次，就在需求自己的 Git 仓库里接一个提交，数据库只记最新那一版。对话线一换，数据却不跟着换。典型场景：

- 用户把需求文档改了 10 版，发现第 5 版更好，按 Esc 回到第 5 版那一步接着说。主代理看到的对话停在第 5 版，库里却是第 10 版。主代理照对话里的版本号保存会被拒，重新读一遍后，就在第 10 版上接着改，用户"回到第 5 版"的意思丢了。
- 第 6 到 10 版对话里做的决定（程序归纳成一句话存下来的"短决定"）还算数，批准时会被引用，等于用户已经放弃的那段对话在给批准作依据。
- 原型、待用户回答的提问也停在第 10 版那条线上。
- 用户之后想切回第 10 版那条线，也没有办法让数据跟回去。

另外，DESIGN.md（界面设计规范）在用户通过原型时就直接写进主仓库根目录，AGENTS.md（项目规范）在用户选"写入"时也直接写进主仓库根目录。这两个文件都还没经过需求批准，就已经落在用户的仓库里了，对话回退也改不回去。

## 目标

- 批准前，主窗口对话里产生的需求内容跟着 pi 的对话线走：换到哪条线，窗口里的需求就是那条线上的样子；换回原来的线，原来的样子原样还在。
- 主代理看到的版本号和程序认的版本号始终一致，回退以后照对话里的版本号保存不会被拒。
- 需求批准、开工以后，需求正文、原型、DESIGN.md、AGENTS.md 进入需求分支，由用户项目的 Git 管理，随需求交付合并进主仓库。

## 非目标

- 已批准的需求不跟着对话线走，包括批准后又在改的修订草稿。
- 后台代理干出来的东西不跟着对话线走：PM 的计划和任务、worker 的改动、审查结论、检查轮、验证输出、提交、推送、PR。它们已经写进真实的工作区或远程仓库，撤不回来。
- 和对话无关的数据不跟着对话线走：设置页里的模型和开关、项目授信、项目索引、守护进程凭证、Shell 登记、日志、备份。
- PM 接手复核、⚑ 事项裁决这些批准以后的流程，这次不改。
- 仓库里已经存在的 AGENTS.md、DESIGN.md，升级时不改动。
- 升级前的对话不能回退到升级前保存的旧版本。
- 给从没批准过的草稿加"取消"入口。

## 整体验证路径

1. 升级到新版本，打开 pi 窗口 → 弹出迁移框，选"迁移" → 原有草稿需求的正文、短决定、原型都还在，内容和升级前一样。
2. 新开一个对话，和主代理一起建需求「订单导出」，连续保存到版本 10，中间做过几条短决定、通过一份原型（带 DESIGN.md）。
3. 按两次 Esc 回到版本 5 那一步 → 对话最后插入一条消息"「订单导出」已恢复至版本 5"；读取需求，正文是版本 5 的正文，版本 6 之后做的短决定不算数，原型回到版本 5 时的样子；主代理照版本 5 保存一次，成功，这条线上成了版本 6。
4. 用 `/tree` 切回版本 10 那条线 → 插入"「订单导出」已恢复至版本 10"；正文、短决定、原型都和第 2 步结束时一样。
5. 在版本 10 这条线上批准需求，建好工作区 → 需求分支上多出一个提交，里面有批准的正文、原型、DESIGN.md；主仓库根目录的 DESIGN.md 没有被改动。
6. 再回到版本 5 那条线 → 插入"「订单导出」已批准，以库里的版本 10 为准"，需求保持已批准。

## 决策记录

- 跟着对话线走的范围：只管批准前、主窗口对话里产生、只存在本机的内容；后台代理的产出和与对话无关的数据都不跟（用户 2026-11-10 决定）。原因：后台代理的产出已经写进真实工作区或远程仓库，撤不回；设置跟着对话走会让人意外，回退一下模型就变回去了。
- 数据的分工：数据库只存运行中的中间状态，例如任务状态、各代理之间的关系和进度，以及短决定、提问这类用户和主代理之间的过程记录；需求正文、原型、DESIGN.md、AGENTS.md 这类文件内容，批准前放在 one-company 自己的 Git 里跟着对话线走，批准开工后放进需求分支由用户项目的 Git 管（用户 2026-11-10 提出并决定）。这样分叉和历史交给 Git，产品原则不用改。
- 短决定、待用户回答的提问、连续性事实、批准清单、原型看板、需求简介留在数据库，每条记下它产生在对话的哪一步（锚点），只有锚点在当前对话线上的才算数（用户 2026-11-10 决定）。被否决：挪进 one-company 的 Git。否决原因：批准时证明"每段内容都有用户决定作依据、没被旧记录冒充"的那条依据链，建在同一个数据库事务和记录版本号上，挪进 Git 等于重写并重新验证威胁模型第二条，估时从 2 到 3 周涨到 4 到 6 周；而数据库里只是按锚点筛选，并不分叉。这一条改正了此前"也放进 Git"的决定，那个决定是在没读批准依据链代码时做的。
- 被否决的方案一：回退时把版本 5 的内容另存成版本 11，历史保持一条直线。否决原因：版本号会跳，主代理要另外收到新编号；两个窗口改同一个需求时互相覆盖。这个方案只是把对话树硬转成一条线，没有碰到"对话是树、数据是线"这个根源。
- 被否决的方案二：在数据库里按对话线各存一份当前状态。否决原因：用户提出了更好的分工，把文件内容交给 Git（见上面第二条）。
- 换对话线时自动换，不弹窗确认（用户 2026-11-10 决定）。启动时用 `pi -c`、`pi --session` 接着旧对话，也和 `/resume` 一样处理（用户 2026-11-10 决定）。
- 当前对话线上从没保存过的需求（比如新对话里 @ 一个别的对话写的需求），用最近保存的那一份；在这条线上第一次保存时从那一份分出来（用户 2026-11-10 决定）。被否决：弹窗让用户选从哪条线接着改。否决原因：要新加窗口，而最常见的就是接着最新的改。
- 多个窗口各走各的对话线，互不覆盖（用户 2026-11-10 决定，随数据的分工一起定）。
- 在途原型（设计师还在做、或交了稿还没确认的那一版）在用户切走后照样做完，归派出它的那条线；"确认原型"窗口只在窗口回到那条线时弹出（用户 2026-11-10 决定）。被否决：切走就停掉作废。否决原因：只是切过去看一眼，设计就白做了。
- 已批准的需求不跟着变，只说明一句（用户 2026-11-10 决定）。从没批准过的草稿现在没有取消的入口（取消要先经裁决，裁决要求需求已批准、有 PM 在跑），所以不写"取消后复活"（用户 2026-11-10 决定）。
- 恢复失败时对话照常切过去，这个需求在本窗口里用最近保存的那份，不会只恢复一半；消息写明原因、下一步、运行日志（用户 2026-11-10 决定）。被否决：拦住不让切。否决原因：需求数据坏了的时候，对话也没法回退。
- 插入的消息：已恢复的只写一行"「X」已恢复至版本 N"，已批准的只写一行，只有没能恢复的才展开写原因（用户 2026-11-10 决定）。消息样式用 pi 默认的程序消息样式，这次不建 DESIGN.md（用户 2026-11-10 决定，原因同 2026-11-05：只定文字，不涉及颜色和字号）。
- DESIGN.md 改成批准开工后随需求分支写入（用户 2026-11-10 决定）。被否决：照现在一通过原型就写进主仓库根目录。否决原因：写进去以后对话回退改不回来。被否决：批准时写进主仓库根目录。否决原因：用户后来把批准后的文件统一交给需求分支。
- AGENTS.md 必须跟着某个草稿需求改，跟着它的对话线走，批准开工后随需求分支写入（用户 2026-11-10 决定）。代价：只想改规范时也得建一个需求。被否决：照现在立即写，和需求无关。否决原因：用户要求批准前的文件都跟着对话线走。
- 同一条对话线上后派的原型设计师，照这条线上已通过、还没进分支的 DESIGN.md 画（用户 2026-11-10 决定）。被否决：始终照仓库里的画。否决原因：同一个需求的两份原型都改 DESIGN.md 时会互相覆盖。
- 文件提交进需求分支的时机：需求已批准、工作区也建好，两个条件一齐就提交；以后每批准一个新版本再提交一次（用户 2026-11-10 决定）。被否决：等主代理派出 PM 那一刻才提交。
- 提交进需求分支时，分支里的 DESIGN.md 或 AGENTS.md 已经被别人改过，就只合进这次改的部分；同一处两边都改了就不写，说明冲突在哪（用户 2026-11-10 决定）。被否决：一律停下，会让改了无关章节的情况也被拦住；直接覆盖，会悄悄抹掉别人的改动。
- 升级前就有的对话，回退到升级前的保存点时，算作"这条线上没保存过"，用最近保存的那份（用户 2026-11-10 决定）。被否决：迁移时重建每个历史版本。否决原因：待答提问、原型进行状态当时没按版本记，重建只能靠猜。
- 质疑结论：只让主代理照对话里的旧正文重新保存一次，正文能回去，但短决定还会被批准引用，原型也回不去。所以这个需求值得做。
