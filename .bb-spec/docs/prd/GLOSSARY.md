# 术语表

> 全项目术语唯一权威源，仅 /prd 维护。跨语言 / 跨文档以英文锚点对齐；别名只登记实际用过的语言写法。

| 锚点 | 定义 | 别名 |
|---|---|---|
| role-definition | 一份描述可派工子代理的文件：写明名称、描述、职责、模型、思考等级、skills、mcp 和正文；分内置、用户、项目三层，同名时上层覆盖下层 | 简体「角色定义」 |
| role-rules | 程序按职责（pm、worker、reviewer、qa、explore、prototype）固定加进提示词的流程规矩，放在定义正文之后，优先于正文，用户改不到 | 简体「职责规矩」 |
| definition-body | 角色定义文件里头部设置下面的那段文字，用户在这里写专长和偏好；可以为空 | 简体「定义正文」「正文」 |
| generic-definition | 内置的 worker、reviewer、qa、explore、prototype 这 5 个角色定义，流程离不开它们，不能关闭 | 简体「通用定义」 |
| specialist-definition | 按技术栈划分的角色定义，专项 worker 名为 `<栈>-worker`、专项审查名为 `<栈>-reviewer`，同栈的两个预设同一组 skill；包里内置 Go、Node.js / TypeScript、Python、Java / Spring、Vue、React 六对 | 简体「专项定义」「专项 worker」「专项审查」 |
| spec-example | 仓库 `examples/<栈>/` 下的一套团队设计规范样例，含三类文件：并进用户级或仓库根目录 `AGENTS.md` 的关键设计决定、详细规范 skill、和内置专项定义同名并加挂这些 skill 的角色定义；用户用 `/one:examples` 复制到用户层或项目层后照着改 | 简体「设计规范样例」「规范样例」 |
| definition-switch | 除通用定义外每个角色定义的开启 / 关闭状态，默认开启，在设置页的角色定义列表里按空格切换；关闭的定义 PM 选不到 | 简体「定义开关」 |
| review-round | worker 交出一次改动后，PM 派一次审查时程序同时派出的那一批审查代理：通用审查加上本轮要审的专项审查；返修后再派算下一轮 | 简体「审查轮」「第 N 轮审查」 |
| internal-agent | 程序内部的单次模型调用，不能派工：解释器（把用户原话解读成结构化决定）和草稿核验器（核对需求草稿是不是用户原话要求的） | 简体「内部代理」 |
| settings-page | 输入 /one:setting 打开的页面：左边是目录，右边显示目录里选中分类的内容；管角色定义、PM 和两个内部代理的模型、Git 交付档位和合并方式，以及写错没生效的文件 | 简体「设置页」 |
| project-trust | pi 在 `~/.pi/agent/trust.json` 里给每个项目记的信任决定，从主仓库根目录往上找最近的一条：true 为信任，false 为不信任，没有为空；只有信任时项目层才生效。用户在 pi 的授信弹窗、pi 的 `/trust` 命令里设，或在设置页、`/one:examples` 记录为空时选项目层来设为信任 | 简体「授信记录」「受信任」 |
| settings-layer | 设定和开关的存放层级：用户层对所有项目生效；项目层只对当前项目生效、优先于用户层、项目受信任才生效；都没有时用内置默认值 | 简体「用户层」「项目层」 |
| git-delivery | 主代理调用交付工具，把已完成并归档的需求分支交出去：远程档位推送并建立 PR 或 MR、按用户选的方式合并；仅本地档位在本机合进主仓库当前分支。档位在设置页的「开关」里选，没设置时按 origin 所在主机是否在本机 gh 或 glab 里登录过自动选 | 简体「Git 交付」 |
| delivery-mode | Git 交付的两档：远程（推送需求分支、开 PR 或 MR，在 GitHub 或 GitLab 上合并）和仅本地（在本机把需求分支合进主仓库当前分支，不推送） | 简体「档位」「远程」「仅本地」 |
| merge-method | 需求分支合进目标分支的方式，共三种：压缩合并（所有提交压成一个）、普通合并（保留每个提交，另加一个合并提交）、rebase 合并（保留每个提交，接到目标分支后面成一条直线）；在设置页勾选，远程和仅本地都只用勾了的，压缩合并是推荐方式 | 简体「合并方式」 |
| target-branch | 需求分支最终要合进去的分支：远程档位是 origin 的默认分支（没有 origin 时是主仓库当前检出的分支），仅本地档位是主仓库当前检出的分支；PM 同步、最终检查和交付都对准它 | 简体「目标分支」 |
| requirement-archive | 需求以完成关闭时程序写进需求分支并提交的文件：`docs/prd/<需求编号>.<需求描述>.md`（最终批准的需求正文和实现记录），以及批准过的原型 `docs/prd/<需求编号>.<原型名称>.html` | 简体「归档」「需求归档」 |
| workspace-recycle | 需求关闭后删掉它的 worktree 目录和本地分支；只有把需求分支再合进主仓库当前分支一次不带来任何改动时才放行 | 简体「回收工作区」 |
| code-module | `src/core/<名>/`、`src/modules/<名>/` 下的一个目录，或组装层 `src/app/extension/`、`src/app/daemon/`；放同一个功能的全部源文件，只能引用排在它下面的模块，顺序以架构测试里的清单为准 | 简体「代码模块」 |
| prototype | 一份单个 HTML 文件的界面设计，样式和脚本写在文件里，浏览器直接打开就能看；带名字和版本，用户在程序窗口里通过后写进需求草稿，批准需求时一起批准 | 简体「原型」 |
| prototype-designer | 只负责出原型的子代理职责，只能由主窗口在澄清阶段派出；内置定义名为 prototype | 简体「原型设计师」 |
| in-flight-prototype | 设计师还在做，或已经交稿、用户还没通过或放弃的那一版原型；草稿里有它时不能批准 | 简体「在途原型」 |
| prototype-opinion | 用户在确认原型窗口"其他（自己输入）"一行写的话，可能是提问、要改原型的地方或要改需求的地方；交给主代理先弄清意图再处理，这一版仍在等确认；用户写过意见后主代理才能重派、顶替这一版 | 简体「意见」 |
| prototype-option-list | 原型设计师交稿时附上的一组方案名称（2 到 6 个，每个最多 20 字），按顺序对应原型里画的方案，程序按顺序编字母 A 到 F；有清单时"确认原型"窗口按它列出"方案 A：<名称>"等选项 | 简体「方案清单」 |
| prototype-picked-option | 用户在"确认原型"窗口里选中的那个方案（字母和名称），和通过的那一版原型存在一起；出现在批准需求窗口里，并交给 PM 和它派出的子代理，写明其余方案不做 | 简体「选定方案」 |
| prd | 用户和主代理一起写、经用户批准的需求说明，分背景、需求、功能、实现、验收几个板块，PM 和子代理按它干活 | 简体「需求正文」「PRD」 |
| ask-window | 主代理调用 `one_company_user_interact` 的 ask 动作后程序弹出的选择窗口，需求澄清提问和面板事项提问共用；用户点选某一项时，这一项的标题加理由就是用户这一轮的原话 | 简体「提问窗口」 |
| input-box | 程序窗口里输入行下面显示已输入文字、接收按键的区域：能换行、移动光标；一行太长时不折行，跟着光标左右滚动；行数多时上下滚动并提示上下还有几行；光标移到别的选项后收起成一行；大段粘贴折叠显示；pi 全屏模式下可点击定位光标 | 简体「输入栏」 |
| status-panel | 主会话输入栏下方的区域：每个运行中的需求占一组行，第一行是目标、任务进度（已完成数/总数）和用量；有子代理在跑或有任务级待处理事项时，下面每个任务占一行，审查中的任务再缩进一层列出每个审查代理；没有任务行时写 PM 在做什么；以 ⚑ 开头的行是待处理事项；底部另有主窗口派出的原型设计和检索两组行；需求行、待处理事项行和正在运行的子代理行可以选中，在子代理行上按回车打开步骤窗口 | 简体「状态面板」 |
| pending-item | 状态面板上以 ⚑ 开头、需要用户处理的一行，如待裁决、待验收；用户选中后插入决策包，主代理再针对它发起面板事项提问 | 简体「待处理事项」 |
| operation-id | 程序给每次写入类工具调用生成的 UUIDv7 编号，用来认出同一次操作；中断的操作由程序按内容找回它的编号续完；模型不填写它 | 简体「操作编号」 |
| database-migration | 本机数据库的版本号比当前代码要求的旧、而且当前代码有办法转换时，pi 窗口在守护进程启动前弹框问用户；用户选「迁移」后，程序先备份 data.db，再在一次事务里把旧库转成当前格式（index.db 则删掉重建），失败时库不变 | 简体「迁移」「数据迁移」「迁移框」 |
| maintenance-marker | 备份、恢复、恢复对账开始时程序放在维护目录里的隐藏文件 `.database-maintenance.json`，记着留标记的进程的进程号和启动时间；它存在时别处打开该目录的本机数据库会被拒绝，维护正常结束时删除 | 简体「维护标记」 |
| counting-cycle | 任务的执行次数和被打回次数从哪里开始数：任务创建时开始第 1 个周期，改了计划且满足条件时开始新周期，之前的执行和打回不再计入；每个周期执行最多 2 次、返修 1 次 | 简体「计数周期」 |
| replan-allowance | PM 自己改计划、让已执行过的任务开始新计数周期的机会；用户两次决定之间只有 1 次，用户每做一次决定恢复为 1 | 简体「重算额度」 |
| goal-hold | 已执行过、没完成的任务占着它负责的需求章节：PM 不能取消它，同角色的其他任务不能拿走这些章节，修改它时目标不能减少；只有用户对这个任务选了拆分，或选了调整并批准了新版本，才放开 | 简体「占住目标」 |
| split-request | PM 为待更新且占住目标的已执行任务上报，请用户决定是否让它按当前批准版本拆分；用户可选拆分、不拆或终止 | 简体「请求拆分」 |
| step | 子代理的一次工具调用，例如读一个文件、写入一次改动、跑一条命令；codemode 脚本里调用的工具也各算一步 | 简体「步骤」 |
| step-window | 在状态面板选中正在运行的子代理行、按回车弹出的窗口：按先后列出这个子代理的全部步骤，做完的打 ✓、报错的打 ✗、正在做的转圈，只写每一步做了什么，不显示对话内容；步骤只记在守护进程内存里 | 简体「步骤窗口」 |
| daemon | 每个仓库一个、在后台跑 PM、worker、原型设计师、explore 等代理会话的 Node 进程；同一仓库的多个 pi 窗口共用它，窗口打开时它没在跑就自动拉起；最后一个窗口断开、空闲满 10 分钟、又没有需求在跑时自己退出 | 简体「守护进程」「后台进程」 |
| protocol-version | 窗口和守护进程之间消息格式的编号，格式一变就加 1；握手时两边不同就无法通信 | 简体「协议版本号」「通信版本号」 |
| code-fingerprint | 根据 one-company 安装目录里 `src/`、`resources/` 两个目录下的全部文件和 `package.json` 的内容算出的摘要，其中任何一个文件变了它就变；守护进程启动时的指纹和此刻磁盘上的不同，就算守护进程代码过旧 | 简体「代码指纹」 |
