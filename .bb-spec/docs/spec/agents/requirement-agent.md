# 需求代理

## 目的
让主会话只负责与用户对齐需求，把具体实施交给一个持有完整需求上下文的长期代理。

## 逻辑
主会话在需求文档经用户确认后派出需求代理，派工携带仓库身份、需求身份与工作目录；同一需求同一时间最多一个需求代理。
需求代理读取规范与需求文档，自行或调用规划角色产出任务集，把任务集与工作流形状一并提议给用户确认，确认后执行。
执行时按形状派出角色，或对简单任务自行完成；自行完成的任务同样提交实现交付证据并通过工具核对，不因执行者不同而免检。
需求阶段与任务进度只通过运行信息工具推进，工具按阶段检查校验证据；需求代理不能绕过工具改写状态。
主会话转发的补充需求由需求代理并入当前需求：影响任务集或形状时重新提议，不影响时直接处理。
需求代理在需求完成、被拒绝或被用户停止后结束；结束与阻塞经对话中继通知主会话。需求经提交前审查失败回退到执行阶段时，主会话可重新派出需求代理，新派出的需求代理为新的运行身份。

## 约束
- C-1：当主会话派出需求代理时，系统应要求需求已经用户确认，并绑定仓库身份、需求身份与工作目录；同一需求已有活动需求代理时拒绝再派，返回现有运行身份；需求经提交前审查失败回退到执行阶段且没有活动需求代理时允许重新派出，新运行使用新的运行身份。
- C-2：当需求代理开始工作时，系统应由它完成任务规划并提议任务集与工作流形状，经用户确认后才进入执行；主会话不自行规划。
- C-3：当需求代理执行任务时，系统应允许其按形状派出角色或自行完成简单任务；自行完成的任务须提交与实现角色相同的交付证据并经工具核对，状态推进只经运行信息工具。
- C-4：当主会话转发补充需求时，系统应让需求代理判断影响：改变任务集或形状时重新提议确认，否则并入处理；不得静默扩大范围。
- C-5：如果需求代理结束、被阻塞或需要用户决策，系统应经对话中继通知主会话，不直接在面板内要求用户对话。

## 例子
用户在主窗口确认"订单导出"需求文档后，主会话派出需求代理；需求代理规划出两个任务并提议"任务一由 worker 完成、任务二自行完成、含白盒审查与黑盒验收"，用户确认后开始执行。

## 验收
### AC-1 派出前提与唯一性 ← C-1
- 触发: 操作 对未确认需求派出需求代理，再对已确认需求连续派出两次，最后让该需求经提交前审查失败回退到执行阶段后再派一次
- Given: 两个需求的仓库身份与需求身份明确
- When: 观察四次派工结果
- Then: 未确认需求被拒绝；已确认需求第一次成功并绑定身份与工作目录，第二次返回已有运行身份而不新建；回退后的派出成功且运行身份与此前不同

### AC-2 规划与提议由需求代理完成 ← C-2
- 触发: 操作 派出需求代理并观察其到执行前的动作
- Given: 需求含规范与需求文档，主会话未做任务规划
- When: 需求代理运行至用户确认
- Then: 任务集由需求代理产出，与工作流形状一并提议，用户确认前没有派出实现角色或修改代码

### AC-3 自行完成仍受交付核对 ← C-3
- 触发: 操作 让需求代理对形状中标记为自行完成的任务直接实现，并省略测试映射
- Given: 该任务有验收条目与验证命令
- When: 需求代理请求把任务标为完成
- Then: 工具因缺少交付证据拒绝完成，补齐证据并验证成功后才能完成；状态未被直接改写

### AC-4 补充需求并入或重新提议 ← C-4
- 触发: 操作 分别转发一条不影响任务集的补充与一条需要新增任务的补充
- Given: 需求代理正在执行
- When: 需求代理处理两条补充
- Then: 第一条直接并入处理；第二条重新提议任务集与形状并等待确认，确认前不新增任务执行

### AC-5 结束与决策经中继 ← C-5
- 触发: 操作 让需求代理分别完成需求、遇到产品决策问题和被阻塞
- Given: 主会话窗口打开
- When: 观察通知路径
- Then: 三种情况均以中继消息到达主会话，面板不出现要求用户直接对话的入口
