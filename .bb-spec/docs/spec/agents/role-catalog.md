# 角色目录

## 目的
让用户预先配置可用的角色子代理，并让派工只在明确的三层关系内发生。

## 逻辑
角色目录由三层定义文件合并：包内默认（planner、worker、reviewer、acceptance 与需求代理）、用户全局目录、项目目录；同名时项目覆盖全局、全局覆盖包内默认。
每个角色定义包含名称、职责说明、可用工具、是否继承技能与项目上下文；需求代理定义同样可被覆盖。
派工关系固定三层：主会话只派出需求代理，以及提交前审查这一处直接派出的白盒审查者；需求代理只派出角色目录内的角色；角色不再向下派工。
角色设置页按角色目录列出全部角色（含需求代理），逐角色配置模型、思考等级与 MCP。
定义文件损坏或缺少必需字段时该角色不可用并显示原因，不用默认定义静默替代。

## 约束
- C-1：当系统装载角色目录时，系统应合并包内默认、用户全局与项目三层定义文件，同名按项目、全局、包内默认的优先级覆盖，并把需求代理作为可覆盖的角色纳入目录。
- C-2：当主会话派工时，系统应只允许派出需求代理和提交前审查的白盒审查者；当需求代理派工时，系统应只允许派出角色目录内的角色；角色发起的派工应被拒绝。
- C-3：当角色设置页展示角色时，系统应列出角色目录中的全部角色（含需求代理），新增的用户角色无需改代码即可配置。
- C-4：如果某角色定义文件损坏或缺少必需字段，系统应把该角色标为不可用并显示具体原因，不用其他定义替代，也不影响其他角色。

## 例子
用户在项目目录新增一个"api-designer"角色定义并在设置页为它选好模型；需求代理在形状中把接口设计任务派给它；该角色试图再派 worker 时被拒绝。

## 验收
### AC-1 三层合并与覆盖 ← C-1
- 触发: 操作 在包内默认、全局目录和项目目录分别放置同名 worker 定义与各自独有的角色定义
- Given: 三份 worker 定义的职责说明不同
- When: 装载角色目录
- Then: worker 取项目定义，三处独有角色均出现，需求代理出现在目录中且可被项目定义覆盖

### AC-2 三层派工关系 ← C-2
- 触发: 操作 让主会话尝试派出 worker、让需求代理派出目录外角色、让 worker 尝试派出 reviewer，再让主会话派出需求代理与提交前审查者
- Given: 角色目录已装载
- When: 系统处理五次派工
- Then: 前三次被拒绝并说明原因，后两次成功

### AC-3 设置页随目录变化 ← C-3
- 触发: 操作 新增一个用户角色定义后打开设置页
- Given: 该角色定义合法
- When: 查看角色标签
- Then: 新角色与需求代理均出现，可为其配置模型、思考与 MCP，未修改任何代码

### AC-4 损坏定义不静默替代 ← C-4
- 触发: 操作 让项目目录的 reviewer 定义缺少必需字段
- Given: 全局目录有合法的 reviewer 定义
- When: 装载目录并尝试派出 reviewer
- Then: reviewer 显示不可用及具体原因，派工被拒绝；没有回退到全局定义，其他角色正常
