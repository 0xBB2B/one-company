# 工作流形状

## 目的
让每个需求按复杂度使用不同的角色组合，同时保持用户对成本与门禁的控制。

## 逻辑
形状包含任务集、每个任务的角色序列（只能来自角色目录，或标记为需求代理自行完成）以及门禁声明（是否包含白盒审查、是否包含黑盒验收）及唯一验收报告位置。
默认提议包含两项门禁；声明不包含任一门禁时必须向用户明确说明并取得确认，确认作为用户决定记录。
需求代理经对话中继提议形状，用户确认后执行；执行中发现需要新增任务或角色（升级形状）时再提议一次，确认前不执行超出形状的派工。
形状约束实施派工：需求确认后允许先派规划角色，写入仅限本需求任务目录与索引；其他未列入的角色不得派出，任务顺序与依赖按形状执行；角色不得再向下派工。
简单需求可以是"单任务、需求代理自行完成、不含门禁"，但仍需经用户确认。

## 约束
- C-1：当需求代理提议形状时，系统应包含任务集、每任务角色序列与门禁声明，角色只能来自角色目录或标记为自行完成；默认提议包含白盒审查与黑盒验收。
- C-2：当用户确认形状时，系统应记录确认后才开始执行；如果形状声明不含某项门禁，系统应把该确认作为用户决定记录，未记录成功不得执行。
- C-3：当执行中需要超出已确认形状的任务或角色时，系统应重新提议并等待确认，确认前不派出超出形状的运行。
- C-4：当按形状实施派工时，系统应拒绝派出未列入的角色；需求已确认且规划前检通过时允许先派规划角色，其写入仅限本需求任务目录与索引，并拒绝角色再向下派工。

## 例子
需求代理提议"任务一 worker 实现、任务二 planner 拆解后由两个 worker 分别写测试与实现、含白盒审查与黑盒验收"；用户确认后执行；中途发现任务二还需要 reviewer 单独核对接口，需求代理再次提议并获确认后才派出。

## 验收
### AC-1 提议内容与默认门禁 ← C-1
- 触发: 操作 让需求代理为一个两任务需求提议形状
- Given: 角色目录含 planner、worker、reviewer、acceptance
- When: 查看提议内容
- Then: 每个任务都有角色序列或自行完成标记，角色均在目录内，门禁声明默认包含白盒审查与黑盒验收

### AC-2 跳过门禁需用户决定 ← C-2
- 触发: 操作 让需求代理提议不含黑盒验收的形状，用户确认；另在决策记录不可写时确认
- Given: 决策记录可观察
- When: 用户确认后观察执行与记录
- Then: 第一种情况用户决定记录成功后开始执行；第二种情况记录失败，执行没有开始并显示原因

### AC-3 升级形状再问一次 ← C-3
- 触发: 操作 在执行中让需求代理发现需要新增 reviewer 角色
- Given: 已确认形状不含 reviewer
- When: 需求代理处理该需要
- Then: 出现新的形状提议，确认前没有派出 reviewer；确认后按新形状派出

### AC-4 形状之外不得派工 ← C-4
- 触发: 操作 让需求代理尝试派出形状未列入的角色，再让某角色尝试派出另一角色
- Given: 形状已确认
- When: 系统处理两次派工请求
- Then: 两次均被拒绝并说明原因，没有产生新的运行
