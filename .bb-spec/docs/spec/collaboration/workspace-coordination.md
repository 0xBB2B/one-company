# 多仓库工作区协调

## 目的
让用户对主会话说一次需求，就能在前端与后端等多个仓库分别推进，且跨仓库接口有唯一裁定者。

## 逻辑
窗口的工作区由其启动目录决定：启动目录及其子目录内发现的全部 Git 仓库都是成员；在某个仓库或其 worktree 内启动时，工作区只有该仓库。
主会话在澄清阶段识别需求涉及的成员仓库，把跨仓库契约（接口路径、请求响应结构、错误码等声明式成品）写入每个相关仓库自己的规范，并为每个仓库建立各自的需求文档。
用户确认后主会话为每个相关仓库派出一个需求代理；需求代理只读取本仓库的规范与契约，不读取或修改其他仓库。
需求代理之间不直接通信；一方需要改契约时经中继向主会话提出，主会话裁定（必要时询问用户）后修改各仓库契约，并把变更作为补充转发给其他相关需求代理。
跨仓库顺序由工作流形状表达：任务可以声明等待另一成员仓库的需求到达某阶段，需求代理据本机流程数据核对后再继续。
面板、提问投递与控制范围均为本窗口工作区内的仓库；范围外的仓库互不可见。

## 约束
- C-1：当窗口启动时，系统应把其启动目录及子目录内发现的全部 Git 仓库作为工作区成员，可见、可控与投递范围限定为这些仓库；在仓库或其 worktree 内启动时范围仅为该仓库；启动目录之外的仓库不可见。
- C-2：当需求涉及多个成员仓库时，系统应由主会话把跨仓库契约以声明式成品写入每个相关仓库的规范并建立各自需求文档，确认后为每个相关仓库派出各自的需求代理，需求代理不得读写其他仓库。
- C-3：当需求代理需要变更跨仓库契约时，系统应经中继提交给主会话裁定，不得直接联系其他需求代理；裁定后主会话更新各仓库契约并转发补充，未裁定前需求代理不得按变更后的契约实现。
- C-4：当工作流形状声明等待另一成员仓库需求到达某阶段时，系统应从本机流程数据核对该阶段后才继续，核对失败或数据缺失时等待并显示原因。

## 例子
用户在包含前端与后端两个仓库的目录启动窗口，对主会话说"实现订单导出"；主会话把导出接口契约写入两个仓库的规范，确认后派出两个需求代理。后端代理发现某字段无法提供，经中继请求改契约，主会话裁定后更新两份规范并转发给前端代理；前端联调任务等待后端需求验收通过后执行。在后端仓库内单独启动的窗口只看到后端代理。

## 验收
### AC-1 可见范围随启动路径 ← C-1
- 触发: 操作 分别在包含两个仓库的父目录、其中一个仓库内、该仓库的 worktree 内和一个无关目录启动窗口并查看面板
- Given: 两个仓库各有活动需求代理
- When: 对照四个窗口的面板与控制入口
- Then: 父目录窗口看到并能控制两个仓库的需求代理；仓库内与其 worktree 内的窗口只看到该仓库的；无关目录窗口看不到且无法控制

### AC-2 一次澄清、多仓派工、契约各自落盘 ← C-2
- 触发: 操作 在父目录窗口对涉及两个仓库的需求完成澄清并确认
- Given: 契约含接口路径与错误码
- When: 观察两个仓库的规范、需求文档与派工
- Then: 两个仓库各自的规范都内联了完整契约并各有需求文档；派出两个需求代理，各自只访问本仓库文件，访问另一仓库被拒绝

### AC-3 契约变更经主会话裁定 ← C-3
- 触发: 操作 让后端需求代理请求删除契约中的一个字段，并让它尝试直接通知前端需求代理
- Given: 两个需求代理均在执行
- When: 观察消息路径与两个仓库的规范变化
- Then: 请求到达主会话，直接通知被拒绝；裁定前后端代理未按新契约实现，裁定后两个仓库的契约同步更新且前端代理收到补充

### AC-4 跨仓库等待按本机状态核对 ← C-4
- 触发: 操作 让前端需求代理的联调任务声明等待后端需求进入验收通过，再分别在后端未通过与已通过时观察
- Given: 后端需求的本机流程数据可读
- When: 前端需求代理处理该任务
- Then: 未通过时任务显示等待及原因且不执行；通过后核对状态再执行；本机数据缺失时保持等待并显示缺失
