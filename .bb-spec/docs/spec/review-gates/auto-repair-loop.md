# 自动返修

## 目的
把可由测试、实现和既有规则解决的技术问题在流程内闭环，一次返修解决已暴露的一类错误，同时不无限循环，也不把纯技术问题转嫁给用户。

## 逻辑
需求代理在用户已授权的目标、文件范围和验收标准内派发实现角色，由它完成先失败后通过与自验收的修复，随后调用原审查角色重审；审查角色始终只报告不修改。
首次返修的派工要求列明错误假设、同类受影响场景和本轮要增加的验证，不只转发一个失败例子。同一根因再次失败时，先重新核对相应状态、数据边界或接口契约，给出与新旧复现关联的修复方向，再派修复。新增的同类验证只证明原有要求，不借此增加功能、改变验收或扩大写入权限。
修复需要扩大目标、文件范围或验收标准的，属于产品决策，不自动返修。
白盒审查未通过的返修在修复完成后对整个分支重审；黑盒验收未通过的返修在修复通过白盒重审后再重新验收。
每个审查阶段检查独立计数，一次归因、修复派发并再次调用原审查角色为一轮，上限三轮；验收返修内嵌的白盒重审未通过计入白盒阶段检查轮次且不清零。第三轮重审仍未通过时记录技术阻塞并停止，这是确定性状态转换，不写入决策记录。停止后用户可经对话中继授权新一轮返修，系统不自动重试，也不重置轮次。授权提问由系统明确标示阶段检查与轮次，固定为“继续返修 / 停止”；只有用户选择“继续返修”并成功写入决定后授予该轮权限，其他答复不授予权限，撤回不写决定。

## 约束
- C-1：当审查问题归因为可自动解决且修复不超出用户已授权的目标、文件范围和验收标准时，系统应自动派发实现角色修复，并再次调用原审查角色重审，期间不询问用户。
- C-2：如果修复需要扩大目标、文件范围或验收标准，系统应把该问题归为产品决策，不得自动返修。
- C-3：当需求代理首次派发获准返修时，系统应在派工要求中列明错误假设、同类受影响场景及验证补充，修改只派给实现角色，新增验证不得增加功能、改变验收或扩大写入权限。
- C-4：如果同一根因在后续交付或审查中再次失败，系统应先重新核对状态、数据边界或接口设计，给出与新旧复现关联的修复方向，再在获准范围内派发修复。
- C-5：当黑盒验收未通过进入返修时，系统应在修复后先由白盒审查者对整个分支重审，通过后再重新调用黑盒验收者；其中白盒重审未通过计入白盒阶段检查的轮次且不清零。
- C-6：在同一审查阶段检查的自动返修期间，系统应最多执行三轮修复与重审，不得通过改名、重派或改归属重置同一项检查的轮次。
- C-7：如果同一审查阶段检查第三轮重审仍未通过，系统应记录技术阻塞并停止，不写入决策记录，不继续返修，也不把纯技术问题转为用户决策请求。
- C-8：当技术阻塞后用户经对话中继明确授权新一轮返修时，系统应从原轮次继续计数执行该轮；未获授权的失败不自动重试；系统仅将固定选项“继续返修”记录为指定阶段检查、指定轮次的授权，拒绝、含糊答复、撤回和决定写入失败均不得放行。

## 例子
白盒审查者指出分片处理串用状态，问题在已批准文件范围内。需求代理派实现角色修复，派工要求同时检查消息与内容块隔离；重审再次因同根因未通过时先重查输入边界再派修复；第三轮仍未通过则停止并报告技术阻塞，直到用户经中继授权第四轮，轮次从四继续。

## 验收
### AC-1 白盒审查问题自动修复 ← C-1
- 触发: 操作 让白盒审查者报告一个不涉及产品决策的实现或测试问题
- Given: 用户已批准的目标、文件范围和验收标准足以完成修复
- When: 需求代理完成归因
- Then: 系统自动派发实现角色修复并由白盒审查者对整个分支重审，期间没有询问用户

### AC-2 超出授权范围不自动返修 ← C-2
- 触发: 操作 让白盒审查者报告一个必须修改任务文件范围之外的文件才能解决的问题
- Given: 该文件不在任务声明的范围内
- When: 需求代理完成归因
- Then: 系统没有派发修复，该问题作为产品决策向用户提出

### AC-3 首次返修覆盖同类场景 ← C-3
- 触发: 操作 对一个因输入边界混淆而失败的任务启动已获准返修
- Given: 原要求已包含相互独立输入不影响彼此，写入范围足够
- When: 需求代理派工
- Then: 派工要求明确错误假设、相关输入类别和验证补充，修改只派给实现角色，审查角色没有修改文件

### AC-4 重复根因先核对设计 ← C-4
- 触发: 操作 在同一根因第二次出现时请求返修
- Given: 上一轮具体案例已修复，但同类输入或时序仍违反原要求
- When: 需求代理准备下一轮修复
- Then: 先给出与新旧复现关联的状态、数据边界或接口核对结论，再派范围内修复，不只追加针对新案例的特判要求

### AC-5 验收返修内嵌白盒重审并计入轮次 ← C-5
- 触发: 操作 让黑盒验收者报告一个由实现偏差造成的验收失败，且修复后的白盒重审第一次未通过
- Given: 白盒阶段检查此前已用掉一轮，规范与验收明确且不需要用户选择
- When: 需求代理完成归因并派发修复
- Then: 修复后先由白盒审查者重审，白盒阶段检查轮次变为两轮；白盒重审通过后才再次调用黑盒验收者，期间没有询问用户

### AC-6 三轮后停止且不重置 ← C-6, C-7
- 触发: 操作 让同一审查阶段检查的非产品问题连续三轮修复后仍未通过，随后尝试通过改名与重派继续
- Given: 每轮修复都由已有授权覆盖，并由原角色重审
- When: 第三轮重审再次返回未通过
- Then: 系统停止返修并报告技术阻塞，不向用户询问如何解决纯技术问题，决策记录没有新增条目，改名与重派没有开启新轮次

### AC-7 用户授权后继续计数 ← C-8
- 触发: 操作 在技术阻塞后经对话中继授权新一轮返修
- Given: 同一项检查已停在第三轮未通过
- When: 用户明确授权
- Then: 系统执行第四轮修复与重审且轮次显示为四；拒答、含糊答复、撤回、旧轮次或其他阶段检查的授权均没有放行，决定写入失败时仍保持阻塞
