# 白盒审查的时机与重点

## 目的
让白盒审查一次看到完整改动，并把审查精力集中在会造成真实损害的问题上。

## 逻辑
需求的所有任务都完成并各自通过自验收后，主 agent 对当前分支相对基线的完整改动派工一次白盒审查，而不是每完成一个任务审一次。审查者先以攻击者视角找可触发的安全问题，再以真实非恶意故障视角找鲁棒性问题，每条发现都给出位置、触发条件或攻击路径、影响与修复方向；然后核对每个任务的验收在测试与实现中的可追踪关系与 TDD 可信度。没有实际触发路径的问题不阻断。

## 约束
- C-1：当需求进入白盒审查时，系统应在所有任务完成后对整个分支只派工一次审查，不得在单个任务完成时派工审查。
- C-2：当白盒审查者审查时，系统应把安全性与鲁棒性作为首要审查重点，每条发现必须包含位置、触发条件或攻击路径、影响与修复方向。
- C-3：如果某个问题没有实际可触发的路径，系统应不把它作为阻断项，也不要求为其增加防御代码。
- C-4：当白盒审查者完成重点审查后，系统应逐条核对每个任务的验收在测试与实现中的可追踪关系，测试遗漏或证据不可信即为阻断项。

## 例子
三个并行任务先后完成并各自通过验证，主 agent 只在第三个任务完成后派工一次白盒审查；审查者报告一处路径穿越（含攻击路径与修复方向）和一条未被测试覆盖的验收，两者都进入返修；一处只有在数据库文件被手工破坏时才触发的分支被写入建议而非阻断。

## 验收
### AC-1 只在全部完成后审查一次  ← C-1
- 触发: 操作 执行一个含三个任务的需求
- Given: 三个任务依次完成并各自通过验证
- When: 前两个任务完成时与第三个任务完成时分别观察
- Then: 前两个任务完成时没有派工白盒审查，第三个任务完成后只派工一次覆盖整个分支的白盒审查

### AC-2 安全与鲁棒性发现带触发路径  ← C-2, C-3
- 触发: 操作 让分支中同时存在一处可触发的路径穿越和一处只在不可能场景下才触发的分支
- Given: 白盒审查者已被派工
- When: 审查者提交裁决
- Then: 路径穿越作为阻断项出现且带位置、攻击路径、影响与修复方向；不可能场景的分支不作为阻断项，也没有要求增加防御代码

### AC-3 测试遗漏是阻断项  ← C-4
- 触发: 操作 让某个任务的一条验收没有对应测试
- Given: 安全与鲁棒性审查未发现问题
- When: 审查者核对可追踪关系并提交裁决
- Then: 裁决为 FAIL，问题定位到该任务的该条验收
