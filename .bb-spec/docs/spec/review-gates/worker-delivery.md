# 实现交付证据核对

## 目的
避免局部测试通过或非空证据被误认为任务已经完整交付。

## 逻辑
需求代理取得实现角色的合法结构化裁决后，对照本任务核对证据。
本任务要求的每条验收都须有可定位到实际测试的映射，映射中的测试须位于本次验证范围。
最终验证命令须符合任务约定且结果成功；开发中的先失败后通过记录不因此被误判。
相关回归失败须区分本次造成、已存在、已安排的后续接入缺口和未能归因四类，并给出证据与责任。
本次造成或未能解释的相关失败不能以局部通过掩盖。
证据核对通过后需求代理仍独立复跑；全部任务完成后才进行统一集成验证。
不为交付核对新增完整会话采集，存在映射也不自动证明断言正确。

## 约束
- C-1：当需求代理核对实现交付时，系统应逐项比对本任务全部验收、真实测试位置及验证范围，不只检查覆盖清单非空；最终验证命令必须符合任务约定且明确成功。
- C-2：如果验收漏项、测试位置不存在或无法定位、验证范围不足、最终命令不符或失败，系统应报告具体原因并不放行。
- C-3：当出现相关回归失败时，系统应按本次造成、已有问题、后续接入缺口或未能归因分类并说明证据、责任和恢复通过节点；本次造成或未能解释的相关失败阻止交付。
- C-4：当交付证据满足要求时，系统应由需求代理独立复跑后才放行，开发阶段的历史失败不单独否定最终成功；全部任务完成后仍须通过约定集成验证，机械映射不能代替测试证明力核对。

## 例子
任务要求三条验收，实现者只提供一条映射且报告一个无关命令通过，需求代理指出另外两条遗漏及最终命令不符，不进入提交。

## 验收
### AC-1 完整证据后独立复跑 ← C-1, C-4
- 触发: 操作 提交含可信开发失败记录和完整最终通过证据的任务结果
- Given: 每条验收均映射到真实且在验证范围内的测试，没有未解释的相关失败
- When: 需求代理核对交付
- Then: 确认约定最终命令成功后独立复跑，复跑成功才放行，开发阶段的历史失败不阻断；本结论不取代后续集成验证

### AC-2 缺项或错误验证不能通过 ← C-1, C-2
- 触发: 操作 分别提交漏一条验收、测试位置不存在或无法定位、测试未纳入验证、最终命令不同或失败的案例
- Given: 其他内容均满足要求，其中命令失败案例仍包含较早的一条成功命令
- When: 需求代理核对结果
- Then: 各案例均报告具体缺项或失败原因且不放行，不因清单非空或曾有成功命令而通过

### AC-3 相关回归失败有归属且不藏匿 ← C-3, C-4
- 触发: 操作 提交目标测试通过但相关回归失败的结果
- Given: 分别准备本次造成、已有问题、已安排后续接入及无法归因四类有证据的案例
- When: 需求代理判断任务是否可交付
- Then: 分类和责任可见，本次造成及无法解释的失败阻止交付，已有和后续问题列明处理及恢复通过节点，也不将局部通过当作整个需求通过
