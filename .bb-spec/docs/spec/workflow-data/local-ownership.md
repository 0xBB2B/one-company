# 本机流程数据归属

## 目的
让用户在创建需求文档和独立工作目录之前即可记录决定，并在同仓库的不同工作目录中定位同一需求。

## 逻辑
流程数据以仓库身份和需求身份归属，不以当前对话所在目录或分支名称代替身份。
同仓库的多个 worktree 定位同一需求的数据，不同需求与不同仓库的数据分别保存。
首次合法记录请求可建立本机用户数据区中的归属记录，不要求需求文档、任务文档或验收报告已经存在。
工作目录只是该需求的开发现场，删除 worktree 或功能分支不删除流程数据。
流程数据仅保存在本机，不随 Git 提交、推送或克隆同步。

## 约束
- C-1：当主会话首次记录已明确归属仓库与需求的流程数据时，系统应将其保存在本机用户数据区，并允许需求文档和计划中的 worktree 尚不存在。
- C-2：当用户从同仓库的不同 worktree 查询同一需求时，系统应定位同一份归属记录；不同仓库或不同需求不得因名称相同而混用数据。
- C-3：当本需求的 worktree 或功能分支被删除时，系统应保留已保存的流程数据；Git 提交、推送或克隆不得自动携带这些数据。
- C-4：如果仓库或需求身份缺失、冲突或无法核对，系统应拒绝关联写入并显示具体原因，不猜测归属或改用另一个需求的数据。

## 例子
用户在需求文档尚未建立时记录创建 worktree 的授权，得到本机记录回执；随后在新 worktree 查询该需求，可以找到同一条授权。

## 验收
### AC-1 文档与 worktree 创建前记录 ← C-1
- 触发: 操作 在需求文档与计划工作目录都不存在时记录一条已授权决定
- Given: 当前仓库可识别，需求身份明确，本机用户数据区尚无该需求
- When: 通过决策工具提交合法决定
- Then: 返回可查询的记录回执，记录位于本机用户数据区，未创建需求文档或 worktree

### AC-2 同仓库共享且不同归属隔离 ← C-2
- 触发: 操作 从同仓库的两个 worktree 查询同一需求，再查询同名的另一仓库需求和同仓库另一需求
- Given: 第一个需求已有一条带唯一标记的记录
- When: 分别通过工具查询这四个归属
- Then: 前两个查询返回同一条记录，后两个不返回该记录

### AC-3 工作目录清理与 Git 不带走记录 ← C-3
- 触发: 操作 删除已完成需求的 worktree 和功能分支，再提交推送并克隆该仓库
- Given: 清理已获准且不存在活动写入，本机已有该需求流程数据
- When: 在本机查询原需求并检查 Git 交付内容
- Then: 原需求记录仍可查询，新增提交和克隆内容不含本机流程数据

### AC-4 无法确认身份时拒绝 ← C-4
- 触发: 操作 在仓库身份不可确认或需求身份相互冲突时提交更新
- Given: 已有一个名称相似但身份不同的需求
- When: 工具处理请求
- Then: 返回身份错误，相似需求及其他归属的数据均未改变
