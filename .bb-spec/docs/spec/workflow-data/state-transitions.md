# 需求与任务状态推进

## 目的
用程序阻止非法状态和跳过验证的阶段推进，使进度具有明确含义。

## 逻辑
需求阶段限于 draft、confirmed、planned、executing、reviewing、accepting、accepted、rejected。
任务进度限于 todo、doing、done、failed；子运行状态独立存在，不代替任务进度。
正常需求顺序为起草、确认、规划完成、执行、审查、验收、完成，每一步都检查其前提。
任务先登记执行中，再关联子运行；子运行交付满足结构化门禁后，验证命令成功且有本次提交时已核对提交信息，才可完成任务。
已有实现满足需求且无改动时仍须通过对应的结构化证据与验证，不要求伪造新提交。
返修保留原运行与失败原因，在已有授权内记录必要决定后回退受影响任务；纯技术失败不自动将需求判为 rejected。
定义变更需要用户确认，已完成需求不原地重开；增加任务或重验不得沿用失效的完成结论。

## 约束
- C-1：当工具初始化或更新状态时，系统应只接受约定的需求八种阶段及任务四种进度，拒绝未知值和将子运行状态写成任务进度。
- C-2：当需求正常推进时，系统应逐阶段核对前提：确认需用户确认回执，规划完成需规划产物核验，执行需调度就绪，审查需全部任务完成，验收需匹配版本的白盒 PASS，完成需黑盒结构化结果与指定报告一致且全部通过。
- C-3：当任务开始或结束时，系统应先登记 doing 再关联实际子运行；done 必须具备合法交付与成功验证，有本次提交时还须核对提交信息，无改动时须有既有实现已满足要求的证据，失败应记录 failed 与具体原因，启动回执或子运行结束不得直接完成任务。
- C-4：当发生返修、规划退回或产品变更时，系统应核对原运行停止、已授权范围及对应决定后执行有理由的回退；仅产品裁决可将需求置为 rejected，纯技术失败保持阻塞且已完成需求不得原地重开。

## 例子
子代理正常结束但任务验证命令失败，任务被记录为 failed，需求仍处于执行阶段，不能仅凭子运行结束进入审查。

## 验收
### AC-1 状态集合不可扩张 ← C-1
- 触发: 操作 提交未知需求阶段、未知任务进度及子运行的 paused 值作为任务进度
- Given: 已有合法需求阶段和任务进度
- When: 通过状态工具请求修改
- Then: 三类请求均被拒绝，原值不变，错误提示列明对应合法集合

### AC-2 阶段门禁逐项核对 ← C-2
- 触发: 操作 按正常阶段顺序推进需求，对每一步分别移除必要前提后请求推进，再补齐前提请求推进
- Given: 每次失败测试使用该阶段合法起始状态，完成测试含匹配的结构化结果与指定报告
- When: 通过工具推进 confirmed、planned、executing、reviewing、accepting、accepted
- Then: 缺少前提时均保持原阶段并给出缺失原因，前提齐全才依序推进，直接从 draft 跳到 accepted 被拒绝

### AC-3 子运行与任务完成分离 ← C-3
- 触发: 操作 启动任务，依次测试只有启动回执、交付失败、验证失败、有提交但未核对、全部条件满足及无改动的合法交付
- Given: 各场景均有明确任务与子运行归属，无改动场景有既有实现证据和成功验证
- When: 查询任务并请求完成
- Then: 启动先显示 doing，前四种场景不得显示 done，失败有具体原因，后两种满足门禁后完成任务，无改动场景不伪造提交

### AC-4 回退与拒绝有依据 ← C-4
- 触发: 操作 请求合法返修和规划退回，再测试未经授权扩范围、原运行未停止、纯技术失败置 rejected 及重开已完成需求
- Given: 合法场景有对应前提与必要决定，其余场景分别缺少所需依据
- When: 通过工具处理回退或拒绝请求
- Then: 合法请求保留原因与原运行关联后回退，其余请求被拒绝且不重复派工或改写已完成需求
