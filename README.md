## 这是什么

one-company 把开发分为三个层次：

- **主会话（main）**：在当前窗口理解真实需求，区分目标、非目标、约束、允许动作和未决项；对照已批准完整需求与可信决定，核对 PM 的接手理解，不无理由要求用户重新全量审批。
- **需求代理（PM）**：先读取当前已批准完整需求，回报目标、非目标、约束、允许动作、未决项与场景理解；主代理核对通过后，才正式产出和维护 plan 与 task，并在已有授权内派工。接手复核本身不增加授权，不另设产品 planner。
- **角色代理**：main 或 PM 可派只读 explore 查找证据；PM 安排 worker 实现、reviewer 审查和 acceptance/QA 黑盒验收。worker 给自己新增或修改的函数、方法、类、类型与导出常量写说明注释（参照 Go 官方库写法：以名称开头，说明做什么、各参数与返回值的含义），审查检查缺失或与行为不符；代理用 grep 直接搜索注释和代码。explore 不继承父代理完整会话，只接收最小问题范围，结果须由父代理核验整合。

代码审查检查实现是否合理，功能验收检查实际行为是否符合已批准目标。各角色的权限、版本和阶段门槛由程序核对，角色说明或代理自报通过不能代替实际检查。

worker 交结果时，程序检查需求工作区：有文件被改动、却不在本需求任何未取消任务的写入范围内，就拒收这次结果，worker 把文件恢复后才能重交。这条检查不看语言，`package.json`、`go.mod`、`Cargo.toml` 等依赖清单被顺手改了都会被拦下；被 Git 忽略的文件不算。PM 提交时也核对：要提交的文件只要有一个不在本需求任何任务（包括已取消的任务）的写入范围内，整次提交就被拒绝。新增或升级第三方依赖须由 PM 交你裁决，你同意后 PM 才把依赖清单放进任务的写入范围，reviewer 审查时核对。

## 安装

```bash
pi install git:github.com/0xBB2B/one-company
```

本地开发时使用 `pi install /absolute/path/to/one-company`，并先在该目录执行 `pnpm install --frozen-lockfile` 安装锁定依赖。本框架使用 pnpm 11.7.0，运行及测试均使用 Node；运行 pi 的 Node 版本需 ≥ 22.19。角色代理随包提供，无需另装子代理系统。

Git 是必须由用户预先安装的系统工具，并且需要位于 `PATH` 中。本包不捆绑、下载或自动安装 Git。正常 npm 安装以及由 pi 触发、且允许执行安装脚本的 npm 安装会运行 `preinstall` 检查：执行 `git --version` 失败时，安装以非零状态退出，并提示“必须预先安装Git并确保PATH可用”。

`--ignore-scripts`、pnpm 禁用第三方安装脚本，以及 `pi install /absolute/path` 这类仅登记本地路径的方式，可能跳过 `preinstall`。运行时直接调用 `PATH` 上的 `git` 并传固定参数，不再做其他核验；此时缺少 Git 会在首次需要 Git 的操作（读取仓库身份、保存需求正文、受管提交）处报错。

## 卸载

```bash
pi remove git:github.com/0xBB2B/one-company
```

卸载不会立即停止已启动的后台进程：它们会在空闲后自动退出，也可以手动停止。本机的需求状态、运行与对话记录会保留，重新安装后仍可读取。

## 快速开始

在 Git 仓库中打开 pi。本包的所有会话命令均以 `/one:` 开头：

| 命令 | 用途 |
|---|---|
| `/one:agents` | 查看角色定义并复制为新定义 |
| `/one:ps` | 查看和管理终端命令任务 |
| `/one:git-delivery` | 开启或关闭可选的 Git 交付工具 |

### 当前项目索引

已接入仓库可由代理调用 `one_company_project_manage`。和索引相关的参数如下，参数放在 `request` 里：

```json
{ "request": { "action": "init", "repoId": "<当前 lifecycle 中的 64 位仓库身份>", "preview": true } }
```

- 索引相关的 `action` 是 `init`、`status`、`refresh`；`preview` 只允许用于 `init`。设为 `true` 时，经真实宿主 UI 确认后仅单次枚举路径元数据，不读取文件正文、不创建 `index.db`。
- `init`（非预览）或 `refresh` 经当前真实宿主 UI 确认扫描范围后，由仓库守护进程执行；`init` 成功即登记本仓库已初始化，此后守护进程持有索引，不依赖窗口是否在线。
- `status` 不扫描文件，返回当前索引状态及是否已初始化（`managed`）。
- 初始化和刷新会索引当前代码、配置与普通文档，提取 TS/TSX、JS/JSX、Go 的结构和可证明的同文件直接调用；其他语言只保留文件级记录。语法错误返回 `partial`，不会回退旧正文。
- `.git`、被 Git 忽略的路径、依赖、构建/缓存/日志、本机数据库、敏感凭据、链接文件、多链接文件、嵌套仓库和 `docs/prod` 正文都不进入索引。归档需求只登记合法 UUID 文件路径，状态固定为 `unknown`，不产生活动需求授权。
- 默认预算为单文件 2 MiB、文本集合 20 MiB、20,000 个目录条目、64 层深度。发布前会再次读取并核对 hash，因此一次完整构建最多读取两倍文本集合预算。工具输出最多 32 KiB、100 项；截断、预算耗尽、跳过项和必要阻塞状态会明确返回。

索引写入仓库外的 `index.db`，未变文件按内容 hash 和解析器版本跨刷新、跨进程复用。同一仓库的多个窗口复用守护进程与同一份索引；切换分支后按当前分支重新对账。

索引不监听文件。主会话和 PM、worker、reviewer、explore 都通过 `one_company_knowledge_query` 查询；每次查询前，守护进程按修改时间、大小与 ctime 找出新增、修改、删除的文件，有变化才增量重建，再在更新后的索引上查询。结果反映查询那一刻的磁盘内容并标注索引代次，交付后文件再变化不追踪，下一次查询自然读到新内容。`docs/prod` 始终只处理路径元数据；对账时发现归档与本机旧活动需求对应，先阻止续接并标记待核对，不读取归档正文，不凭归档将需求改成 `completed`。可信关闭原因保持不变，归档删除或 Git 回退不会恢复授权。

grep、find、ls 工具在主会话和各角色中都不搜索 `.git` 与被 Git 忽略的路径；命令行里的搜索由会话说明约束。

## 守护进程

守护进程就是负责持续运行代理的后台进程。每个仓库一个守护进程；同一仓库通过 Git worktree 建立的多个工作目录共用这个进程。打开主窗口时会自动启动，不需要手动操作。

进程会在空闲后自动退出，空闲时限为 10 分钟；设备合盖睡眠的时间不计入。进程崩溃或电脑重启后，之前未结束的运行会被标记为中断，不会自动续跑；需要继续时在对话中让主代理重新派出 PM。网络断开时，相关运行会暂停；网络恢复后在 PM 面板按 p 恢复，运行从断开的地方接着继续。模型请求超时不算断网：会自动重试，最多 3 次，每次间隔 2、4、8 秒；3 次都超时就按失败结束，并写明原因。主窗口直接派出的检索没有恢复入口，网络断开时按失败结束，结果卡片写明原因，需要时让主代理重新派出。

## PM 面板

面板位于输入框下方，只显示正在运行或已暂停的 PM，一个需求对应一个 PM；需求结束后该行消失。输入框为空且没有补全菜单时，按 ↓ 进入面板，按 Esc 回到输入框。

```
● 2 个需求运行中
├─ ⠹ 角色跳跃、跳跃动画 · ↻5 · 5 tool uses · 33.8k token (62%) · 12.3s
│    └ 派 worker 执行 login（第 2 次尝试）
│      └ ⚑ 待你裁决：任务 login 两次未完成
└─ ⠹ 角色快跑 · ↻42 · 38 tool uses · 91.0k token (84%) · 2m17s
     └ 规划中（计划 v2 · 3 个任务）
```

每个 PM 一行：需求目标、轮数、工具调用次数、token 用量与缓存命中率（均为 PM 与其全部子代理之和）、耗时。下一行是程序按真实状态生成的"在做什么"。等待你的决定或已暂停时行首显示 ⏸，计时停止。

以 ⚑ 开头的行是等待你处理的事项。用 ↑↓ 选中后按 Enter，事项的决策包会插入当前对话；主代理读完并查清原因后，用问答窗口给出建议，你在窗口里选一项或自己写。决策包本身不是你的决定。待你裁决、待你验收、取消或拒绝需求这类要登记的决定，窗口里的选项文字由程序固定，你选中的选项、自己写的话，或在对话里亲手输入的话才作为你的决定；其余事项的回答只是给主代理的指示。“待你确认原型”仍在按 Enter 后由程序的确认窗口处理。PM 提交计划被拒时会按原因自己改一次，两次都被拒就出现“待你裁决：PM 计划两次提交被拒”；PM 停下、又没有任何东西会让它继续时出现“待你处理：PM 停下了”。在 PM 行按 p 暂停或恢复该 PM，它派出的子代理随之暂停或恢复；停止需求请在对话中告诉主代理。多个主窗口看到的是同一份数据，一个窗口处理掉的事项会从所有窗口消失。

### 界面原型先确认再实现

需求里涉及界面的任务（网页、桌面或手机界面，以及终端输出），PM 会先派 worker 做一个 HTML 原型，你确认后才开始实现。终端界面的原型是在网页里模拟的终端窗口。

1. worker 交出原型后，面板里出现"⚑ 待你确认原型：任务 xxx（第 N 版）"。
2. 选中这一行按 Enter：默认浏览器打开原型文件，同时弹出确认窗口，窗口里写着文件路径、大小和指纹。
3. 在窗口里选"通过"，PM 随后派 worker 按这一版实现；把光标移到"返工"直接输入要改什么再按回车，意见会原话交给 PM，worker 改出新版本后面板里会再出现这一事项。按 Esc 暂不决定，事项留在面板里。

原型的通过和返工只认这个窗口里的选择，在对话里说"原型可以"不算数。通过只对你看到的那一版有效，原型出了新版本要重新确认。原型文件保存在本机数据目录，不进业务仓库，单个文件不超过 1 MB。审查和验收时，reviewer 与 QA 会对照你通过的原型检查实际界面。任务交过原型后，PM 修改任务时去不掉界面标记；这样的任务 PM 也不能自行取消：你不要这个界面了，就告诉主代理调整需求，你批准新版本后 PM 才能取消它。PM 一开始没把任务标为界面任务，或另建一个不带标记的任务，程序拦不住，由 reviewer 在审查时发现并打回。

## @需求

在输入框里打 `@`，补全列表会在文件前面列出当前工作区状态正常的草稿和进行中需求，说明里写着"草稿"或"进行中"，PM 正在运行时写"PM 运行中"，工作区有多个仓库时还写仓库名。选中后插入 `@[标题#编号尾]`，编号尾至少 4 位，和别的需求重复时自动加长。一句话可以 @ 多个需求，也可以跨仓库。

- **带 @ 的话**：主代理知道这句话针对哪些需求，对每个需求分别判断：要改需求内容就修改草稿并请你批准，批准后改动会自动送到 PM；只是给 PM 的指示就转给 PM（PM 看到的内容标为主代理转述，只作参考）；其他情况直接回答。这句话里的"同意"只对 @ 到的需求有效。
- **不带 @ 的话**：主代理自己判断是新需求，还是涉及哪一个或哪几个现有需求。要登记批准时，程序会弹出黄色的"批准需求"窗口，显示需求名、版本和简介，你选"确认"才生效。
- **回答面板事项**：在 PM 面板打开 ⚑ 事项后，在主代理弹出的问答窗口里回答，或直接在对话里说，都算对这个事项的回答，不需要再 @。
- @ 了不存在、已关闭或状态异常的需求时，会给出黄色提示，写明是哪一个、为什么；这句话只附上有效的需求。

窗口不会一直"绑定"某个需求。重开窗口或用 pi 的恢复对话功能后，直接 @ 需求或在面板里打开事项就能接着处理。

## 主代理提问

主代理需要你做决定时（比如"起跳时机选哪种"），会弹出一个蓝色边框的提问窗口，不在对话里直接问。窗口从上到下是：

- 灰色一行写"提问"和需求名、版本，下面是加粗的问题。
- 灰色的"根源自检"：主代理说明这个问题针对的根源，以及为什么这些选项是从根源解决，而不是临时修补。
- 2 到 4 个选项。每个选项下面有一行灰色的理由，写它的好处或坏处；推荐的那个挂绿色"推荐"，再多一行绿色的推荐理由。
- 最后一项"其他（自己输入）"：不想从选项里挑时，用自己的话回答。光标移到这一项，下面就出现输入栏，直接打字，回车提交。

窗口打开时光标就停在推荐项上，直接按回车就是"按推荐的来"。↑↓ 选择，回车确认；按 Esc 表示暂不回答，问题会保留，之后在对话里直接回答也算数。

你在窗口里的选择或输入，就是你这一轮说的话，主代理据此修改草稿。窗口里的回答只算回答，不能用来批准需求或裁决事项；要批准时请在主窗口直接说。回答之后，对话里会留下一块记录，写着问题和你的回答。

主代理登记问题时必须写全根源自检、2 到 4 个选项，并恰好推荐一个、写明推荐理由；少了任何一项，程序都不会弹窗，会让主代理补全后重新登记。

## 规范

代理要遵守的规范有三个来源，你不需要为这个包编辑任何文件：

- **包内自带的规范**，随包安装，分三层：
  - `shared/`：主代理和所有子代理都遵守，包括准确如实、聚焦需求、保护已有改动、同一问题试三次不成就停下、收尾自检、搜索范围。
  - `rules/`：只给主代理，包括主会话职责、沟通方式、递进式澄清、执行授权、归档需求、简报格式。
  - `agents/`：每个子代理角色自己的说明。
- **用户级 `~/.pi/agent/AGENTS.md`**：你自己维护的个人规范。主代理按 pi 的惯例读取，每个子代理启动时也读取。这个包只读不写。
- **项目 AGENTS.md**（仓库根目录）：这个项目长期遵守的约定。主代理按 pi 的惯例读取，每个子代理启动时读取主仓库根目录的这份文件。文件改了以后，新派出的子代理读到新内容。

你在对话里提出长期约定时（例如"不允许使用泛型"），主代理会把它和这次要做的功能分开，提交项目 AGENTS.md 的新内容。程序弹出黄色窗口，显示新内容和现有文件的差异，你选：

- **写入**：写进仓库根目录的 AGENTS.md。
- **不写入**（或按 Esc）：不动文件。
- **其他（自己输入修改意见）**：不动文件，你的原话交给主代理，它改好后再弹一次窗。

主代理不能用 edit 或 write 工具直接改仓库根目录的 AGENTS.md，程序会拒绝；子代理也改不了这个文件。命令行里的写入程序拦不住，由会话说明约束。

## 角色与设置

角色固定为 **main、PM、explore、worker、reviewer、acceptance/QA** 六类，PM 直接负责规划。

explore 在派出方工作区内用 read/grep 和 `one_company_knowledge_query` 检索本地代码，或联网搜索/抓取网页（含内网，首版不核对查询词）；search/fetch 是非业务能力，不增加第 11 个核心业务工具。输出为有界结论、本地路径/行号/hash（宿主按文件实际内容核对）或 URL/短引文/时间，以及覆盖范围和未知项；不可用时如实报告。它不修改代码或计划，派工输入不含 prod 正文，不再派工。

角色定义来源：

| 来源 | 目录 | 生效范围 |
|---|---|---|
| 包内默认 | `agents/` | 随包提供 |
| 用户设置 | `~/.pi/agent/agents/` | 当前用户的项目 |
| 项目设置 | 仓库内 `.pi/agents/` | 当前项目 |

同名角色优先使用项目定义，其次是用户定义，最后是包内默认。项目定义只有在 pi 中将项目设为受信任后才会加载。

执行 `/one:agents` 打开角色定义页（只读）。页面是一张表，每行一份生效的定义，列出名称、来源（内置、用户、项目）、模型和思考等级；右上角写着各层各有几份定义。按键如下：

- ←→ 切换分类：左边是五个职责（pm、worker、reviewer、qa、explore），右边是"内部"和"问题"。
- ↑↓ 选择定义，回车在原地展开详情（描述、skills、MCP、文件路径），再按回车或 Esc 收起。
- C 复制为新定义：先在页内输入新名称（名称三层内不能重复，重名当场提示），再在窗口里选复制到用户层或项目层，每个选项都写出会生成的文件路径。已有同名文件的层、以及项目未受信任时的项目层会变暗、选不中，并写明原因。复制完回到原来的分类，新定义被选中并标成绿色。
- pm 和内部定义只能同名复制，用来覆盖内置的那一份。

设置页不提供编辑，请直接修改对应目录下的 md 文件。写错的定义、缺少 role 的其他工具的定义、以及项目未受信任时没加载的项目层，都列在"问题"分类里，写明原因，不会顶掉内置团队。

定义可选填 model、thinking 与 mcp。mcp 列出这个角色要用的 MCP 服务（比如公司内网的检索服务），pm、explore、worker、reviewer、qa 的定义都生效，解释器和草稿核验器这两个内部定义不接受。服务用 pi 自带的 MCP 接入，不用另装插件：mcp 里写的名字要和 `~/.pi/agent/mcp.json` 里 `mcpServers` 下的服务名一致，配置就按 pi 的 mcp.json 格式写。派出时只连接定义里点名的服务，模型通过 codemode 脚本或工具搜索调用它们的工具，服务设了 `exposure` 的按设置来；codemode 脚本里不能调用分类模型或生图模型。程序不按只读与否拦截这些工具，不想让角色用到的工具，在 mcp.json 里用 `toolExposure` 设成 `hidden`。点名的服务在 mcp.json 里不存在或被停用时算缺失，配置写错时写明原因；这两种情况都不报错，角色照常用本包自带的工具。需要 OAuth 登录的服务，先在 pi 里用 `/mcp` 登录一次，守护进程不会弹出浏览器。连接日志在 `~/.pi/agent/mcp.log`。model 可以只写模型名（如 `gpt-6.1-sol`），也可以写成"提供方/模型名"（如 `5x/gpt-6.1-sol`）。只写模型名时，主会话所在的提供方有这个模型就用它；没有、而本机恰好只有一个提供方有，就用那一个；有多个时报错并列出候选，请改写成"提供方/模型名"。model 不填时跟派工时主会话的模型，thinking 不填时跟主会话的思考等级。

安装包自带的定义里，解释器用 `gpt-6-luna` 加 medium 思考，其余都用 `gpt-6.1-sol`：pm、worker、reviewer、qa、explore 用 high 思考，草稿核验器用 medium 思考。解释器换成 luna 是为了让批准登记更快：用真实输入对比，批准一份草稿的解读总耗时中位数从约 52 秒降到约 12 秒，解读合规率相当。使用前本机的模型配置里要有这两个模型并配好凭据，否则派工和批准会报"模型不可用"并写明原因。想换模型，就用 C 把定义复制到用户层或项目层，再改文件里的 model。

"内部"分类里是两个程序内部使用的模型调用：解释器（把你的原话解读成确认、裁决等结构化决定）和草稿核验器（检查需求草稿是否符合你的意思）。它们的定义文件里只有 model 和 thinking 生效，提示词固定在程序里。复制出来的定义不写 model 时跟主会话的模型，不写 thinking 时不思考。设置的模型在本机找不到或没有凭据时，操作会报错并写明原因，不会悄悄改用主会话的模型。

## Shell 管理

通过终端执行的命令称为 Shell 任务。本窗口主会话与本工作区守护进程启动的任务统一登记，列表显示它们属于哪个窗口或代理，以及是否仍在运行；工作区外不计入。状态栏显示任务总数和各类来源的数量。

执行 `/one:ps` 打开管理页，选择任务后按 `K` 停止。如果系统无法确认进程是否已结束，这个任务显示为“待确认”，只能再次请求停止，不能手工标记为已停止。已结束的任务在页面看到它结束 1 分钟后从列表消失；子代理的 Shell 只显示进程信息，不显示命令和目录。

代理调用命令时可以设置 `background: true` 在后台执行，用户手动输入的命令保持等待执行结果。后台任务仍有超时限制，到期后停止命令及其子进程。

主窗口的 bash、write、edit 与普通 pi 一致，不另设文件或命令限制。PM 在需求 worktree 内通过受控提交工具按任务本地提交明确列出的文件；推送与合并由你在外部操作。

## 本机数据

数据根目录默认为 `~/.pi/agent/one-company/`；设置 `PI_CODING_AGENT_DIR` 时，使用该目录下的 `one-company/`。本机运行数据不随 Git 同步，主要存放位置如下：

| 位置（相对于数据根目录） | 内容 |
|---|---|
| `repos/<仓库身份>/data.db` | 需求状态、运行、对话、决策和文件占用 |
| `repos/<仓库身份>/index.db` | 当前代码、普通资料、结构关系与全文搜索片段的可重建持久索引；每次查询前按需增量对账，索引相关 action 为 init、status、refresh |
| `repos/<仓库身份>/requirements/<UUIDv7>/` | 需求的 `prod.md` 和只跟踪该正文的独立本机 Git 仓库 |
| `repos/<仓库身份>/prototypes/<UUIDv7>/` | 界面任务的 HTML 原型，每个版本一个文件 |
| `global.db` | 守护进程控制凭证、Git 交付工具开关与主会话 Shell 任务登记 |
| `repos/<仓库身份>/logs/<启动 UUIDv7>.log` | 每次后台进程启动产生的运行日志 |
| `sock/` | 窗口与后台进程通信所需的文件，位于数据根目录一级 |

业务数据使用 SQLite 保存，每条数据库记录以 UUIDv7 作为唯一主键。同一仓库的多个 worktree 共用仓库数据库；数据库文件及 WAL/SHM 附属文件只允许当前用户读写。数据根必须与该仓库全部 worktree 分离，初始化会核对真实路径。

内部存储服务提供完整一致性备份和隔离恢复：操作前要你在界面上确认，还有代理在运行时拒绝执行，维护期间其他连接的写入会失败；恢复副本默认 `needs_review`；旧备份中的 `active` 永不自动获得执行权限，较新的可信 closing/closed 元数据不会被旧状态覆盖。较新终态元数据可以保留，但旧备份不包含备份之后尚未纳入快照的新正文。

`one_company_requirement_manage` 经真实宿主 lifecycle、输入结构和 UI 交互授权，提供 create、updateDraft、confirmUpdate、read、diff、metadata 与 list（只给主代理，列出本窗口草稿与进行中需求的编号、标题与状态，不含正文）。保存 draft 只保存正文版本，不批准目标；确认目标也不自动授予规划或实施权限。正文存储内部只提供 create、save、readVersion、diffVersions、verifyVersion 五个固定接口：每个需求使用 UUIDv7 身份和独立本机 Git，只提交 `prod.md`，完成归档名固定为 `<UUIDv7>.<需求描述>.md`。closing/closed 或未知、冲突状态拒绝专用正文读取，现有项目快照入口在读取内容前排除 `docs/prod`。

需求事件服务按已批准的准确提交对和 hash 即时提供差异，持久保存事件元数据及 PM 消费位置，不在 SQLite/outbox 保存正文或 patch；草稿及外部未确认修改不产生批准通知。专用服务在读取与交付正文时复核生命周期和访问代次，进入 `closing` 后先撤权，不等待普通索引或积压通知。普通 read、Shell、Git 历史、MCP 等通用旁路没有全面正文拦截；主会话已有消息或摘要也不会自动清空。

普通日志使用 `.log` 文件，记录后台进程的正常输出和错误输出，不写入 SQLite。每次启动使用独立文件，权限为 `0600`（仅当前用户可读写）；启动失败时只查看本次日志末尾。关闭窗口后，后台进程仍可继续写日志。

需求正文位于上表的数据根目录中，不进入业务仓库。

## 多窗口与工作区

工作区按启动目录划分：在仓库内启动窗口时，工作区通常只有该仓库；从包含多个仓库的父目录启动时，可以管理其中发现的多个仓库。

同一仓库的不同 worktree 共用仓库身份和后台进程，从这些工作目录打开的窗口能看到同一批需求与运行。涉及多个仓库的接口或数据格式时，先在各仓库规范中写清约定，确认后再分别建立需求文档并启动需求代理。

同一文件或代码范围同时只允许一个任务写入；其他任务等待它停止写入并释放使用权后再接手，不同文件的任务可以并行。

## Git 交付

**进入最终检查前同步目标分支。** 目标分支是 origin 的默认分支；仓库没有 origin 时，是主仓库当前检出的分支。PM 在进入最终检查前把需求分支同步到目标分支的最新提交：能 rebase 就 rebase。rebase 有冲突时，需求分支的全部改动会合成一份，重新应用到目标分支最新提交上，冲突文件带冲突标记，由 PM 安排 worker 修复后再提交。需求分支不包含目标分支最近一次拉取到的提交时，不能开始最终检查。

**Git 交付工具默认关闭。** 执行 `/one:git-delivery` 选择开启后，主窗口才会出现交付工具。需求以完成关闭、归档写入之后，主代理可以用它交付：
- 先核对完成凭据。工作区里除了归档文件，不能有其他未提交的改动；归档内容必须和完成时记录的一致；分支里不能夹带别的 `docs/prod` 文件。
- 如果验收之后目标分支又前进了：能干净 rebase 就继续，并在 PR 里注明"验收后已自动 rebase，这部分未重新验证"；有冲突就停下，按新需求处理。
- 界面请你确认之后，才提交归档、推送核对过的那个提交。推送不会强推；远端分支不是快进时，推送会被拒绝。
- 推送后按远端地址选择 gh 或 glab，建立 PR；同一分支已有 PR 时直接复用。PR 标题是需求标题加 `[需求编号]`，PR 描述只有需求编号和交付信息，不含需求正文。
- PR 建好后，界面让你选"自己 review"或"自动合并"。自动合并会等仓库要求的检查通过后再合并，优先 squash；仓库不允许 squash 时，改用它允许的方式。这个选择只能由你在界面上做，模型不能替你选。

## 已知限制

**普通工具仍可能读到需求正文。** 需求关闭后，专用需求工具不再提供它的正文，项目索引和知识查询也不收录 `docs/prod` 里的归档。但普通的读文件、命令和 Git 历史工具没有被全面拦截。主代理需要时可以直接读 `docs/prod` 归档，例如用户问到已完成的需求，或合并代码遇到冲突要判断当初的要求，读到的只是历史记录，不当作当前目标。子代理的角色说明要求不主动去读，这只是说明，不是程序拦截；子代理误读时也不保证每次都能被发现。

**主会话不会自动忘掉旧需求。** 需求关闭时，框架会结束这个需求的 PM 和它派出的代理，并建议你清空上下文再开始新需求。主会话本身不会被自动清空，也不会被强制暂停。如果你继续在原会话里聊，之前读到的需求内容和摘要仍可能影响后面的回答。

**模型长时间不回话时，子代理会一直显示运行中。** 子代理的模型请求没有空闲超时。主窗口派出的检索可以让主代理停止后重新派出；PM 和它派出的子代理，需要你在面板上暂停或让主代理停止。

**一次解读最长接近 4 分钟。** 解释器把你的话整理成正式决定时，首次回答和重答各限时 120 秒，两次都用满时接近 4 分钟。

**同一需求问答和改版太多后，批准可能被拒。** 批准时，程序会把这个需求以往的待答问题、仍然有效的决定和沿用的原依据一起交给解释器参考。这部分最多 48K 字节，待答问题和仍然有效的决定各最多 20 条；连同草稿正文，整个请求最多 64KiB。超出时批准会被拒，并写明原因；重试没有用，只能先回答或处理掉已有的问题和待定事项。测试里，60 段的短草稿批准一版后再改一段，没有超出。

**装到仓库外的依赖程序查不到。** 全局 `pip install`、`go install` 这类安装不改仓库里的文件，交结果时的检查发现不了；只能靠 reviewer 核对代码里新出现的第三方 import。

**程序不核对回答里引用的行号。** 主代理按规则从带行号的工具结果里取行号，但程序不检查它写得对不对。

**测试范围有限。** 只在 macOS 上测过，真实模型验收只用 gpt-6.1-sol（解释器用 gpt-6-luna）跑过，没做过物理断电测试；Docker 安装测试在本机跳过。

## 常见问题

**无法连接后台进程时会怎样？**
启动代理、查询状态等操作会显示连接失败，不会假装成功。重新打开面板或窗口通常能让后台进程重新启动。

**为什么一个任务的问题也出现在另一个窗口？**
需求代理属于仓库的后台进程。提问、失败提示等消息会发送到仍连接该仓库的窗口，所以其他窗口也可能看到同一次运行的动态。

**为什么面板看不到别的项目？**
面板只显示当前工作区中发现的仓库，与窗口的启动目录有关。

**如何添加自定义角色？**
在用户角色目录 `~/.pi/agent/agents/` 或项目角色目录 `.pi/agents/` 下新增角色定义文件，然后在 `/one:agents` 中查看。同名角色优先使用项目定义；项目定义需要该项目在 pi 中受信任。

**需求代码什么时候提交？**
PM 在需求 worktree 分支内按任务完成情况本地提交明确列出的文件；检查阶段不提交。推送与合并默认由你在外部操作；用 `/one:git-delivery` 开启 Git 交付工具后，也可以让主代理提交归档、推送并建立 PR，推送前和合并方式都会在界面上问你。

**怎么查某个需求改了哪些代码？**
PM 每次提交时，程序都会在提交说明末尾加一行 `Requirement: <需求编号>`。在主分支运行 `git log --grep <需求编号>`，就能列出这个需求的提交；交付时的 rebase 和合并时的 squash 都不会让它丢失。反过来，想知道某个函数被哪些需求改过，运行 `git log -L :函数名:文件路径`，从列出的提交说明里找需求编号，再去 `docs/prod/<需求编号>.<需求描述>.md` 读当初的需求。在网页上自己 squash 合并时，推荐把仓库的 squash 默认提交说明设成"PR 标题加各条提交说明"（GitHub 里叫 Pull request title and commit details）：合并后的提交正文会带上每条原始提交的说明，PR 标题里没写需求编号也能查到。如果设成"只用 PR 标题"，要保证 PR 标题里有需求编号，否则合并后的提交里没有编号。

### 测试

每个新功能合并、上线之前，必须跑完全量测试并全部通过：下表里的类型检查、单元、集成、安装四项纯代码测试每次都跑；改了产品代码时，再加上与改动相关的真实模型验收。

| 命令 | 测什么 |
|---|---|
| `pnpm run typecheck` | 类型检查。不包含 `tests/` 下的文件，改了测试要实际运行 |
| `pnpm test` | 单元测试，4 个进程并行，本机一轮 10 分钟以上 |
| `pnpm run test:integration` | 集成测试：真实守护进程、真实临时 SQLite 库、跨进程 |
| `pnpm run test:integration:installed` | 同上，但先打包安装本包，守护进程从安装产物启动 |
| `pnpm run test:installation` | 按真实 pi 安装方式安装后再测；Docker 安装测试在没有 Docker 时跳过 |
| `pnpm run test:acceptance:parallel` | 真实模型验收，见下一节；9 条各跑 3 次一轮约 50 分钟 |

纯代码测试在当前提交上跑一遍、全部通过即可。测试临时目录是单层的 `/tmp/pi-t-XXXXXX`，整轮跑完按登记删除；不要改成多层目录，否则守护进程通信文件的路径会超过 macOS 的 104 字节上限。本机睡眠定时偏慢时，个别计时敏感的测试会偶发失败，单独重跑通过就不算代码问题。

### 真实模型验收

`tests/acceptance/` 下有 9 条验收，每条都在临时目录里真实安装本包、建样例项目，再由真实模型扮演主代理和各角色，从提需求一直走到完成关闭：

- 零自定义：全新数据根、只用包内默认定义，从需求草稿走到用户验收和完成关闭；首条消息里的长期约定会写进样例项目的 AGENTS.md。
- 自定义需求文档规范：受信任项目换了板块顺序，归档按项目规范插入实现记录和验收记录。
- 专业角色：复制默认 worker 为界面专业 worker 并挂项目 skill，PM 自动选中它；界面任务先做原型，用户通过后才实现。另有两条对照：装了专业 worker 但任务不匹配、装了匹配的专业 worker。
- 修错：样例项目预埋两处错误（快跑倍率写成 1.2、空中按 Shift 也加速），连测试都断言了错误行为；需求要求 1.5 倍且空中不加速，PM 要把代码和测试一起改对。
- 渐进需求：同一现场先做完"快跑"并合并，再做"跳跃"并在实施中追加"动画"，之后在同一会话和新会话里各问 13 个问题，检查回答的依据和出处。
- @需求：用 @ 指明一个或多个需求，追加功能、转告 PM、跨需求修正，由程序核对决定对象。
- 检索：主代理在没有需求、没初始化索引时派 explore 做网页和本地检索，再初始化索引检索。

跑法：

```bash
ONE_COMPANY_ACCEPTANCE_MODEL=<提供方>/<模型> \
ONE_COMPANY_ACCEPTANCE_OUTPUT=<绝对路径> \
pnpm run test:acceptance:parallel --repeat 3 [--only <编号…>]
```

- `ONE_COMPANY_ACCEPTANCE_MODEL`：主会话用的模型，例如 `5x/gpt-6.1-sol`。各角色和内部调用用包内定义里写的模型。
- `ONE_COMPANY_ACCEPTANCE_OUTPUT`：证据输出目录。每条每次一个子目录，里面有会话记录、`data.db`、`report.json`；总进度写在 `summary.txt`。
- `--repeat`：每条跑几次，默认 1。`--only`：只跑测试名冒号前编号匹配的那几条，例如 `--only M9-AC12`，所以测试名开头的编号不要删改。
- 运行时把 `~/.pi/agent/` 下的 `models.json` 和 `auth.json` 复制进一个只有当前用户能读写的临时 agent 目录，跑完随临时目录删除，不改动你自己的 `~/.pi/agent/`。
- 各条各次同时启动，相隔 20 秒；某次 10 分钟没有任何更新会被自动停下。
- 用 gpt-6.1-sol 时，本机 `models.json` 里它的思考等级 `off` 要写成 `null`：这个模型不接受关闭思考。

判定规则：真实模型输出有波动，所以要在同一个提交上同时跑 3 次，3 次全过才算通过；有一次不过，修好后在新提交上重新同时跑 3 次。改了产品代码后，相关验收在新提交上重跑；只改验收脚本或文档不重跑。全部失败时，先查会话记录里有没有 `429 usage_limit_reached`：模型服务有用量额度，用完后大约半小时恢复。

### 性能基准与测量工具

这三个工具不在测试命令里，需要时手动运行。

- **索引内核基准**：`node --experimental-strip-types tests/helpers/m3-benchmark.ts --output <全新的绝对路径目录> [--scenario all|cold|restart|events] [--smoke]`，只认 Node v22.19.0 或 v26.8.2，换版本会直接拒绝。用约 1000 个文件、文本不超过 20 MiB 的样例项目，测冷启动建索引、重启后复用、需求事件投递。参考目标：冷初始化 60 秒内；重启时未变文件不重新解析；已确认需求的事件 95% 在 2 秒内可投递。`--smoke` 只用几个文件快速检查脚本本身能跑。
- **知识查询基准**：`node --experimental-strip-types tests/helpers/m4-query-benchmark.ts --output <全新的绝对路径目录> --scenario smoke|formal`。参考目标：热态精确查询 95% 在 500 毫秒内；中文搜索和有限事实查询 95% 在 2 秒内。失败的样本也算进分母，不能剔除。
- **验收测量**：`node tests/acceptance/measure.ts <验收输出目录>`，从真实模型验收的证据里取数，生成 `<目录>/measure.md`：PM 接手用时与 token、检索的输入输出大小与父代理回读、PM 查角色目录与选中定义、各角色 token 与总用时。token 用模型返回的实际用量，字数不当 token；每次运行一行，给中位数和最大值，失败、截断、测不了的单独列出，不算"节省了百分之多少"。

记录基准结果时，写明机器（CPU、内存、系统）、Node 版本和冷热状态；所有样本和失败都要记，不能只挑最好的一次。
