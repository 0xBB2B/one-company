## 前置条件

- **pi**，运行它的 Node ≥ 22.19。
- **Git**，自己装好并能在 `PATH` 里找到。本包不会替你装。
- **模型**：所有角色默认跟随主窗口的模型和思考等级，主窗口选的模型要配好凭据，否则派工和批准时会报"模型不可用"。想给某个角色换模型，在 `/one:setting` 里改：PM、解释器、草稿核验器在目录的「模型」里改，worker 等角色按 C 复制一份定义再改文件里的 model。
- **在 Git 仓库里打开 pi**，或者在一个子目录各自是 Git 仓库的父目录里打开。

## 安装

```bash
pi install git:github.com/0xBB2B/one-company
```

角色代理随包提供，不用另装子代理系统。

卸载：`pi remove git:github.com/0xBB2B/one-company`。已启动的后台进程不会立即停止，空闲后自动退出，也可以手动停止；本机的需求和对话记录会保留，重装后还能读到。

## 上手

1. 在仓库里打开 pi，直接说需求，例如"登录页加上验证码登录"。
2. 需要你拿主意时，主代理（和你对话的那个代理）会弹出蓝色提问窗口。光标默认停在推荐项上，按回车就是"按推荐的来"。
3. 需求涉及界面时，主代理会先派原型设计师出 HTML 原型，浏览器打开后你在"确认原型"窗口里选通过或返工。
4. 需求草稿写好后，说"批准"。程序弹出黄色"批准需求"窗口，选"确认"才生效；草稿里通过的原型会列在窗口里，一起批准。
5. 后台的 PM 开始拆任务、派人干活，进度显示在输入框下方的状态面板里。
6. 面板里出现 ⚑ 就是在等你：按 ↓ 进入面板，选中这一行按 Enter 处理。
7. 你验收通过后，需求关闭。代码已经提交在这个需求的分支里，推送和合并由你自己做，推荐用 rebase 合并。

| 命令 | 用途 |
|---|---|
| `/one:setting` | 查看和复制角色定义，改 PM 和两个内部代理的模型，开关 Git 交付 |
| `/one:ps` | 查看和停止终端命令任务 |

## 功能

### 角色

你只和当前窗口的主代理说话，其他角色都在后台运行。

| 角色 | 做什么 |
|---|---|
| 主代理（main） | 和你理清需求：目标、不做什么、约束、允许的动作、还没定的事 |
| PM | 一个需求一个 PM，写计划、拆任务、派工 |
| worker | 写代码 |
| reviewer | 代码审查：实现是否合理 |
| acceptance/QA | 功能验收：实际行为是否符合批准的目标 |
| explore | 只读查资料，主代理和 PM 都能派 |
| prototype（原型设计师） | 需求涉及界面时出 HTML 原型，只能由主代理派 |

### 状态面板

```
● 2 个需求运行中
├─ ⠹ 角色跳跃、跳跃动画 · 任务 1/5 · ↻5 · 5 tool uses · 33.8k token (62%) · 12.3s
│    └ 派 worker 执行 login（第 2 次尝试）
│      └ ⚑ 待裁决：任务 login 两次未完成
└─ ⠹ 角色快跑 · 任务 0/3 · ↻42 · 38 tool uses · 91.0k token (84%) · 2m17s
     └ 规划中（计划 v2 · 3 个任务）
● 1 个原型设计运行中
└─ ⠹ 设置页（第 2 版）· brand-designer · ↻6/30 · 1m24s
● 1 个检索运行中
└─ ⠹ 联网 · 企业微信自建应用是否需要公网回调地址 · ↻2/15 · 12.3s
```

- 每行一个正在运行或已暂停的 PM，需求结束后这一行消失。
- 第一行是需求目标、任务进度、轮数、工具调用次数、token 用量（括号里是缓存命中率）和耗时。任务进度写成"任务 已完成几个/一共几个"，计划里没取消的任务都算，还没有计划或任务全部取消时不显示。轮数到耗时这几项都算上了 PM 派出的子代理。
- 第二行是它现在在做什么。行首 ⏸ 表示在等你或已暂停，计时停止。
- ⚑ 开头的行是等你处理的事项。
- PM 下面是这个窗口里主代理直接派出、还在运行的原型设计师。每条一行：原型名称和第几版、用的设计师定义、已用轮数和轮数上限、耗时。交稿或结束后这一行消失。
- 最下面一组是这个窗口里主代理直接派出、还在运行的检索。每条一行：联网还是查本地文件、要查的问题、已用轮数和轮数上限、耗时。

| 按键 | 作用 |
|---|---|
| ↓ / Esc | 进入面板（输入框为空且没有补全菜单时）/ 回到输入框。只有检索或原型设计在跑时没有可选的行，按 ↓ 不会进入 |
| ↑↓ + Enter | 打开选中的 ⚑ 事项 |
| p | 暂停或恢复这个 PM 和它的子代理 |

要停止需求，在对话里告诉主代理。多个窗口看到的是同一份数据，在一个窗口处理掉的事项，所有窗口都会消失。

<details>
<summary>检索那一组</summary>

- 只显示本窗口派出的检索，别的窗口派的看不到。
- 检索行选不中，也不能暂停。想停下某个检索，在对话里让主代理停。
- 检索结束后这一行消失，结果照旧以卡片插回对话。
- PM 派出的检索不在这一组里，算在 PM 那一行的汇总数字里。

</details>

<details>
<summary>⚑ 事项怎么处理、哪些话算你的决定</summary>

1. 按 Enter 后，事项的决策包插入对话。决策包只是材料，不是你的决定。
2. 主代理查清原因后，弹出问答窗口给建议，你选一项或自己写。

- 待裁决、待验收、取消或拒绝需求这类要登记的决定，选项文字由程序固定。只有你选中的选项、自己写的话，或在对话里亲手输入的话，才算你的决定。其他事项的回答只是给主代理的指示。
- PM 提交的计划被拒时，会按原因自己改一次。第二次还被拒，就出现"待裁决：PM 计划两次提交被拒"。
- PM 停下了、又没有任何东西会让它继续时，出现"待处理：PM 停下了"。
- PM 遇到还没派出的任务需要你决定（比如界面缺原型、要新增依赖）时，出现"待裁决：任务 xxx PM 上报需要决定"。

</details>

### 界面先出原型

需求涉及界面时（网页、桌面、手机界面，以及终端输出），主代理在澄清阶段派原型设计师出一个 HTML 原型。原型设计师是只出原型的子代理，只能由主窗口派出。终端界面的原型是网页里模拟的 80 列终端窗口。

1. 设计师交稿后，浏览器自动打开原型，同时弹出"确认原型"窗口。
2. 选"通过"，这一版写进需求草稿；选"返工"并输入意见，主代理带着上一版和你的原话重派设计师；选"放弃这一版"，它不再挡住批准；按 Esc 暂不决定，之后让主代理再打开。
3. 批准需求时，窗口里列出这一版一起批准的原型。批准需求就是连同原型一起批准。

<details>
<summary>原型规则</summary>

- 只认程序窗口里的选择，在对话里说"原型可以"不算数。
- 一个需求可以有多份原型，每份有名字，各自出版本、各自确认。新版本里没改的原型原样沿用。不要某份原型时，让主代理弹出"移除原型"窗口。
- 还有设计师在做、或交了稿你还没选的原型时，程序不让批准。原型通过之后文件被改过或被删了，程序也不让批准，会写明是哪份原型第几版，请让主代理重派设计师或把它移除。
- 需求被取消、驳回或完成时，它还在做的原型设计师随之停止；之后这个需求的原型不能再交稿、确认或移除。
- 程序窗口同一时间只显示一个。设计师交稿时你正开着别的窗口（主代理的提问、批准窗口、/one:setting 等），确认原型窗口等它关掉再弹。
- worker、reviewer、QA 都从批准的需求版本里拿原型。PM 发现要改界面、需求里却没有原型的任务，不会派出，会上报给你，你回主窗口补原型再批准新版本。
- 原型存在本机数据目录，单个文件不超过 1 MB。
- **升级须知**：升级前已在进行、计划里还带着旧原型记录（PM 给任务打界面标记、在面板里确认原型的那套）的需求，请在升级前做完或取消；升级前已经完成的需求，请先交付到 Git 并回收它的工作目录。升级后程序不处理这些需求：读到它们的计划或关闭记录会报格式错误，查关闭状态、回收工作目录都会失败，同一仓库的状态面板也可能因此显示不出来。

</details>

### @需求

在输入框打 `@`，补全列表会先列出草稿和进行中的需求，选中后插入 `@[标题#编号尾]`。一句话可以 @ 多个需求，也可以跨仓库。

- **带 @**：只针对 @ 到的需求。要改需求就改草稿再请你批准，批准后自动送到 PM；只是给 PM 的指示就转给 PM；其他情况直接回答。这句话里的"同意"只对 @ 到的需求有效。
- **不带 @**：主代理自己判断是新需求还是哪个已有需求。
- @ 了不存在、已关闭或状态异常的需求，会出现黄色提示，写明原因。

窗口不会绑定某个需求。重开窗口后，直接 @ 需求，或在面板里打开事项，就能接着处理。

<details>
<summary>补全列表的说明文字</summary>

- 只列当前工作区状态正常的草稿和进行中需求，排在文件前面。
- 说明里写"草稿"或"进行中"；PM 正在运行时写"PM 运行中"；工作区有多个仓库时还写仓库名。
- 编号尾至少 4 位，和别的需求重复时自动加长。
- PM 收到的转述会标为"主代理转述"，只作参考。
- 在面板打开 ⚑ 事项后，在问答窗口里答或直接在对话里说，都算对这个事项的回答，不用再 @。
- @ 到无效需求时，这句话只附上有效的需求。
- 要登记批准时弹出的黄色"批准需求"窗口，显示需求名、版本和简介。草稿带原型时，窗口里还列出这一版一起批准的原型（本次新确认、沿用上一版、本次移除），这时就算你 @ 了需求也会弹窗。还有原型在做或等你确认时，程序不让批准。
- 用 pi 的恢复对话功能后，也能直接 @ 需求或在面板里打开事项接着处理。

</details>

### 主代理提问

主代理需要你做决定时，会弹出蓝色提问窗口，不在对话里直接问。窗口里有问题、"根源自检"（为什么这些选项是解决根本问题而不是临时修补）、2 到 4 个选项，每个选项带一行理由，推荐的那个标绿色"推荐"并写出推荐理由，最后一项是"其他（自己输入）"。

- 光标默认停在推荐项上，直接按回车就是"按推荐的来"；↑↓ 切换。
- 移到"其他（自己输入）"直接打字，回车提交。
- Esc 表示暂不回答，问题会保留，之后在对话里答也算数。

你的回答就是你这一轮说的话：点选某一项时，是这一项的标题和理由；选"其他"时，是你输入的文字。主代理据此修改草稿，对话里会留下一块记录写着问题和你的回答。窗口里的回答不能用来批准需求或裁决事项，要批准请在主窗口直接说。主代理登记问题时必须写全根源自检、2 到 4 个选项，并恰好推荐一个、写明推荐理由；问题、根源自检、选项和理由里不能用"我""你""您"，要写"用户""AI"或需求里的角色（如负责人），这样你点选的理由能原样写进需求。不符合任何一条，程序都不会弹窗，会让它改好再登记。

### 长期约定写进 AGENTS.md

你在对话里提出长期约定时（比如"不允许使用泛型"），主代理会把它和本次功能分开，程序弹出黄色窗口，显示对仓库根目录 AGENTS.md 的改动：

- **写入**：写进文件。
- **不写入**或 Esc：不动文件。
- **其他**：输入修改意见，主代理改好后再弹一次窗。

主代理和子代理都不能用 edit、write 直接改这个文件，程序会拒绝。命令行里的写入程序拦不住，靠会话说明约束。

### Git 交付

- PM 在需求自己的 worktree 分支里，按任务本地提交明确列出的文件；检查阶段不提交。
- 进入最终检查前，PM 会把需求分支同步到目标分支的最新提交。目标分支是 origin 的默认分支，没有 origin 时是主仓库当前检出的分支。
- 推送和合并默认由你自己做。在 `/one:setting` 的「开关」里开启 Git 交付后，主代理可以替你提交归档、推送、建 PR，推送前和合并方式都会在界面上问你。开关存在 pi 设置文件 `one-company` 字段的 `git-delivery` 下（`true` 或 `false`），和模型设定一样分用户层和项目层，项目层优先，项目在 pi 里受信任才生效。

<details>
<summary>同步与交付的细节</summary>

**同步目标分支**：能 rebase 就 rebase。有冲突时，需求分支的全部改动合成一份，重新应用到目标分支最新提交上，冲突文件带冲突标记，由 PM 安排 worker 修复后再提交。需求分支不包含目标分支最近一次拉取到的提交时，不能开始最终检查。

**交付工具**（需求以完成关闭、归档写入之后可用）：

1. 核对完成凭据：除了归档文件（需求正文和它附带的原型 HTML），工作区不能有其他未提交的改动；归档内容必须和完成时记录的一致；分支里不能夹带别的 `docs/prd` 文件。
2. 验收后目标分支又前进了：能干净 rebase 就继续，并在 PR 里注明"验收后已自动 rebase，这部分未重新验证"；有冲突就停下，按新需求处理。
3. 你在界面确认后，才提交归档、推送核对过的那个提交。不会强推，远端不是快进时推送会被拒绝。
4. 按远端地址选 gh 或 glab 建 PR，同一分支已有 PR 就复用。PR 标题是需求标题加 `[需求编号]`，描述只有需求编号和交付信息，不含需求正文。
5. 界面让你选"自己 review"或"自动合并"，这个选择只能你在界面上做。自动合并会等仓库要求的检查通过后再合并：
   - GitHub 仓库允许 rebase 时用 rebase。不允许时，窗口按仓库允许的方式列出"自动合并（合并提交）""自动合并（squash）"让你选；一种都不允许，或者查不到仓库设置时，"自动合并"选不了，窗口里写明原因。
   - GitLab 按项目设置的合并方式合并。

</details>

### Shell 任务

终端里执行的命令叫 Shell 任务。`/one:ps` 列出本窗口主会话与本工作区守护进程（在后台持续运行代理的进程）启动的任务，工作区外不计入；选中按 `K` 停止。

<details>
<summary>Shell 任务的细节</summary>

- 列表显示每个任务属于哪个窗口或代理、是否还在运行。状态栏显示任务总数和各类来源的数量。
- 系统确认不了进程是否结束时，显示"待确认"，只能再次请求停止，不能手动标记为已停止。
- 已结束的任务从它实际结束算起 1 分钟后从列表消失，重新打开管理页也不会再出现；已结束任务的耗时停在结束那一刻，不再增长。
- 子代理的 Shell 只显示进程信息，不显示命令和目录。
- 代理可以用 `background: true` 在后台执行命令，你手动输入的命令会等结果。后台任务也有超时，到期后连同子进程一起停止。
- 主窗口的 bash、write、edit 和普通 pi 一样，不另加限制。

</details>

## 设置

### 规范从哪来

你不需要为这个包编辑任何文件。代理会读这几处规范：

| 位置 | 谁读 | 内容 |
|---|---|---|
| 包内 `shared/` | 所有代理 | 准确如实、聚焦需求、保护已有改动、同一问题试三次不成就停、收尾自检、搜索范围 |
| 包内 `rules/` | 主代理 | 主会话职责、沟通方式、递进式澄清、执行授权、归档需求、简报格式 |
| 包内 `role-rules/` | 对应职责 | 各职责的流程规矩，程序加在定义正文之后，冲突时以它为准 |
| 包内 `agents/` | 对应角色 | 五个内置角色定义：只有名称、描述、职责和空的 skills、mcp，正文为空 |
| `~/.pi/agent/AGENTS.md` | 主代理和每个子代理 | 你的个人规范，本包只读不写 |
| 仓库根目录 `AGENTS.md` | 主代理和每个子代理 | 项目长期约定；改了以后，新派出的子代理读到新内容 |

### 角色定义

| 来源 | 目录 | 说明 |
|---|---|---|
| 项目 | 仓库内 `.pi/agents/` | 优先级最高；项目在 pi 里设为受信任后才加载 |
| 用户 | `~/.pi/agent/agents/` | 对你的所有项目生效 |
| 包内默认 | `agents/` | 随包提供 |

同名时按项目 → 用户 → 包内的顺序取。定义只认 worker、reviewer、qa、explore、prototype 五种职责。新增一个角色，就在前两个目录里放一份 md 文件，然后在 `/one:setting` 里查看。正文只写这个角色的专长和偏好（例如"擅长 Go，新函数按 Go 官方库风格写说明注释"），可以为空；流程规矩由程序加上。reviewer 审查时会拿到被审任务所用 worker 定义的正文，违反其中写明的规范列为阻塞。

`/one:setting` 页面里角色定义只读，不提供编辑：左边目录选分类，→ 进右栏，↑↓ 选定义，回车展开详情，C 复制成新定义（选复制到用户层还是项目层）。要改定义就直接改对应目录里的 md 文件；PM、解释器、草稿核验器的模型在目录的「模型」里改，Git 交付在「开关」里开启。写错的定义列在"问题"分类里并写明原因，不会顶掉内置角色。

<details>
<summary>角色定义页的更多说明</summary>

- 表格每行一份生效的定义，列出名称、来源、模型和思考等级；焦点在目录时，底部写这一职责各层各有几份。
- 按键：←/Esc 回目录；在「模型」和「开关」里按 R 清除本层；终端窄于 60 列时，目录和内容轮流显示。
- 左边目录列五个职责（worker、reviewer、qa、explore、prototype），打开时停在 worker；下面是「模型」「开关」，有写错的文件时再多一项「问题」。
- 详情包括描述、skills、MCP、正文写没写和文件路径。
- 复制时先输入新名称，三层内不能重名。已有同名文件的层，以及项目未受信任时的项目层，会变暗选不中并写明原因。复制出的文件头部只改名称，没写 skills、mcp 时补上空列表，正文原样保留。复制完新定义被选中并标成绿色。
- "问题"分类还会列出缺少 role 的其他工具的定义、设置文件里写错的设定、头部 role 写成 pm、interpreter、draft-verifier 的旧定义文件（它们已不再使用，模型改在目录的「模型」里），以及项目未受信任时没加载的项目层。

</details>

### 换模型

所有角色默认跟随主窗口：PM、解释器、草稿核验器用主窗口当时的模型和思考等级；worker、reviewer、qa、explore、prototype 跟随派出它的一方（PM 派出的跟随这个 PM，主窗口直接派出的 explore 和 prototype 跟随主窗口）。

- **PM、解释器、草稿核验器**：在 `/one:setting` 目录的「模型」里改。回车后依次选模型（只列配了凭据的模型，另有"跟随主会话"）、思考等级（另有"跟随主会话"，所选模型不支持的等级选不了）、存到用户层还是项目层；R 清除当前这一层的设定。设定存在 pi 设置文件 `~/.pi/agent/settings.json` 或项目里 `.pi/settings.json` 的 `one-company` 字段下，项目层优先，项目在 pi 里受信任才生效。PM 下次启动、内部代理下次调用时生效。
- **worker、reviewer、qa、explore、prototype**：用 C 把定义复制到用户层或项目层，再在文件里写 `model` 和 `thinking`。`model` 写模型名（`gpt-6.1-sol`）或"提供方/模型名"（`5x/gpt-6.1-sol`）。

解释器负责把你的原话解读成确认、裁决这类正式决定；草稿核验器检查需求草稿是否符合你的意思。主窗口用推理较重的模型和较高的思考等级时，批准需求会变慢，可以在目录的「模型」里单独给解释器换一个快的模型。

<details>
<summary>模型解析规则</summary>

- 只写模型名时：主会话所在的提供方有这个模型就用它；没有、而本机只有一个提供方有，就用那一个；有多个就报错并列出候选。
- 设定或定义里的模型在本机找不到、没有凭据，或思考等级不被这个模型支持时，操作会报错并写明原因，不会悄悄换别的模型。设置文件写错的那一项不生效，改用下一层，并列在"问题"分类里。
- 批准草稿时，标题下只写了"由 PM 规划"或"用户未说明"的段落由程序判断：只要你明确确认了这份草稿的目标，这些段落就算已确认，解释器对它们拿不准也不会挡住批准；它们也不会被当成要实施的内容。你说要修改、暂缓或删掉这样的段落时，仍按你的话处理。
- 解释器的回答格式不对时，程序会写明是哪个字段错了，让它照着改一次。

</details>

### 给角色接 MCP

定义里的 `mcp` 列出这个角色要用的 MCP 服务（比如公司内网检索），名字要和 `~/.pi/agent/mcp.json` 里 `mcpServers` 下的服务名一致。用的是 pi 自带的 MCP，不用另装插件。

<details>
<summary>MCP 的细节</summary>

- worker、reviewer、qa、explore、prototype 的定义都生效；PM、解释器、草稿核验器没有定义文件，不接 MCP。
- 派出时只连接定义里点名的服务。模型通过 codemode 脚本或工具搜索调用它们的工具，服务设了 `exposure` 的按设置来；codemode 脚本里不能调用分类模型或生图模型。
- mcp.json 里没写 `exposure` 的服务，pi 默认按 codemode 处理：模型要先写一段脚本，再在脚本里调用服务的工具。pi 规定同一个进程最多同时运行 2 个 codemode 脚本，第 3 个会被直接拒绝。所有角色都在守护进程这一个进程里运行，共用这 2 个名额，所以几个角色同时用 MCP 时，后面的角色可能拿不到结果。
- 需要多个角色同时用某个服务时，在 mcp.json 里给这个服务写 `"exposure": "direct"`。这样它的工具会直接列给模型调用，不占 codemode 的名额。代价是这些工具的说明每轮都会发给模型；单次调用返回的文字超过 20 KB 时，pi 会截掉中间一段。
- 程序不按只读与否拦截这些工具。不想让角色用的工具，在 mcp.json 里用 `toolExposure` 设成 `hidden`。
- 点名的服务不存在或被停用时算缺失，配置写错时写明原因；两种情况都不报错，角色照常用本包自带的工具。
- 需要 OAuth 登录的服务，先在 pi 里用 `/mcp` 登录一次，守护进程不会弹浏览器。
- 连接日志在 `~/.pi/agent/mcp.log`。

</details>

## 原理

### 一个需求怎么流转

1. 主代理和你把需求整理成草稿。涉及界面时，主代理派原型设计师出原型，你在窗口里通过的原型写进草稿。你批准后（连同草稿里的原型），主代理派出 PM。
2. PM 先读批准的完整需求，回报它理解的目标、不做什么、约束、允许的动作、未决项和场景。主代理对照批准的需求和可信决定核对通过后，PM 才写计划（plan）和任务（task），并在已有授权内派工。这次核对本身不增加任何授权。
3. worker 实现，reviewer 审查，QA 黑盒验收。各职责的流程规矩由程序加进提示词；注释写法、语言规范这类只适合某类工作的要求，写在你自己定义的 worker 正文里，reviewer 按这份正文审。
4. 需要你决定的事，以 ⚑ 事项出现在面板上。

各角色的权限、版本和阶段门槛都由程序核对，角色说明或代理自称"通过"不能代替实际检查。explore 不继承派它的代理的完整会话，只拿到最小的问题范围，它的结果由派它的代理核验后再用。

<details>
<summary>explore 能做什么</summary>

- 在派出方的工作区里用 read、grep 和 `one_company_knowledge_query` 查本地代码，或联网搜索、抓取网页（含内网，首版不核对查询词）。search/fetch 是非业务能力，不增加第 11 个核心业务工具。
- 输出有界的结论、本地路径/行号/hash（宿主按文件实际内容核对）或 URL/短引文/时间，以及覆盖范围和未知项；用不了时如实报告。
- 不改代码或计划，派工输入不含需求正文，不能再派工。

</details>

### 改动范围检查

- **worker 交结果时**：改了不在本需求任何未取消任务写入范围内的文件，结果被拒收，恢复文件后才能重交。不分语言，`package.json`、`go.mod`、`Cargo.toml` 这类依赖清单被顺手改了也会被拦下；被 Git 忽略的文件不算。
- **PM 提交时**：要提交的文件只要有一个不在本需求任何任务（含已取消的）的写入范围内，整次提交被拒绝。
- **新增或升级第三方依赖**：PM 必须交给你裁决。你同意后，依赖清单才进入任务的写入范围，reviewer 审查时核对。
- **同一文件同一时间只有一个任务能写**，其他任务等它释放；改不同文件的任务可以并行。

### 守护进程

守护进程是在后台持续运行代理的进程。每个仓库一个守护进程，同一仓库的多个 worktree 共用。打开主窗口时自动启动，空闲后自动退出：空闲时限 10 分钟，合盖睡眠的时间不计入。

| 情况 | 结果 |
|---|---|
| 进程崩溃或电脑重启 | 未结束的运行标记为中断，不自动续跑；要继续就让主代理重新派出 PM |
| 断网 | 运行暂停；联网后在面板按 p 恢复，从断开的地方接着跑 |
| 模型请求超时 | 自动重试最多 3 次，间隔 2、4、8 秒；都超时就按失败结束并写明原因 |
| 主窗口直接派的检索遇到断网 | 按失败结束，结果卡片写明原因，需要时让主代理重派 |

### 多窗口与多仓库

- 工作区按启动目录划分：在仓库里启动就只有这个仓库；在包含多个仓库的父目录启动，可以管理其中发现的多个仓库。面板只显示当前工作区里的仓库。
- 同一仓库的不同 worktree 共用后台进程，从它们打开的窗口看到同一批需求。
- PM 属于仓库的后台进程，它的提问和失败提示会发给连着这个仓库的所有窗口。
- 涉及多个仓库的接口或数据格式时，先在各仓库规范里写清约定，确认后再分别建需求。

### 项目索引

代理通过 `one_company_knowledge_query` 查询代码索引。索引不监听文件；每次查询前，守护进程检查哪些文件变了，有变化就增量重建，所以结果总是反映查询那一刻的磁盘内容。grep、find、ls 工具不搜 `.git` 和被 Git 忽略的路径；命令行里的搜索由会话说明约束。

<details>
<summary>索引工具的参数、范围和预算</summary>

已接入仓库可由代理调用 `one_company_project_manage`，索引相关参数放在 `request` 里：

```json
{ "request": { "action": "init", "repoId": "<当前 lifecycle 中的 64 位仓库身份>", "preview": true } }
```

- 索引相关的 `action` 是 `init`、`status`、`refresh`；`preview` 只用于 `init`。设为 `true` 时，经真实宿主 UI 确认后只枚举一次路径元数据，不读文件正文、不创建 `index.db`。
- `init`（非预览）和 `refresh` 经真实宿主 UI 确认扫描范围后，由守护进程执行；`init` 成功即登记本仓库已初始化，此后守护进程持有索引，不依赖窗口在线。
- `status` 不扫描文件，返回索引状态和是否已初始化（`managed`）。
- 索引当前代码、配置和普通文档，提取 TS/TSX、JS/JSX、Go 的结构和可证明的同文件直接调用；其他语言只保留文件级记录。语法错误返回 `partial`，不回退旧正文。
- 不进索引的：`.git`、被 Git 忽略的路径、依赖、构建/缓存/日志、本机数据库、敏感凭据、链接文件、多链接文件、嵌套仓库、`docs/prd` 正文。归档需求只登记合法 UUID 文件路径，状态固定为 `unknown`，不产生活动需求授权。
- 默认预算：单文件 2 MiB、文本合计 20 MiB、20,000 个目录条目、64 层深度。发布前会再读一次核对 hash，所以一次完整构建最多读两倍文本预算。工具输出最多 32 KiB、100 项；截断、预算耗尽、跳过项和阻塞状态会明确返回。
- 索引存在仓库外的 `index.db`，未变文件按内容 hash 和解析器版本跨刷新、跨进程复用。同一仓库的多个窗口共用一份索引；切换分支后按当前分支重新对账。
- 增量对账按修改时间、大小和 ctime 找出新增、修改、删除的文件。结果标注索引代次；交付后文件再变化不追踪，下次查询自然读到新内容。
- `docs/prd` 始终只处理路径元数据。对账时发现归档与本机旧的活动需求对应，先阻止续接并标记待核对，不读归档正文，也不凭归档把需求改成 `completed`。可信关闭原因保持不变，删除归档或 Git 回退不会恢复授权。

</details>

### 本机数据

数据根目录默认是 `~/.pi/agent/one-company/`（设了 `PI_CODING_AGENT_DIR` 时放在该目录下的 `one-company/`），不随 Git 同步。需求正文也在这里，不进业务仓库。

| 位置（相对数据根目录） | 内容 |
|---|---|
| `repos/<仓库身份>/data.db` | 需求状态、运行、对话、决策和文件占用 |
| `repos/<仓库身份>/index.db` | 项目索引，可重建 |
| `repos/<仓库身份>/requirements/<UUIDv7>/` | 需求正文 `prd.md`，和只跟踪它的独立本机 Git 仓库 |
| `repos/<仓库身份>/prototypes/<需求编号>/<名称>.v<版本>.html` | 界面原型，每个版本一个文件 |
| `repos/<仓库身份>/logs/<启动 UUIDv7>.log` | 每次后台进程启动的运行日志 |
| `global.db` | 守护进程控制凭证、主会话 Shell 任务登记 |
| `sock/` | 窗口与后台进程通信用的文件，位于数据根目录一级 |

<details>
<summary>存储、日志与需求正文服务的细节</summary>

- **数据库**：SQLite，每条记录以 UUIDv7 为主键。同一仓库的多个 worktree 共用一个库；数据库文件和 WAL/SHM 附属文件只允许当前用户读写。数据根目录必须和仓库的所有 worktree 分开，初始化时核对真实路径。
- **备份与恢复**：提供完整一致的备份和隔离恢复。备份包含各需求批准版本引用的原型文件，打包前逐个核对指纹；草稿里还没批准的原型不保证包含。操作前要你在界面上确认；有代理在运行时拒绝执行；维护期间其他连接的写入会失败。恢复出的副本默认 `needs_review`；旧备份里的 `active` 永远不会自动获得执行权限，较新的可信 closing/closed 元数据不会被旧状态覆盖。保留的较新终态元数据不代表旧备份里有备份之后的新正文。
- **日志**：后台进程的正常输出和错误输出写进 `.log` 文件，不进 SQLite。每次启动一个独立文件，权限 `0600`；启动失败时只看本次日志末尾。关掉窗口后后台进程仍可继续写日志。
- **需求工具** `one_company_requirement_manage`：经真实宿主 lifecycle、输入结构和 UI 交互授权，提供 create、updateDraft、confirmUpdate、read、diff、metadata 和 list（只给主代理，列出本窗口草稿和进行中需求的编号、标题、状态，不含正文）。保存草稿只保存正文版本，不批准目标；确认目标也不自动授予规划或实施权限。
- **正文存储**：只有 create、save、readVersion、diffVersions、verifyVersion 五个固定接口。每个需求用 UUIDv7 身份和独立本机 Git，只提交 `prd.md`；完成后的归档名固定为 `<UUIDv7>.<需求描述>.md`；最终批准版本带原型时，每份原型另存为 `<UUIDv7>.<原型名称>.html`，和正文放在一起，双击就能在浏览器里打开。closing/closed、未知或冲突状态拒绝专用正文读取；项目快照入口在读取内容前排除 `docs/prd`。
- **需求事件服务**：按已批准的提交对和 hash 即时给出差异，持久保存事件元数据和 PM 读到的位置，不在 SQLite/outbox 里存正文或 patch；草稿和外部未确认的修改不产生批准通知。读取和交付正文时复核生命周期和访问代次，进入 `closing` 后先撤权，不等索引或积压通知。

</details>

## 已知限制

- **普通工具仍可能读到需求正文。** 需求关闭后，专用需求工具和项目索引都不再提供它的正文，但普通的读文件、命令、Git 历史、MCP 工具没有被全面拦截。主代理需要时可以直接读 `docs/prd` 里的归档（比如你问到已完成的需求，或合并冲突时要判断当初的要求），读到的只当历史记录。子代理被要求不主动去读，但这只是说明，不是程序拦截，误读了也不保证每次都能发现。
- **主会话不会自动忘掉旧需求。** 需求关闭时，框架会结束它的 PM 和子代理，并建议你清空上下文再开新需求。主会话不会被自动清空或暂停，继续在原会话里聊，之前的需求内容和摘要仍可能影响回答。
- **模型长时间不回话时，子代理会一直显示运行中。** 子代理的模型请求没有空闲超时。主窗口派的检索和原型设计师可以让主代理停掉重派；PM 和它的子代理需要你在面板上暂停或让主代理停止。
- **解读慢时要手动取消。** 解释器的回答不设时间上限，模型服务卡住时批准会一直等着，按 Esc 或修改输入可以取消；模型服务完全没有回应时，约 10 分钟后报错。
- **同一需求问答和改版太多后，批准可能被拒。** 批准时，程序会把以往的待答问题、仍有效的决定和沿用的依据一起交给解释器，这部分最多 48K 字节，待答问题和有效决定各最多 20 条；连同草稿正文，整个请求最多 64KiB。超了就拒绝批准并写明原因，重试没用，只能先回答或处理掉已有的问题和待定事项。测试里，60 段的短草稿批准一版后再改一段，没有超出。
- **装在仓库外的依赖查不到。** 全局 `pip install`、`go install` 不改仓库文件，交结果时的检查发现不了，只能靠 reviewer 核对代码里新出现的第三方 import。
- **程序不核对回答里引用的行号。**
- **测试范围有限。** 只在 macOS 上测过；真实模型验收只用 gpt-6.1-sol 跑过（解释器等内部调用跟随主会话，也用它）；没做过物理断电测试；Docker 安装测试在本机跳过。
- **Git 检查可能被跳过。** 安装时的 `preinstall` 会跑 `git --version`，失败就中止安装并提示"必须预先安装Git并确保PATH可用"。但 `--ignore-scripts`、pnpm 禁用第三方安装脚本，以及 `pi install /absolute/path` 这类只登记本地路径的安装会跳过它。运行时直接调用 `PATH` 上的 `git` 并传固定参数，不再做其他核验，所以这时缺 Git，会在第一次读取仓库身份、保存需求正文或受管提交时报错。

## 常见问题

**目录里没有 Git 仓库能用吗？**
pi 照常可用，但每次启动会警告，需求和后台代理用不了。`git init` 后重启 pi 即可。只 `git init`、还没有提交的仓库也能提需求：开工时确认窗口会问你，确认后程序在当前分支建一个不含任何文件的空提交（说明为 init）作为起点，不动暂存区和工作目录；取消就什么都不建。建提交需要配好 Git 的用户名和邮箱，没配时窗口会显示 Git 给的原因。

**连不上后台进程会怎样？**
启动代理、查询状态等操作会显示连接失败，不会假装成功。重新打开面板或窗口通常就能让后台进程重新启动。

**为什么别的窗口也看到了这个需求的提问？**
PM 属于仓库的后台进程，消息会发到所有连着这个仓库的窗口。

**为什么面板看不到别的项目？**
面板只显示当前工作区里的仓库，由窗口的启动目录决定。

**怎么查某个需求改了哪些代码？**
PM 每次提交都会在说明末尾加一行 `Requirement: <需求编号>`。

- 查一个需求的提交：在主分支跑 `git log --grep <需求编号>`。
- 查一个函数被哪些需求改过：跑 `git log -L :函数名:文件路径`，从提交说明里找需求编号，再去读 `docs/prd/<需求编号>.<需求描述>.md`；当时批准的界面原型在同一目录的 `<需求编号>.<原型名称>.html`。

**PR 用哪种方式合并？**
推荐 rebase：需求分支上的每个提交原样接到目标分支上，每条提交说明里的需求编号都留着，历史也是一条直线。把仓库设成只允许 rebase：

- **GitHub**：仓库 Settings → General → Pull Requests，勾选 Allow rebase merging，取消勾选 Allow merge commits 和 Allow squash merging。
- **GitLab**（需要 Maintainer 或 Owner 权限）：项目 Settings → Merge requests：
  - Merge method 选 Fast-forward merge。
  - Squash commits when merging 选 Do not allow。
  - 勾选 Enable automatic rebase prior to merge，目标分支前进了也能在合并时自动 rebase（GitLab 19.2 起可用）。
