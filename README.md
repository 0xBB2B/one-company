## 这是什么

one-company 的目标设计把开发分为三个层次，完整工作流仍在改造中：

- **主会话（main）**：在当前窗口理解真实需求，区分目标、非目标、约束、允许动作和未决项；对照已批准完整需求与可信决定，核对 PM 的接手理解，不无理由要求用户重新全量审批。
- **需求代理（PM）**：先读取当前已批准完整需求，回报目标、非目标、约束、允许动作、未决项与场景理解；主代理核对通过后，才正式产出和维护 plan 与 task，并在已有授权内派工。接手复核本身不增加授权，不另设产品 planner。
- **角色代理**：main 或 PM 可派只读 explore 查找证据；PM 安排 worker 实现、reviewer 审查和 acceptance/QA 黑盒验收。worker 给自己新增或修改的函数、方法、类、类型与导出常量写说明注释（参照 Go 官方库写法：以名称开头，说明做什么、各参数与返回值的含义），审查检查缺失或与行为不符；代理用 grep 直接搜索注释和代码。explore 不继承父代理完整会话，只接收最小问题范围，结果须由父代理核验整合。

代码审查检查实现是否合理，功能验收检查实际行为是否符合已批准目标。各角色的权限、版本和阶段门槛由程序核对，角色说明或代理自报通过不能代替实际检查。

> **当前进度**：M0—M8 已完成，正在进行最后的 M9 整体验收；目标仍为六类角色、10 个核心业务工具。当前阶段的 AC 状态、阻塞与续接说明见 [M9-STATUS.md](M9-STATUS.md)，权威范围见[当前计划](SQLITE-KNOWLEDGE-REBUILD-PLAN.md)。
>
> **阅读范围**：下面保留的长命令、面板、运行资源及设置说明没有按新流程重新完整验收，不能作为新流程授权或可用性承诺，当前能力以计划和 M9-STATUS.md 为准。旧工作流永久淘汰，未完成能力默认拒绝，不能由旧流程兜底；保留旧说明、资源和用户数据不表示旧入口可执行，也不表示旧运行资源已经全部删除。

## 安装

```bash
pi install git:github.com/0xBB2B/one-company
```

本地开发时使用 `pi install /absolute/path/to/one-company`，并先在该目录执行 `pnpm install --frozen-lockfile` 安装锁定依赖。本框架使用 pnpm 11.7.0，运行及测试均使用 Node；运行 pi 的 Node 版本需 ≥ 22.19。角色代理随包提供，无需另装子代理系统。

Git 是必须由用户预先安装的系统工具，并且需要位于 `PATH` 中。本包不捆绑、下载或自动安装 Git。正常 npm 安装以及由 pi 触发、且允许执行安装脚本的 npm 安装会运行 `preinstall` 检查：执行 `git --version` 失败时，安装以非零状态退出，并提示“必须预先安装Git并确保PATH可用”。

`--ignore-scripts`、pnpm 禁用第三方安装脚本，以及 `pi install /absolute/path` 这类仅登记本地路径的方式，可能跳过 `preinstall`。运行时直接调用 `PATH` 上的 `git` 并传固定参数，不再做其他核验；此时缺少 Git 会在首次需要 Git 的操作（读取仓库身份、保存需求正文、受管提交）处报错。

## 卸载

```bash
pi remove git:github.com/0xBB2B/one-company
```

卸载不会立即停止已启动的后台进程：它们会在空闲后自动退出，也可以手动停止。本机的需求状态、运行与对话记录会保留，重新安装后仍可读取。

## 快速开始

在 Git 仓库中打开 pi。本包的所有会话命令均以 `/one:` 开头：

| 命令 | 用途 |
|---|---|
| `/one:agents` | 查看角色定义并复制为新定义 |
| `/one:ps` | 查看和管理终端命令任务 |
| `/one:git-delivery` | 开启或关闭可选的 Git 交付工具 |

### 当前项目索引

已接入仓库可由代理调用 `one_company_project_manage`。公开参数只有：

```json
{ "action": "init", "repoId": "<当前 lifecycle 中的 64 位仓库身份>", "preview": true }
```

- `action` 只接受 `init`、`status`、`refresh`；`preview` 只允许用于 `init`。设为 `true` 时，经真实宿主 UI 确认后仅单次枚举路径元数据，不读取文件正文、不创建 `index.db`。
- `init`（非预览）或 `refresh` 经当前真实宿主 UI 确认扫描范围后，由仓库守护进程执行；`init` 成功即登记本仓库已初始化，此后守护进程持有索引，不依赖窗口是否在线。
- `status` 不扫描文件，返回当前索引状态及是否已初始化（`managed`）。
- 初始化和刷新会索引当前代码、配置与普通文档，提取 TS/TSX、JS/JSX、Go 的结构和可证明的同文件直接调用；其他语言只保留文件级记录。语法错误返回 `partial`，不会回退旧正文。
- `.git`、被 Git 忽略的路径、依赖、构建/缓存/日志、本机数据库、敏感凭据、链接文件、多链接文件、嵌套仓库和 `docs/prod` 正文都不进入索引。归档需求只登记合法 UUID 文件路径，状态固定为 `unknown`，不产生活动需求授权。
- 默认预算为单文件 2 MiB、文本集合 20 MiB、20,000 个目录条目、64 层深度。发布前会再次读取并核对 hash，因此一次完整构建最多读取两倍文本集合预算。工具输出最多 32 KiB、100 项；截断、预算耗尽、跳过项和必要阻塞状态会明确返回。

索引写入仓库外的 `index.db`，未变文件按内容 hash 和解析器版本跨刷新、跨进程复用。同一仓库的多个窗口复用守护进程与同一份索引；切换分支后按当前分支重新对账。

索引不监听文件。主会话和 PM、worker、reviewer、explore 都通过 `one_company_knowledge_query` 查询；每次查询前，守护进程按修改时间、大小与 ctime 找出新增、修改、删除的文件，有变化才增量重建，再在更新后的索引上查询。结果反映查询那一刻的磁盘内容并标注索引代次，交付后文件再变化不追踪，下一次查询自然读到新内容。`docs/prod` 始终只处理路径元数据；对账时发现归档与本机旧活动需求对应，先阻止续接并标记待核对，不读取归档正文，不凭归档将需求改成 `completed`。可信关闭原因保持不变，归档删除或 Git 回退不会恢复授权。

grep、find、ls 工具在主会话和各角色中都不搜索 `.git` 与被 Git 忽略的路径；命令行里的搜索由会话说明约束。

## 守护进程

守护进程就是负责持续运行代理的后台进程。每个仓库一个守护进程；同一仓库通过 Git worktree 建立的多个工作目录共用这个进程。打开主窗口时会自动启动，不需要手动操作。

进程会在空闲后自动退出，空闲时限为 10 分钟；设备合盖睡眠的时间不计入。进程崩溃或电脑重启后，之前未结束的运行会被标记为中断，不会自动续跑；需要继续时在对话中让主代理重新派出 PM。网络短暂断开时，相关运行先暂停，网络恢复后自动继续。

## PM 面板

面板位于输入框下方，只显示正在运行或已暂停的 PM，一个需求对应一个 PM；需求结束后该行消失。输入框为空且没有补全菜单时，按 ↓ 进入面板，按 Esc 回到输入框。

```
● 2 个需求运行中
├─ ⠹ 角色跳跃、跳跃动画 · ↻5 · 5 tool uses · 33.8k token (62%) · 12.3s
│    └ 派 worker 执行 login（第 2 次尝试）
│      └ ⚑ 待你裁决：任务 login 两次未完成
└─ ⠹ 角色快跑 · ↻42 · 38 tool uses · 91.0k token (84%) · 2m17s
     └ 规划中（计划 v2 · 3 个任务）
```

每个 PM 一行：需求目标、轮数、工具调用次数、token 用量与缓存命中率（均为 PM 与其全部子代理之和）、耗时。下一行是程序按真实状态生成的"在做什么"。等待你的决定或已暂停时行首显示 ⏸，计时停止。

以 ⚑ 开头的行是等待你处理的事项。用 ↑↓ 选中后按 Enter，事项的决策包会插入当前对话，主代理接着说明情况与选项；只有你随后亲手输入的话才作为你的决定。在 PM 行按 p 暂停或恢复该 PM，它派出的子代理随之暂停或恢复；停止需求请在对话中告诉主代理。多个主窗口看到的是同一份数据，一个窗口处理掉的事项会从所有窗口消失。

## @需求

在输入框里打 `@`，补全列表会在文件前面列出当前工作区状态正常的草稿和进行中需求，说明里写着"草稿"或"进行中"，PM 正在运行时写"PM 运行中"，工作区有多个仓库时还写仓库名。选中后插入 `@[标题#编号尾]`，编号尾至少 4 位，和别的需求重复时自动加长。一句话可以 @ 多个需求，也可以跨仓库。

- **带 @ 的话**：主代理知道这句话针对哪些需求，对每个需求分别判断：要改需求内容就修改草稿并请你批准，批准后改动会自动送到 PM；只是给 PM 的指示就转给 PM（PM 看到的内容标为主代理转述，只作参考）；其他情况直接回答。这句话里的"同意"只对 @ 到的需求有效。
- **不带 @ 的话**：主代理自己判断是新需求，还是涉及哪一个或哪几个现有需求。要登记批准时，程序会弹出黄色的"批准需求"窗口，显示需求名、版本和简介，你选"确认"才生效。
- **回答面板事项**：在 PM 面板打开 ⚑ 事项后，你接下来的回答就是对这个事项的裁决，不需要再 @。
- @ 了不存在、已关闭或状态异常的需求时，会给出黄色提示，写明是哪一个、为什么；这句话只附上有效的需求。

窗口不会一直"绑定"某个需求。重开窗口或用 pi 的恢复对话功能后，直接 @ 需求或在面板里打开事项就能接着处理。

## 主代理提问

主代理需要你做决定时（比如"起跳时机选哪种"），会弹出一个蓝色边框的提问窗口，不在对话里直接问。窗口从上到下是：

- 灰色一行写"提问"和需求名、版本，下面是加粗的问题。
- 灰色的"根源自检"：主代理说明这个问题针对的根源，以及为什么这些选项是从根源解决，而不是临时修补。
- 2 到 4 个选项。每个选项下面有一行灰色的理由，写它的好处或坏处；推荐的那个挂绿色"推荐"，再多一行绿色的推荐理由。
- 最后一项"其他（自己输入）"：不想从选项里挑时，用自己的话回答。光标移到这一项，下面就出现输入栏，直接打字，回车提交。

窗口打开时光标就停在推荐项上，直接按回车就是"按推荐的来"。↑↓ 选择，回车确认；按 Esc 表示暂不回答，问题会保留，之后在对话里直接回答也算数。

你在窗口里的选择或输入，就是你这一轮说的话，主代理据此修改草稿。窗口里的回答只算回答，不能用来批准需求或裁决事项；要批准时请在主窗口直接说。回答之后，对话里会留下一块记录，写着问题和你的回答。

主代理登记问题时必须写全根源自检、2 到 4 个选项，并恰好推荐一个、写明推荐理由；少了任何一项，程序都不会弹窗，会让主代理补全后重新登记。

## 角色与设置

目标角色固定为 **main、PM（requirement-agent）、explore、worker、reviewer、acceptance/QA** 六类。PM 直接负责规划，独立产品 planner 及其派工、恢复和别名入口在 M7 移除；上述目标尚未完成运行时接线，不表示现有角色资源已移除。

explore 在派出方工作区内用 read/grep 和 `one_company_knowledge_query` 检索本地代码，或联网搜索/抓取网页（含内网，首版不核对查询词）；search/fetch 是非业务能力，不增加第 11 个核心业务工具。输出为有界结论、本地路径/行号/hash（宿主按文件实际内容核对）或 URL/短引文/时间，以及覆盖范围和未知项；不可用时如实报告。它不修改代码或计划，派工输入不含 prod 正文，不再派工。

以下是尚未按新角色体系重新验收的既有角色来源与设置说明，不代表六类角色已全部可配置或可运行。角色定义来源：

| 来源 | 目录 | 生效范围 |
|---|---|---|
| 包内默认 | `agents/` | 随包提供 |
| 用户设置 | `~/.pi/agent/agents/` | 当前用户的项目 |
| 项目设置 | 仓库内 `.pi/agents/` | 当前项目 |

同名角色优先使用项目定义，其次是用户定义，最后是包内默认。项目定义只有在 pi 中将项目设为受信任后才会加载。

执行 `/one:agents` 打开角色定义页（只读）。页面是一张表，每行一份生效的定义，列出名称、来源（内置、用户、项目）、模型和思考等级；右上角写着各层各有几份定义。按键如下：

- ←→ 切换分类：左边是五个职责（pm、worker、reviewer、qa、explore），右边是"内部"和"问题"。
- ↑↓ 选择定义，回车在原地展开详情（描述、skills、MCP、文件路径），再按回车或 Esc 收起。
- C 复制为新定义：先在页内输入新名称（名称三层内不能重复，重名当场提示），再在窗口里选复制到用户层或项目层，每个选项都写出会生成的文件路径。已有同名文件的层、以及项目未受信任时的项目层会变暗、选不中，并写明原因。复制完回到原来的分类，新定义被选中并标成绿色。
- pm 和内部定义只能同名复制，用来覆盖内置的那一份。

设置页不提供编辑，请直接修改对应目录下的 md 文件。写错的定义、缺少 role 的其他工具的定义、以及项目未受信任时没加载的项目层，都列在"问题"分类里，写明原因，不会顶掉内置团队。

定义可选填 model（provider/id）、thinking 与 mcp；不填时继承派工时主会话的模型与思考等级。

"内部"分类里是两个程序内部使用的模型调用：解释器（把你的原话解读成确认、裁决等结构化决定）和草稿核验器（检查需求草稿是否符合你的意思）。它们的定义文件里只有 model 和 thinking 生效，提示词固定在程序里。不设置时沿用主会话的模型，并且不思考。想让它们用更快的模型，就用 C 把它复制到用户层或项目层，再改文件里的 model。设置的模型在本机找不到或没有凭据时，操作会报错并写明原因，不会悄悄改用主会话的模型。

## Shell 管理

通过终端执行的命令称为 Shell 任务。本窗口主会话与本工作区守护进程启动的任务统一登记，列表显示它们属于哪个窗口或代理，以及是否仍在运行；工作区外不计入。状态栏显示任务总数和各类来源的数量。

执行 `/one:ps` 打开管理页，选择任务后按 `K` 停止。如果系统无法确认进程是否已结束，页面会要求你核对；确认后可将它标记为已停止。

代理调用命令时可以设置 `background: true` 在后台执行，用户手动输入的命令保持等待执行结果。后台任务仍有超时限制，到期后停止命令及其子进程。

主窗口的 bash、write、edit 与普通 pi 一致，不另设文件或命令限制。PM 在需求 worktree 内通过受控提交工具按任务本地提交明确列出的文件；推送与合并由你在外部操作。

## 本机数据

数据根目录默认为 `~/.pi/agent/one-company/`；设置 `PI_CODING_AGENT_DIR` 时，使用该目录下的 `one-company/`。本机运行数据不随 Git 同步，主要存放位置如下：

| 位置（相对于数据根目录） | 内容 |
|---|---|
| `repos/<仓库身份>/data.db` | 需求状态、运行、对话、决策、消息、窗口、文件占用和错误详情 |
| `repos/<仓库身份>/index.db` | 当前代码、普通资料、结构关系与全文搜索片段的可重建持久索引；经宿主批准持续同步，公开 action 为初始化、状态和刷新 |
| `repos/<仓库身份>/requirements/<UUIDv7>/` | 需求的 `prod.md` 和只跟踪该正文的独立本机 Git 仓库 |
| `global.db` | 全局角色设置、Git 交付工具开关与主会话 Shell 任务登记 |
| `repos/<仓库身份>/logs/<启动 UUIDv7>.log` | 每次后台进程启动产生的运行日志 |
| `sock/` | 窗口与后台进程通信所需的文件，位于数据根目录一级 |

业务数据使用 SQLite 保存，每条数据库记录以 UUIDv7 作为唯一主键。同一仓库的多个 worktree 共用仓库数据库；数据库文件及 WAL/SHM 附属文件只允许当前用户读写。数据根必须与该仓库全部 worktree 分离，初始化会核对真实路径。

检测到旧 `data.sqlite`、`global.sqlite` 或其 WAL/SHM 残留时不会新建替代空库。M1 内部存储服务已提供受控迁移、完整一致性备份和隔离恢复：操作先登记并核对授权与写入者停止状态，恢复副本默认 `needs_review`；旧备份中的 `active` 永不自动获得执行权限，较新的可信 closing/closed 元数据不会被旧状态覆盖。较新终态元数据可以保留，但旧备份不包含备份之后尚未纳入快照的新正文。

M1 的 `requirement_manage` 已接通真实宿主 lifecycle、输入结构和 UI 交互授权，提供 create、updateDraft、confirmUpdate、read、diff 与 metadata。保存 draft 只保存正文版本，不批准目标；确认目标也不自动授予规划或实施权限。正文存储内部只提供 create、save、readVersion、diffVersions、verifyVersion 五个固定接口：每个需求使用 UUIDv7 身份和独立本机 Git，只提交 `prod.md`，完成归档名固定为 `<UUIDv7>.<需求描述>.md`。closing/closed 或未知、冲突状态拒绝专用正文读取，现有项目快照入口在读取内容前排除 `docs/prod`。内部状态职责见 [需求状态基础](runtime/requirement-state.md)。

需求事件服务按已批准的准确提交对和 hash 即时提供差异，持久保存事件元数据及 PM 消费位置，不在 SQLite/outbox 保存正文或 patch；草稿及外部未确认修改不产生批准通知。专用服务在读取与交付正文时复核生命周期和访问代次，进入 `closing` 后先撤权，不等待普通索引或积压通知。这些基础能力不表示完整 PM 调度、最终 QA 和完成关闭流程已经上线。普通 read、Shell、Git 历史、MCP 等通用旁路没有全面正文拦截；主会话已有消息或摘要也不会自动清空。

普通日志使用 `.log` 文件，记录后台进程的正常输出和错误输出，不写入 SQLite。每次启动使用独立文件，权限为 `0600`（仅当前用户可读写）；启动失败时只查看本次日志末尾。关闭窗口后，后台进程仍可继续写日志。

旧版本在仓库内 `.pi-company/` 保存的规范与需求文档不再被读取或更新，也不产生任何授权，可按需保留或自行删除。新需求正文位于上表的数据根目录中，不进入业务仓库。

## 多窗口与工作区

工作区按启动目录划分：在仓库内启动窗口时，工作区通常只有该仓库；从包含多个仓库的父目录启动时，可以管理其中发现的多个仓库。

同一仓库的不同 worktree 共用仓库身份和后台进程，从这些工作目录打开的窗口能看到同一批需求与运行。涉及多个仓库的接口或数据格式时，先在各仓库规范中写清约定，确认后再分别建立需求文档并启动需求代理。

同一文件或代码范围同时只允许一个任务写入；其他任务等待它停止写入并释放使用权后再接手，不同文件的任务可以并行。

## Git 交付

**进入最终检查前同步目标分支。** 目标分支是 origin 的默认分支；仓库没有 origin 时，是主仓库当前检出的分支。PM 在进入最终检查前把需求分支同步到目标分支的最新提交：能 rebase 就 rebase。rebase 有冲突时，需求分支的全部改动会合成一份，重新应用到目标分支最新提交上，冲突文件带冲突标记，由 PM 安排 worker 修复后再提交。需求分支不包含目标分支最近一次拉取到的提交时，不能开始最终检查。

**Git 交付工具默认关闭。** 执行 `/one:git-delivery` 选择开启后，主窗口才会出现交付工具。需求以完成关闭、归档写入之后，主代理可以用它交付：
- 先核对完成凭据。工作区里除了归档文件，不能有其他未提交的改动；归档内容必须和完成时记录的一致；分支里不能夹带别的 `docs/prod` 文件。
- 如果验收之后目标分支又前进了：能干净 rebase 就继续，并在 PR 里注明"验收后已自动 rebase，这部分未重新验证"；有冲突就停下，按新需求处理。
- 界面请你确认之后，才提交归档、推送核对过的那个提交。推送不会强推；远端分支不是快进时，推送会被拒绝。
- 推送后按远端地址选择 gh 或 glab，建立 PR；同一分支已有 PR 时直接复用。PR 描述只有需求标题和交付信息，不含需求正文。
- PR 建好后，界面让你选"自己 review"或"自动合并"。自动合并会等仓库要求的检查通过后再合并，优先 squash；仓库不允许 squash 时，改用它允许的方式。这个选择只能由你在界面上做，模型不能替你选。

## 已知限制

**普通工具仍可能读到需求正文。** 需求关闭后，专用需求工具不再提供它的正文，项目索引和知识查询也不收录 `docs/prod` 里的归档。但普通的读文件、命令和 Git 历史工具没有被全面拦截。主代理需要时可以直接读 `docs/prod` 归档，例如用户问到已完成的需求，或合并代码遇到冲突要判断当初的要求，读到的只是历史记录，不当作当前目标。子代理的角色说明要求不主动去读，这只是说明，不是程序拦截；子代理误读时也不保证每次都能被发现。

**主会话不会自动忘掉旧需求。** 需求关闭时，框架会结束这个需求的 PM 和它派出的代理，并建议你清空上下文再开始新需求。主会话本身不会被自动清空，也不会被强制暂停。如果你继续在原会话里聊，之前读到的需求内容和摘要仍可能影响后面的回答。

## 常见问题

**无法连接后台进程时会怎样？**
启动代理、查询状态等操作会显示连接失败，不会假装成功。重新打开面板或窗口通常能让后台进程重新启动。

**为什么一个任务的问题也出现在另一个窗口？**
需求代理属于仓库的后台进程。提问、失败提示等消息会发送到仍连接该仓库的窗口，所以其他窗口也可能看到同一次运行的动态。

**为什么面板看不到别的项目？**
面板只显示当前工作区中发现的仓库，与窗口的启动目录有关。

**如何添加自定义角色？**
在用户角色目录 `~/.pi/agent/agents/` 或项目角色目录 `.pi/agents/` 下新增角色定义文件，然后在 `/one:agents` 中查看。同名角色优先使用项目定义；项目定义需要该项目在 pi 中受信任。

**需求代码什么时候提交？**
PM 在需求 worktree 分支内按任务完成情况本地提交明确列出的文件；检查阶段不提交。推送与合并默认由你在外部操作；用 `/one:git-delivery` 开启 Git 交付工具后，也可以让主代理提交归档、推送并建立 PR，推送前和合并方式都会在界面上问你。

## 开发

内部语法解析入口 `runtime/syntax-parser.ts` 使用随包分发的 TS/TSX、JS/JSX、Go 语法 WASM 和固定版本 `web-tree-sitter` 运行时。安装后可离线解析，不需要 CodeGraph 或现场编译；资源缺失、损坏或版本不兼容时明确失败。该低层入口只解析调用方提供的源码字符串；项目扫描、结构提取、持久化和宿主授权分别由 `runtime/project-index-policy.ts`、`runtime/code-extractor.ts`、`runtime/index-store.ts`、`runtime/project-index-service.ts` 和 `runtime/project-manage-tool.ts` 负责。资源来源、许可证和使用边界见 [解析资源说明](resources/tree-sitter/README.md)。

pnpm install --frozen-lockfile
pnpm test
