# Git 提交规范

## 适用范围

只要任务涉及以下任一操作，就必须遵守本 skill：

- 创建新的 Git commit
- 使用 `--amend` 修改 commit
- 使用 rebase、cherry-pick 或其他方式重写 commit 信息
- 根据用户要求整理、拆分或合并提交

只查看历史、查看 diff 或检查工作区时，不需要创建提交。

在 pi-company 会话中，使用 `pi_company_git_commit` 创建提交：`paths` 填明确的文件列表，`message` 填提交信息。重命名同时列出新旧路径。工具核对写入范围并保留其他文件的暂存内容；Shell 的 Git 元数据只读，不能用 bash 执行 add、commit、amend 或历史重写。外部 hook、filter 或签名程序无法安全执行时停止并报告原因，不关闭检查。以下终端命令示例适用于包外的用户终端。

## 提交信息格式

普通提交优先采用以下格式：

```text
<type>(<scope>): <subject>

[按需补充背景、关键方案、影响、验证或项目约定的 trailers]
```

小改动可以只包含标题；复杂改动、破坏性变更或需要后续维护者理解取舍时，再补充有价值的正文。正文不要求使用固定字段名。

`scope` 可选。当修改明确属于某个模块时使用，例如 `cluster`、`dashboard`；跨模块或范围很小时可以省略：

```text
perf: 优化集群后台结果格式
```

### 标题规则

- 使用 Conventional Commits 类型，类型必须是小写英文。
- 优先使用以下类型：`feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert`。
- 标题使用中文或英文均可，简洁说明修改意图，不以句号结尾。
- 避免使用 `update`、`修改一些问题`、`临时修复` 等无法表达意图的标题。
- 标题尽量控制在 72 个字符以内。
- 破坏性变更使用 `!`，例如 `feat(api)!: 调整接口响应结构`，并在正文中说明迁移影响。

### 正文换行

正文段落之间的分隔必须是实际换行。`\n` 只是字符串中的转义写法，不是换行；如果它出现在提交记录中，Git 会把反斜杠和字母 `n` 原样显示出来。

创建多行提交时，优先使用单引号 heredoc，避免把包含 `\n\n` 的字符串直接传给 shell 或提交工具：

```sh
git commit -F - <<'EOF'
<type>(<scope>): <subject>

[按需补充背景、关键方案、影响、验证或项目约定的 trailers]
EOF
```

不得在提交正文中出现字面量 `\n`；提交前后都应检查实际内容，而不是只检查生成提交信息的变量或命令参数。提交后可使用以下命令检查：

```sh
if git show -s --format=%B HEAD | grep -Fq '\n'; then
  printf '%s\n' '提交正文包含字面量 \n' >&2
  exit 1
fi
```

### 正文规则

- 正文是可选的；标题已经清楚表达小改动时，不要为了填模板而补正文。
- 复杂改动需要正文时，优先说明与后续维护相关的信息，例如背景、关键方案、边界、用户可观察影响或验证结果。
- 不要为了满足格式而编造根因、实现方法或验证结果；无法确认的信息应省略或先补充诊断。
- 正文内容可以使用中文，必要时保留代码、命令、路径和标识符原文。
- 项目已有正文模板或 trailers 时，优先遵循项目约定。
- 除非用户明确要求，否则不要在正文中加入与本次修改无关的历史背景或未来计划。

## 创建提交的流程

1. 先确认用户确实要求提交；仅完成代码修改时不要擅自创建 commit。
2. 执行 `git status --short` 和 `git diff`，确认工作区状态、改动范围和是否存在无关变更。
3. 将本次改动归纳为清晰的标题；对复杂改动、破坏性变更或需要保留上下文的提交，补充必要正文。无法准确说明改动意图或影响时，先补充诊断，不要急于提交。
4. 会话中先确定受管提交的文件列表；用户终端只暂存本次需求涉及的文件，优先使用明确路径的 `git add`，避免无意加入临时文件、日志、构建产物或用户未要求的改动。
5. 对暂存区执行 `git diff --cached` 和 `git diff --cached --check`，确认内容与提交信息一致且没有空白错误。
6. 在提交前运行适用的测试、类型检查、构建或 lint；是否将验证结果写入正文，取决于项目约定和该信息对后续维护的价值。无法运行时，不要编造验证结果。
7. 会话中通过 `pi_company_git_commit` 传入实际多行的 message 和明确文件 paths；用户终端可采用正文换行中的 heredoc 方式；不得把字面量 `\n` 写入提交，不使用 `--no-verify` 绕过已有校验。
8. 提交后执行 `git status --short`、`git show --stat --oneline HEAD` 和 `git log -1 --format=%s`，并确认提交正文（如有）不含字面量 `\n`，工作区状态符合预期且标题格式正确。

## 修改历史提交

- 用户明确要求时，才允许 amend、rebase 或其他历史重写。
- 重写后的每一条目标 commit 都必须重新检查标题；如有正文，再检查其内容和换行。
- 历史重写会改变 commit hash；操作前说明影响，完成后报告新的 hash。
- 不要为了满足格式而擅自重写未被用户指定的历史提交。

## 提交前检查清单

提交前必须逐项确认：

- [ ] 标题符合 `<type>(<scope>): <subject>` 或 `<type>: <subject>`。
- [ ] `type` 是允许的小写类型。
- [ ] 小改动可以只有标题；需要正文时，正文包含对后续维护有价值的信息。
- [ ] 正文（如有）使用实际换行，不含字面量 `\n`。
- [ ] 复杂改动或破坏性变更已说明必要的背景、影响、边界或迁移信息。
- [ ] 暂存区没有无关文件、临时文件或构建产物。
- [ ] `git diff --cached --check` 通过。
- [ ] 适用的测试或检查已运行，未运行项已说明原因。

## 示例

```text
perf(cluster): 优化后台结果格式

将结果分为集群信息、执行概览和任务明细，减少长篇审核内容中的定位成本。

已通过 git diff --check；未执行 TypeScript 检查是因为项目未安装依赖。
```
