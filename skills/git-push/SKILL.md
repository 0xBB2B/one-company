# git-push：提交前审查与推送

## 适用边界

只在用户明确要求提交 PR、Pull Request、Merge Request，或显式调用 `/skill:git-push` 时执行。任何 push 或 PR/MR 创建前必须先完成审查一节的核对；核对不通过或无法核对时一律 fail closed，不推送、不开 PR/MR。

## 预检

在仓库根目录确认：当前分支不是主分支、不是 detached HEAD；工作区改动都属于本次需求；没有来源不明的未跟踪文件。如果本工作区内的其他宿主（其他窗口或同仓库 worktree）在同一需求或同一片代码范围上有活动任务，不切换分支、不重置——等待对方释放范围或改用不冲突的分支后再继续，不得为了腾出分支而覆盖别人的工作现场。

## 采集审查快照

本地 commit 完成后、任何远端写入前，调用 `pi_company_review` 工具（参数：需求身份、仓库工作目录、目标基线分支）。该工具内部先计算当前分支头与内容指纹形成审查快照，再向本次需求所在仓库的守护进程派出 reviewer 执行提交前白盒审查；主会话对每次需求只一次直接派出 reviewer，不重复触发。

## 核对

reviewer 返回结果后，按三重口径核对，任一不通过都按 FAIL 处理：

- 对象字段：返回结果的顶层字段齐全、类型正确，没有约定外字段。
- 语义：`verdict` 为 PASS 时没有遗留的问题项；`verdict` 为 FAIL 时至少有一条具体问题，不接受没有诊断的 FAIL。
- 快照：结果绑定的分支头与内容指纹必须与本次采集的审查快照完全一致；工作区在等待结果期间发生了新的改动，视为快照失效，需要重新采集。

三重核对全部通过且 `verdict` 为 PASS 才能进入下一步。

## 暂存与推送

核对通过后，只 `git add` 本需求获准范围路径——即需求文档规范变更表与相关改动涉及的路径，不暂存范围外的文件。推送时使用通过审查时采集的分支头（审查快照里的那一次提交），不使用之后可能已经前进的最新 HEAD，也不使用强制推送。创建合并请求前，重新确认远端分支头仍与已审快照一致；不一致时旧结果失效，回到"采集审查快照"重新走一遍。

## FAIL 处理

`verdict` 为 FAIL、核对未通过或结果不可用时：

1. 主会话向用户展示归因选项（实现缺陷、规范缺陷、需要产品决策等），用户选择后以 actor user 调用 `decision_record` 记录该归因，取得回执后才能行动；用户未形成选择时保持本地现状不变，不推送、不开 PR/MR。
2. 确认该需求下无未停止运行（旧需求代理的运行已经结束，没有排队、运行中或等待作答的运行）；仍有未停止运行时先请求停止，不得在旧运行仍活动时回退。
3. 调用 `pi_company_workflow retreat` 把需求回退到 executing，参数写明 `stage` 为 executing、`version` 为需求当前版本号、`reason` 为归因说明、`decisionId` 为上一步记录的决定编号；成功后再调用 `pi_company_dispatch` 重新派出需求代理，这次派出获得新运行身份，由新的需求代理接手归因细化与返修，不复用旧运行的上下文。
4. 返修完成后由需求代理自行重走验收，主会话不代为验收。
5. 需求代理返修完成、验收通过后，主会话重新形成一次新的本地提交，重新采集审查快照，重新走一遍审查流程，直到通过才能推送。

## 完成报告

完成后用中文报告：审查快照（分支头与内容指纹）、核对结果、推送的分支与目标分支、PR/MR 地址、期间是否发生过 FAIL 与如何处理、尚未解决的问题。
