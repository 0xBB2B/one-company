# spec-docs：规范与需求包格式

## 目录与事实源

```
<repo>/.pi-company/
├── spec/
│   ├── INDEX.md                     - [<name>](<域>/<name>.md) — <description>
│   ├── GLOSSARY.md                  | 锚点 | 定义 | 别名 |
│   └── <域>/<name>.md               一规则一文件，≤100 行，五节：目的/逻辑/约束/例子/验收
└── requirements/<YYYY-MM-DD>.<slug>/
    ├── requirements.md              定义：name/title/created + 四节
    ├── tasks/INDEX.md               ≤30 行
    ├── tasks/NN-<name>.md           任务定义，≤200 行（扣除示例与成品代码块）
    └── acceptance.md                验收者唯一写入：result/date + 结果表/未覆盖/结论
```

`spec/` 是系统“做什么”的唯一事实源：需求澄清的结果直接写成规则文件的新增、修改或删除，任务、验收与修订归因都以规则文件为准。规则文件只描述当前行为，不写日期、变更来源、历史对照或过渡标记；作废的规则直接删文件，变更追溯只靠 git。`requirements.md` 只说明本次变更为什么做、改了哪些规则文件、边界在哪，不复述规则内容。

决策记录与运行信息只保存在本机，不进入仓库：谁做了什么决定、任务当前处于哪个执行阶段、由哪次派工产出，均属过程状态，不落盘为仓库文件。

新需求先建分支（分支名 = slug），复制 `requirements.template.md`，建立 `tasks/INDEX.md` 与 `acceptance.md` 占位，形成需求包。

`<slug>`、`<域>` 与规则 `<name>` 均为小写英文短横线连接。

## spec/<域>/<name>.md

一规则一文件，只讲一件事，不超过 100 行，强制放在域子目录下，即便该域当前只有一条规则。frontmatter 与正文章节固定：

```
---
name: <kebab-case，与文件名一致>
description: <一句话，不超过 80 字>
---
# <规则标题>

## 目的
<一句话：这条规则为谁解决什么问题>

## 逻辑
<3～10 行：触发、过程、结果，只描述对外可观察行为>

## 约束
- C-1：<EARS 句式，一条一行>
- C-2：...

## 例子
<一个具体场景：输入、过程、预期结果>

## 验收
### AC-1 <标题>  ← C-1
- 触发: 命令 <命令行> | 请求 <方法 路径 + 载荷> | 操作 <界面步骤>
- Given: <前置状态，含数据准备>
- When: <外部输入，与触发一致>
- Then: <可观察输出：返回值 / 响应 / 界面 / 副作用>
```

约束用 EARS 五种句式之一：

| 句式 | 模板 |
|---|---|
| 恒定 | 系统应 <行为> |
| 事件驱动 | 当 <事件> 时，系统应 <行为> |
| 状态驱动 | 在 <状态> 期间，系统应 <行为> |
| 异常行为 | 如果 <非期望条件>，系统应 <行为> |
| 可选特性 | 若启用 <特性>，系统应 <行为> |

每条约束必须可证伪，能写成“什么输入 → 什么结果”；“健壮、友好、高性能”之类没有判定标准的表述禁写。每个功能点至少有一条异常行为约束覆盖失败路径。每条约束至少被一条验收覆盖，每条验收至少回指一条约束。`C-n` 与 `AC-n` 只在本文件内编号，删除条目后编号不复用；跨文件引用写 `<域>/<name>/AC-n`。Then 必须是黑盒可观察结果，数值指标写具体数字和单位。

规则文件禁写源码文件路径、目录名、模块名、函数名、类名、变量名、第三方库名、技术栈名、数据库表名和代码块；命令行、HTTP 路径和界面元素属于黑盒契约，允许写。禁止引用其他规则文件，需要的内容内联复述；术语直接使用 GLOSSARY.md 登记的写法。

## spec/INDEX.md 与 spec/GLOSSARY.md

INDEX.md 每条一行，按域分组，同域按字母序：

```
# 规范索引

## <域>

- [<name>](<域>/<name>.md) — <description>
```

GLOSSARY.md 是全项目术语的唯一权威源，只登记实际使用过的术语与写法：

```
# 术语表

| 锚点 | 定义 | 别名 |
|---|---|---|
| order | 用户提交购买意图后生成的待履约交易单据 | 订单 |
```

## requirements.md

frontmatter 仅含 `name`、`title`、`created` 三个定义字段，不含运行或调度字段。正文固定为且只能为第 1～4 节：

1. 背景：谁在什么场景遇到什么问题；现状只写与现行规范的差异
2. 目标与非目标：目标带可量化指标与单位
3. 规范变更：表格，每行一个规则文件，`| <域>/<name> | 新增 或 修改 或 删除 | 一句话说明 |`；单个需求 1～8 行，超出时拆成多个需求
4. 边界与已知坑：数据量与并发、失败与重试、上下游约束、已知坑

多仓库工作区下，跨仓库的接口或数据契约以成品代码块内联在第 3 节或第 4 节对应说明里，不外链其他仓库的文档。

## tasks/

任务目录由 planner 产出，一任务一文件，每个文件自包含：仅凭该文件、其 refs 指向的规则文件与仓库现有代码即可完成测试、实现与审查，不写“见 requirements”式引用。

任务文件不包含 status、step、agent、commit、note、parallel 等运行或调度字段；这些是执行过程中的调度状态，只存在于执行现场，不写入任务文件本身。

`tasks/INDEX.md` 不超过 30 行：按阶段分组列出任务，每行 `- [T-n <标题>](NN-<name>.md) — <一句话>`，依赖标 `[依赖: T-m]`；每个任务恰被链接一次；末尾列出被否定的备选方案及理由。

`tasks/NN-<name>.md`（`NN` 为两位执行序号，`<name>` 为 kebab-case）frontmatter 字段顺序固定，只含定义字段：

```yaml
---
id: T-n
title: <标题>
depends_on: [T-a, T-b]        # 只能引用编号更小的任务
files: [<绝对路径>, ...]        # 生产文件 ≤ 2；同一生产文件只归一个任务
refs: [<域>/<name>/AC-n, ...]  # ≤ 3 条
verify: <一条命令，退出码 0 即通过>
---
```

正文章节固定为：目标 / 业务规则（来源：<域>/<name>。逐字内联所引 AC 与其回指的 C）/ 涉及文件（`- 新建|修改（生产|测试|非生产）：<路径> — <说明>`）/ 成品定义（可选，仅声明式产物存在，DDL、API 契约、配置的完整成品，exec 原样落盘不得改写）/ 新增第三方依赖（可选，仅本任务引入新库时存在）/ 函数清单（按文件列函数名与职责一句话，不写参数、返回值与实现）/ 协作关系（函数调用关系与外部依赖）/ 验证方式。

三个角色各读其块：test-engineer 读业务规则与验证方式；impl-engineer 读涉及文件、成品定义、新增第三方依赖、函数清单、协作关系；review-engineer 读整份。

一个任务是一个竖切片：`files` 中生产文件不超过 2 个，`refs` 不超过 3 条；触碰同一生产文件的行为合并进同一个任务，不得拆成 `depends_on` 链。`files` 两两不相交的任务才可并行（可并行 = 无依赖关系且生产文件互不相交，由调度推导，不写入任务文件）；`depends_on` 只能引用编号更小的任务；本次新增或修改的每个规则文件的每条验收至少被一个任务 refs 覆盖。

每份任务文件扣除示例代码块与成品代码块（含首尾围栏）后最多 200 行，不限制任务的代码改动量。按整份文件统计物理行，计入 frontmatter 元数据及其分隔行、标题、正文和空行，每份文件独立计算。示例代码块与成品代码块的全部内容及首尾围栏不计数，除此之外的内容均正常计数。计数恰为 200 行时满足行数要求，超过 200 行时报告任务文件超过 200 行。不限制预估或实际代码改动量，不得仅因代码改动超过 200 行而要求拆分任务或拒绝任务。任务文件中的围栏代码块只用于示例与成品定义，检查器扣除全部围栏代码块，不论围栏用 ``` 还是 ~~~ 书写。

计数示例：
- 在 200 行需计数内容之外新增一行元数据、一个标题或一个空行，均变为 201 行并报告任务文件超限。
- 在 200 行需计数内容之外，添加连同围栏共 102 行的示例代码块、成品代码块或同时添加两者，仍为 200 行；在代码块外再新增一行说明文字则为 201 行并报告任务文件超限。
- 其余任务要求均满足且任务文件需计数内容为 200 行时，预估修改 500 行代码、实际修改 600 行代码，在规划和完成核对时均满足任务文件行数要求。

## 验证约定

每个任务文件的“验证方式”节固定为五个要点：

```markdown
## 验证方式
- 真实入口：<公开命令 / 工具 / 页面操作及其契约>
- 必须成立：<行为 1>；<行为 2>
- 场景：正常 / 拒绝 / 重复 / 交错 / 超时 / 退出（不适用项写明理由）
- 模拟边界：允许模拟 <外部边界>；必须真实贯通 <连接或保护>
- 三层责任：目标测试 <命令>；受影响回归 <命令或范围>；集成验证 <由谁在何处完成>
```

“模拟边界”只允许把不受本仓库控制的外部系统换成模拟实现，凡是本次改动引入或修改的连接、鉴权与保护逻辑必须真实贯通，不得连同外部边界一起模拟掉。“三层责任”把验证拆成三层各自的命令或范围：目标测试证明本任务的行为，受影响回归证明没有破坏既有行为，集成验证证明整条链路在真实环境里可用，三层缺一不可、各写各的命令或负责人。

## acceptance.md

验收报告 frontmatter 为 `result: accepted | rejected` 与 `date: <YYYY-MM-DD>`，正文固定为结果表、未覆盖和结论；acceptance.md 只由验收者唯一写入，其他角色不得代写或预填结果。结果表列 `条目 | 结果 | 观察`，逐条列出被验收的任务或验收编号、通过或失败、观察到的具体现象。任一条目 FAIL 或存在未覆盖项即 `rejected`。

## 机械检查

规划者不得自行编写检查脚本，只能调用本 skill 提供的机械检查命令：

```
lint.sh --spec <规则文件>...          检查规则文件格式（≤100 行、name、五节、C/AC 双向覆盖、四行验收、无实现细节）
lint.sh <requirements.md>            检查需求文档四节、规范变更表、被引用规则与索引
lint.sh --tasks <requirements.md>    转发 node task-check.ts <requirements.md>
node task-check.ts <requirements.md> 任务集合机械检查
```

任务检查（`lint.sh --tasks` 与 `task-check.ts`）的退出码与输出：全部通过 0 且首行 `PASS: 仅证明任务机械条件，不证明行为正确`；任一条件不满足 1，每条一行 `FAIL: <任务id或文件>: <字段或缺项>: <原因>`；参数错误/输入不可读/类别无法确认 2 且 `FAIL: <原因>`。规则文件与需求文档检查（`lint.sh --spec`、`lint.sh <requirements.md>`）成功只输出 `PASS`，格式不满足退出码 1，参数错误或输入不存在退出码 2。原文比对以行为单位：任务的业务规则节须逐行包含所引验收块（含标题行及其回指）与回指约束的原文，行尾空白不计，不约束顺序。路径推导：requirementDir = dirname(requirements.md)，specRoot = requirementDir/../../spec，tasksDir = requirementDir/tasks；生产文件类别声明缺失即退出码 2。

机械检查只证明任务集合的格式与引用完整，不证明业务行为正确、不执行 verify 命令、不自动修复；确认前仍需人工逐条检查每条约束是否必要、无歧义、单一且可证伪，验收是否能由第三方仅凭规则文件执行。
