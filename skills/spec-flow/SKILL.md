# spec-flow：需求生命周期

## 角色定位

主会话负责在当前窗口内澄清需求、编写与维护规范（各仓库 `.pi-company/spec/` 下的规则文件）和需求文档（`.pi-company/requirements/<需求身份>/requirements.md`）、向用户取得确认、派出需求代理，并在需求代理提问时中继作答。主会话不规划任务、不派出 planner、worker 或 acceptance 等角色，也不自行推进 confirmed 之后的执行阶段——这些由需求代理在守护进程内独立完成。

## 工作区识别

按当前窗口的启动目录发现所在的仓库子树；一个窗口可能只对应单个仓库，也可能对应多个仓库组成的工作区。本次需求只涉及单个仓库时，规范与需求文档只写入该仓库。需求涉及多个仓库时，跨仓库的接口或数据契约先写入各仓库规范（以成品代码块内联在对应规则文件里），再分别在各仓库建立独立的需求文档；任何一个仓库的需求文档都不得靠引用其他仓库的文档来说明契约。

## 澄清与规范

按递进式澄清逐维度提问：先自查已有规则文件与代码，能确定的给"结论 + 依据"请用户确认，未定项按目标、行为、边界、验收逐维度收口，每轮聚焦一个维度并给出具体选项与推荐项。

- 规则文件一规则一文件、固定五节（目的/逻辑/约束/例子/验收）、不超过 100 行、不含实现细节（不写源码路径、模块名、函数名、技术栈、数据库表名）。
- 需求文档固定四节（背景/目标与非目标/规范变更/边界与已知坑），格式约定沿用规范与需求包格式的 skill，本 skill 不重复定义。

每收口一个维度立即写盘：新增、修改或删除对应规则文件，同步 INDEX 与术语表，同步更新需求文档第 3 节规范变更表。用户在给出的具体选项中作出选择时，先调用 `decision_record`（actor user）再写盘；AI 自主形成的取向调用 `decision_record`（actor ai）。未回答、忽略或取消的问题不记录。

## 确认与派出

没有未收口的维度、每条约束可证伪且有验收覆盖后，只给出规范变更表和本轮变更摘要请用户确认，不在对话中回显文件正文。

用户确认后先调用 `decision_record`（actor user）记录该确认决定，取得回执后依次执行 `pi_company_workflow init`（建立本次需求的本机流程状态）、以 `init` 返回的当前 version 与该决定的 decisionId 调用 `pi_company_workflow advance confirmed`（推进到 confirmed）、`pi_company_dispatch`（派出需求代理）；任一步骤失败即停止，不继续派出。需求涉及多个仓库时，逐仓库重复上述四步，各仓库独立记录确认决定、建立状态并分别派出需求代理。

## 中继

需求代理在规划或执行中遇到需要用户裁决的问题时，会把提问转达给主会话；主会话向用户展示需求代理给出的选项并等待用户选择，用户作答后调用 `pi_company_reply` 把答复回传给发出提问的需求代理。

如果提问是请求变更已写入规范的契约，由主会话裁定后先更新相关仓库的规范文件，再调用 `pi_company_forward` 把裁定结果转发给对应需求代理，不由需求代理自行改写规范。

## 补充需求

用户在需求进行中追加说明时，先判断是否属于本工作区某个进行中需求：属于则调用 `pi_company_forward` 把补充内容转发给对应需求代理，并向用户回执已转发；不属于任何进行中需求则视为新需求，从澄清与规范一节重新开始。

## 续接

`/pi-company:resume` 从本机流程数据定位所在需求：本机流程数据是阶段判断的唯一依据，不从文档推断阶段——需求文档本身不记录运行状态。存在多个候选需求时，列出候选让用户选择；本机流程数据缺失或损坏时阻塞并向用户说明具体原因，不得据此臆测阶段、也不得凭空继续派工。

发现有角色运行处于中断状态时，通过 `pi_company_agents` 的 `resumeInterrupted` 动作续接该运行，不重新从头派出需求代理。
